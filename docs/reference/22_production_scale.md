# 22. 本番スコアは 8 エピソードで決まる

**採点環境で走っているのは 8 本だけである。** 手元の検証は 84 件なので、
**10 倍以上の差がある別の母集団を見ていた。**

> **出典は採点環境から持ち帰ったログ 4 本**（`outputs/prod_eval_results/*.md`）。
> 評価パイプラインは 1 エピソードの開始ごとに `POST /reset` を 1 回投げるので、
> **その回数がエピソード本数である。**
> `solution/` 以下の説明文と `docs/` の他の `.md` は出典にしていない。

## 数えた結果

| 提出 | `/reset` | `/act` | 1 本あたりのステップ数 | 総合スコア |
|---|---|---|---|---|
| 8/09（n=50） | 1 | 4 | — | 0.058 |
| 8/10（n=10） | **8** | 1,978 | 247 | 0.096 |
| 8/10（n=5 ＋ EMA 0.3） | **8** | 1,826 | 228 | **0.1409** |
| 8/11（追加学習した重み） | **8** | 2,173 | **272** | **0.016** |

8/09 のログは途中で切れている（`/act` が 4 回しか残っていない）。残る 3 本はすべて 8 である。

**割り算が裏付けている。** 打ち切りは 300 ステップなので、8 本で 1,826 ステップなら平均 228 ステップ。
追加学習した重みは平均 272 ステップまで伸びており、**打ち切りに張り付いた本数が増えた**
と読める。8 本という本数と矛盾しない。

## ここから分かる 3 つ

### 1. 総合スコアは成功率ではない

8 本の成功率が取れる値は 0、0.125、0.25 … である。
**0.1409 も 0.096 も、そのどれとも一致しない。**
したがって成功率そのものではなく、**何かで重み付けした合成値**である。
配点表は配布されていないため、手元で再現することはできない。

### 2. 0.1409 → 0.016 は 8 本の上の差である

**8 本しかないので、1 本の結末が変わるだけでスコアは大きく動く。**
「8.8 倍の悪化」は倍率としては大きいが、**その根拠となる標本は 8 本**である。
重みが本当に悪いのか、8 本のうち数本が偶然崩れたのかを、この数字だけでは分けられない。

**過去の記述はこの点を踏まえていない。** 8.8 倍という表現を根拠に原因を断定した
文章が `docs/strategy/` にあるが、標本の大きさが書かれていない。

### 3. 手元の 84 件は本番を予測しなかった。母集団が違うから当然である

| | 本数 | 何を並べているか |
|---|---|---|
| 手元の検証 | 84 | LIBERO-plus の摂動 7 種 × スイート 4 つ |
| **採点環境** | **8** | ログに出るのは `タスク用途: 3_Omni` だけ。**中身は非公開** |

手元で「追加学習 0.500 / 素 0.476」と並んでも、**8 本の結果は言い当てられない。**
片方が片方の部分集合である保証すら無い。

**ただし提出どうしの比較は成り立つ。** 運営 Q&A No.29 が
「評価タスク集合・各エピソードの初期状態・乱数シードは採点環境に固定値として
組み込まれており、提出のたびに変わることはない」と回答している。
**毎回同じ 8 本なので、対応の取れた比較になる。**
向き（上がった／下がった）は読めるが、**小さな差を追うには本数が足りない。**

## 何を調べるべきか（優先順）

| 順 | 調べること | なぜ先か | どうやって |
|---|---|---|---|
| **1** | **8 本の正体** | **これが分かれば、手元の検証を本番に合わせられる。** いま最も効く | 運営へ質問する（タスク名の開示ではなく、**スイートと本数**だけでも判断が変わる）。Q&A No.29 は本数を聞かれずに固定と答えているので、聞く価値はある |
| **2** | 手元の検証を 8 本に近づける | 84 件は 2〜3 時間かかるうえ本番を当てない。**当たらない指標に時間を払っている** | **手順は [../howto/04_proxy_eval.md](../howto/04_proxy_eval.md) にある。** 配布 4 タスク × 2 エピソードで本番と同じ形になる |
| 3 | 1 コマを何回見るか | 素と同じ濃さに揃えるため。**バッチ数とデータのコマ数が要る** | `lerobot/libero_plus` の `meta/info.json` の `total_frames` と、学習の `train_config.json` の `batch_size` |
| 4 | 打ち消しの実測 | ソースの証明を数値で確かめる。**優先度は低い**（上の 3 つが決まれば設計が変わる） | 素の重みの `empty_cameras` だけ 2→0 にして、同じ noise で行動を比べる |

## 学習はどうすべきか

**これは判断であり、事実ではない。** 上の表の「不明」が埋まれば変わる。

| | 中身 | なぜ |
|---|---|---|
| **いまの学習は続ける** | 止めない | 学習率・warmup・最後の学習率・ステップ数が**素と完全に一致**している。崩壊した回の組み合わせではない |
| **手元の 84 件を合否の判定に使わない** | 使うのは「壊れていないか」の確認だけ | 本番を予測しないことが実測で分かっている。**動かなくなった・固まったといった大きな壊れ方は拾える** |
| **1 コマあたりの回数を素に揃える** | 20,000 ステップ × バッチ 32 で全データ | 素がその濃さで作られている。**それ以上濃くする根拠が無い** |
| **学習の条件を重みと一緒に持ち出す** | `merge.py` が同梱する | 今回それが無くて原因を確かめられなくなった |
| **小さなスコア差を追わない** | 8 本では読めない | 0.14 → 0.02 のような大きな動きだけを信号として扱う |

## 確認しなおす手順

```bash
# 本番のエピソード本数（採点ログから数える）
for f in outputs/prod_eval_results/*.md; do
  printf '%s  /reset %s  /act %s\n' "$(basename "$f")" \
    "$(grep -c 'POST /reset' "$f")" "$(grep -c 'POST /act' "$f")"
done

# 学習中のチェックポイントが素と同じ条件か（差が出た項目だけ並ぶ）
python3 -c "
import json
run = json.load(open('<学習の出力先>/checkpoints/last/pretrained_model/config.json'))
base = json.load(open('work/artifacts/model_weights_base/config.json'))
for k in sorted(set(run) | set(base)):
    if run.get(k) != base.get(k):
        print(k, base.get(k), '->', run.get(k))
"
```

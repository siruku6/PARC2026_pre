# 18. 手元の 72 行は、採点側で効いた重みを「効かない」と言った

**2026-08-29 に分かった。**同じ重み（`001500`・画像側を開けた 1,500 歩）について、
手元と採点側が逆の答えを出した。

| | 手元の 72 行 216 本 | **採点側 8 エピソード** |
|---|---|---|
| 成功率・点 | 合計点 0.3674 → **0.3351** | Track1 0.370 → **0.492**／Track2 0.154 → **0.233** |
| 対にした符号 | 成功が **9 対 20**（p = 0.061） | — |
| 狙ったカメラ条件 | **3 対 2・3 対 3 の引き分け** | — |
| 読み | **「効いた証拠なし・弱い悪化の疑い」** | **2 トラックとも上がった** |

出典は `work/final_eval/0828_224224_track2_trial1500_s1500` と
`b_PARC2026_final/outputs/submission_logs/track{1,2}/260829_pi0.5_5.0.1.txt`。

## なぜ食い違ったのか —— 測っている量が違う

**手元の合計点は成功率で決まる。**`score_composite.py` の式は
`成功率 × なめらかさ` で、なめらかさは 0.47〜0.52 の狭い範囲しか動かない。
**だから手元の点は、ほぼ成功率の写しである。**

**採点側の Track1 では成功率が動いていない。**打ち切り（300 歩）は
4.2.0 も 5.0.1 も 0 本で、**歩数の合計はむしろ増えた**（1,039 → 1,053）。
**+0.122 は、衝突かなめらかさ 5 項から来ている。**

**つまり手元の 72 行は、上がった当の量を見ていない。**
成功率だけを見て「引き分け」と言い、**衝突となめらかさの改善を丸ごと落とした。**

## だからどうするか

| 使い方 | 可否 |
|---|---|
| **重みの良し悪しを決める** | **使わない。**8/29 に外した |
| **壊れの検出**（大崩れ・起動しない・特定の条件で 0 になる） | **使う。**倍率 1.15 の大崩れはこれで見えた |
| 設定（推論の摘み）の可否 | **対にした符号だけを読む**（`compare_runs_by_task.py`）。率は読まない |

**重みの判定に使える物差しは、いまは 1 日 1 トラック 1 回の提出だけである。**
**だから枠は「重みが変わったとき」に使う**——設定の振り分けに使ってはいけない。

**手元の評価を重みの判定に戻すには、なめらかさ側の分解能を上げる必要がある。**
いまの `score_composite.py` は 5 項を JSON の集計値から作っているので、
**同じ成功率のなかでの改善が 0.01 単位でしか出ない。**エピソードごとの
7 数値を記録する仕掛け（`open_items.md` の F6）が入れば、そこは変わる。

## 一般化して残すこと

**「効かせたい集合で測り直す」だけでは足りなかった。**8/28 に
`blend 4` で学んだのはそれだったが（[knowledge/17](17_track3_picks_the_wrong_object.md) の周辺）、
**今回は集合ではなく「測っている量」が違っていた。**

**確かめること。**手元の物差しが、採点側で動く量と同じ量を見ているか。
**見ていない量は、どれだけ本数を増やしても見えない。**

## 【9/5 に足した】反対向きの読み —— 偏っているのはリーダーボードの側かもしれない

**上の結論（手元の物差しを重みの判定に使わない）には、反証の候補が出ている。**
出典は他チームの報告で、[../materials/slack_talks/weakness_of_leader_board_eval.md](../materials/slack_talks/weakness_of_leader_board_eval.md)
にそのまま置いてある。**まだこちらの手で確かめていない。**

**報告の中身。**同じデータ・同じレシピ・同じ歩数で、**学習の乱数の種だけを変えた 2 本**を
作ったところ、リーダーボードの点には大きな差が出た。**ところが手元で 200 タスクを回すと
87/200（43.5%）と 83/200（41.5%）で、ほとんど差が無かった。**

**この報告が正しければ、読みはこう変わる。**

| | 8/29 の読み | **9/5 に出た反対向きの読み** |
|---|---|---|
| 手元の 72 行と採点側が食い違う理由 | **手元が、採点側で動く量を見ていない** | **採点側が 8 エピソードしかなく、たまたま得意なタスクが多く入っただけ** |
| 手元の評価の使い道 | 壊れの検出だけ | **本数を増やせば、リーダーボードより信用できる物差しになりうる** |
| 提出枠の使い方 | 重みが変わったときだけ使う | 変わらない（枠は 1 日 1 本のままである） |

**2 つの読みは排他ではない。**「測っている量が違う」（上の節）と
「8 エピソードは少なすぎる」は、どちらも成り立ちうる。

**どちらが効いているかを分けるには、本数を増やして測り直すしかない。**
これが `open_items.md` の `F3`・`F8`・`F12`・`F31` を切らずに残している理由である。

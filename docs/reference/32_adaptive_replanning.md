# 32. adaptive replanning —— 迷った場面だけ、引き直しを早める

**何をするものか。** π0.5 は 1 回の推論で 50 コマぶんの行動をまとめて作り、先頭 16 コマ
だけ実行してから作り直す。**この「16」を、場面によって 8 に縮める**のが adaptive
replanning である。縮める判定には、**同じ観測から複数回引いたときの答えのばらつき**を使う。

**なぜばらつきで判定できるのか。** π0.5 は乱数から行動を作るので、同じ観測でも引くたびに
違う答えが出る。**うまくいっていない場面ではこのばらつきが大きい**、という報告がある
（[../materials/articles/260829_zenn_PARC2026_trial.md](../materials/articles/260829_zenn_PARC2026_trial.md)
6 節。成功した場面の 2.6〜3.4 倍）。**つまり出力のばらつきが、その場面での自信の無さを表している。**

> **この文書の書き方について。** コードの根拠は同梱 LeRobot v0.6.0 と
> `solution/policy_server.py` の行番号で示した。秒数の根拠は採点環境から持ち帰った
> ログ 14 本（`outputs/prod_eval_results/*.md`）である。**リポジトリ内の他の `.md` は
> 根拠にしていない。** 再確認する手順は末尾にある。

## 2. なぜ待ち行列を作り直さずに済むのか

**同梱 LeRobot の `select_action` は、`config.n_action_steps` を
`predict_action_chunk` が返った「後」に読む。**

```python
# work/artifacts/vendor/lerobot/policies/pi05/modeling_pi05.py:1231-1236
if len(self._action_queue) == 0:
    actions = self.predict_action_chunk(batch)[:, : self.config.n_action_steps]
    self._action_queue.extend(actions.transpose(0, 1))
return self._action_queue.popleft()
```

そして `predict_action_chunk` は、medoid のために既に差し替えている関数である
（`policy_server.py` の `_install_chunk_sampler`）。
**だから差し替えた関数の中で `policy.config.n_action_steps` に代入して返せば、
その回の消費歩数がそれになる。** RTC（`_get_action_rtc`）のように待ち行列を
自分で持つ必要が無い。

## 3. ばらつきは既に計算されていた

medoid は総当たりの距離を出して、合計が最小の 1 本を選んでいる。
**同じ行列の平均を取れば、それがばらつきである。推論は 1 回も増えない。**

```python
# policy_server.py の pick_medoid
flat = chunks[:, :, :horizon, _POSE_DIMS].reshape(count, -1)
pairwise = torch.cdist(flat, flat)
distances = pairwise.sum(dim=1)                              # medoid 用（元からある）
self._last_disagreement = float(pairwise.sum() / (count * (count - 1)))  # 足した 1 行
return chunks[int(distances.argmin())]
```

| 決め事 | 中身 | なぜ |
|---|---|---|
| 測る次元 | 姿勢 6 次元だけ（`_POSE_DIMS`） | グリッパは ±1 に振れるので、含めるとそこだけで距離が決まる |
| 測る窓 | **起動時の歩数に固定**（16） | 歩数を切り替えても窓が動くと、ばらつきの目盛りがエピソードの途中で変わる |
| 割る数 | `count * (count - 1)` | K を変えても目盛りが揃う |

## 4. しきい値は測らずに、エピソードの中で目盛りを作る

**記事が報告している 0.669 / 1.570 は持ち込めない。** あちらは別のモデルで、
行動の単位も距離の測り方も違う。そのまま入れると、切り替えが一度も起きないか、
常に縮む側に張り付くかのどちらかになる。

**代わりに「このエピソードでこれまでに見たばらつきの中央値より大きいか」で判定する。**
モデルの出力の単位が何であっても自動的に合う。

| 環境変数 | 既定（コード） | 14.0.0 の zip | 何を決めるか |
|---|---|---|---|
| `PARC_ADAPTIVE_CADENCE` | `0`（切） | **`1`（入り）** | 切り替えるかどうか |
| `PARC_ADAPTIVE_CADENCE_HIGH` | `8` | `8` | 迷ったときの歩数 |
| `PARC_ADAPTIVE_MIN_SAMPLES` | `3` | `3` | 目盛りが溜まるまで切り替えない回数 |
| `PARC_SAMPLES` | `1` | **`3`** | 何本引くか。**2 以上でなければ起動時に落とす** |

**採点環境は環境変数を渡さないので、zip の中では既定値そのものを書き換えている。**

**中央値と比べる作りなので、引き直しの約半分が切り替わる。** 偽のモデルで 300 コマ ×
3 エピソードを回すと、引き直しは **16 歩固定の 1.30 倍**（57 回 → 74 回）になった。

## 5. 秒数 —— 採点ログ 14 本から出した式で見積もる

**`合計時間` は採点ログに返る。** 14 本の `合計時間` と `/act` の回数から、
2 つの係数に分けられる。

| 係数 | 値 | 何の時間か |
|---|---|---|
| `/act` 1 回あたり | **0.083 秒** | シム・描画・通信 |
| 引き直し 1 回あたり（K=1・`infer` 10） | **0.447 秒** | π0.5 の推論 1 本 |

出し方は π0.5 の 2 本（3.8.0：`/act` 1,428・183.1 秒、4.2.0：`/act` 991・110.4 秒）の
連立である。**当てはめの裏づけは SmolVLA の 4 本**で、`n_action_steps` 1／2／5 と
`samples=3` の 4 点が同じ形の式に 0.5% 以内で乗る（3.4.0 は予測 1,531 秒に対して実測
1,523.0 秒）。

**Track3（`/act` 2,400）の見積もり。**

| 出すもの | 引き直し | **予想 `合計時間`** | 上限 3,600 秒に対して |
|---|---|---|---|
| いま（K=1・16 歩固定） | 150 | 約 267 秒 | 13 倍 |
| K=3・16 歩固定（切り替え無し） | 150 | **約 401 秒** | 9 倍 |
| **K=3・切り替え入り**（1.30 倍） | 195 | **約 461 秒** | **8 倍** |
| K=3・全部 8 歩（最悪） | 300 | 約 602 秒 | 6 倍 |

**1 回の推論の秒数は切り替えても変わらない。** K=3 で約 1.34 秒（0.447 × 3）で、
**10 秒制限に 7.5 倍の余裕**である。切り替えは「引き直す頻度」を変えるだけで、
1 回の重さを変えない。

**先に決めた読み方。** 返ってきた `合計時間` が約 400 秒なら切り替えが一度も起きて
いない、約 460〜500 秒なら起きている、約 270 秒なら `samples=3` が効いていない
（既定値の書き換え漏れ）。

### 直した見積もりの誤り

**2026-09-07 の午前に「K=3 は 7.2 秒で 10 秒に対して余裕 1.4 倍」と書いたのは誤りだった。**
下敷きにした「π0.5 の 1 推論 1.5〜2.4 秒」という実測は、**もともと `samples=3` で
測った値**である（測定条件が `num_inference_steps=20 samples=3`）。
3 本引いた値にさらに 3 を掛けていた。**同じ誤りから「②と③は同時に入れられない
（推論が 9 回になる）」も出ていたが、これも誤りである**——4 節のとおり、
ばらつきは medoid の距離行列から取るので、K 本の引きは 1 組で足りる。

## 6. 落ちたときの受け皿

| どこで落ちるか | 受け皿 | 起きること |
|---|---|---|
| 切り替えの計算の中 | **ある** | `_fall_back_from_adaptive` が歩数を既定へ戻し、以降は切り替えをやめる。**medoid は生き続ける。**`[parc] adaptive cadence 失敗のため…` を 1 行出す |
| `PARC_SAMPLES` が 1 のまま切り替えを立てた | **起動時に落とす** | 1 本ではばらつきが測れない。**黙って効かないより落ちる方を選んだ** |

**エピソードごとに目盛りを捨てる。** 課題が違えばばらつきの大きさも違うので、
前のエピソードの中央値を持ち越すと判定がずれる。

## 7. 踏んだ罠 —— 待ち行列の `maxlen`（2026-09-07）

**同梱 LeRobot の `reset()` は、待ち行列を「その時点の」`config.n_action_steps` で
作り直す。**

```python
# work/artifacts/vendor/lerobot/policies/pi05/modeling_pi05.py:1128-1129
def reset(self):
    self._action_queue = deque(maxlen=self.config.n_action_steps)
```

**前のエピソードの最後が 8 歩で終わっていると `maxlen=8` の行列ができる。**
次のエピソードで 16 歩ぶん入れると、`deque` は**先頭 8 歩を黙って捨てる**——
腕が chunk の 9 コマ目から動き出す。例外も警告も出ない。

```
maxlen=8  に 16 歩入れる → 実行される歩 = [8, 9, 10, 11, 12, 13, 14, 15]
maxlen=16 に 16 歩入れる → 実行される歩 = [0, 1, 2, ..., 15]
```

**直し方は順番だけである。** `MyPolicy.reset()` の中で、
**歩数を既定へ戻すのを `self._policy.reset()` より先に置く。**

> **次に立てる問い。** 消費する量を実行中に変える仕掛けを足すときは、
> **その量から `maxlen` や配列の大きさを決めている場所が下流に無いか**を先に見る。

### K=3 だけを先に測って分かったこと（2026-09-08）

**失点はまるごと「なめらかさ」側だった。**Track1 は目標に届いた本数が 7/8 のまま
1 本も変わらず、**届いた 1 本あたりの質が 0.5429 → 0.4686 に落ちた**だけである。
Track2 は逆に届いた本数が 5 → 7 に増えたが、質が 0.4176 → 0.2949 に沈んで
点はほぼ横ばいだった。**K=3 は成功・衝突の関門ではなく、質の側を動かす。**

> **切り替えを足すときの向かい風。** 歩数を 16 → 8 にすると **chunk の継ぎ目が倍に増える。**
> 8/14 の実測では `n_action_steps` を 16 → 10 にするだけでジャークが 3.699 → 4.300
> （+16%）と悪化している（[../plan/19_smoothness_beyond_postprocessing.md](../plan/19_smoothness_beyond_postprocessing.md)）。
> **K=3 で既に沈んでいるのと同じ「なめらかさ」を、切り替えがさらに押し下げる筋がある。**
> 逆に期待できるのは Track2 側で、**K=3 だけで届いた本数が +2 になった**ので、
> 迷った場面で引き直しを早めれば、その本数がさらに増える余地はある。

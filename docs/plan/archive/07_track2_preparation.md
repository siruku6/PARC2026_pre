## 1. 問題の理解

### 1.1 Track2 の「位置・視点・ノイズ」とは何か

予選 PDF（p8）の図は Track1〜3 を次のように書く。

| | 同一性 | 摂動 |
|---|---|---|
| Track1（予選で実施） | 同一タスク・同一ドメイン | **テクスチャ等の摂動** |
| **Track2** | **同一タスク・未知ドメイン** | **位置・視点・ノイズ変更** |
| Track3 | 既知タスク組み合わせ・未知ドメイン | 言語指示で新規組み合わせ |

評価環境は予選と同じ **LIBERO-plus**（README で確認済み）であり、その原典は
「7 つの摂動軸を持つベンチマーク」として設計されている（`README.md` の
「7 Perturbation Dimensions」）。**Track1 は運営 Q&A No.21 によりこの 7 軸のうち
Background Textures・Light Conditions（推測を含む）に限定されると確認済み**
（[05_perturbation_categories.md](../../reference/05_perturbation_categories.md)）。

**Track2 の文言「位置・視点・ノイズ」は、残る 4 軸に字面のまま対応する。**
（この対応づけ・各カテゴリの中身・自チームの実測は
[20_track2_perturbation_categories.md](../../reference/20_track2_perturbation_categories.md)
に集約した。以下はその要約。）

| Track2 の文言 | 対応する LIBERO-plus のカテゴリ | 母集団（全 10,030 件中） |
|---|---|---|
| 視点 | **Camera Viewpoints** | 1,599 件（15.9%） |
| ロボットの位置 | **Robot Initial States** | 1,550 件（15.5%） |
| 物体の位置 | **Objects Layout** | 1,525 件（15.2%） |
| ノイズ | **Sensor Noise** | 1,601 件（16.0%） |
| **4 カテゴリ合計** | | **6,275 件（62.6%）** |

（`task_classification.json` を実際に数えた。難易度 1〜5 の分布は 972/1,454/1,328/1,153/1,368
で偏りは大きくない。suite 別も libero_goal 1,621・libero_object 1,619・libero_10 1,573・
libero_spatial 1,462 でほぼ均等。）

**この対応は「Q&A で運営が明言した」ものではない。** 予選 PDF の図の文言と LIBERO-plus の
カテゴリ名を字面で対応付けた**強い推測**である。Track1 の教訓（運営はカテゴリ名を 1 つも
挙げていなかった）を踏まえ、**本選開始後に配布される Track2 の説明・Q&A を最優先で確認し、
この対応が正しいかを裏取りすること**を最初のタスクにする。

### 1.2 具体的にどのようなデータが入力として与えられると考えられるか

配布キットの `submission_template/policy_server.py` のインターフェース（`/reset` に
`instruction`・`/act` に画像＋関節角＋EE位置の観測）は Track2 でも変わらないと考えられる
（予選 PDF はモデル・学習要件を Track 共通の枠で説明している）。**変わるのは環境側が
どの `.bddl`／どのカメラ設定／どの初期状態で評価するかであり、ポリシー側から見える
インターフェースは同一である。**

実装コードを読んで確認した、各カテゴリの実体は次のとおりである（すべて
`LIBERO-plus/libero/libero/envs/` 配下の実装を直接読んだ一次情報）。

| カテゴリ | 実体 | 具体的な数値（実装コードで確認） |
|---|---|---|
| **Camera Viewpoints** | `agentview` カメラをシーン中心を軸に回転・ズーム | シーン中心周りに **水平回転（方位角）・垂直回転（仰角）** をかけ、**距離（`scale_factor`）** を変え、さらに**カメラ自体の向き**を `end_point_rot`／`end_point_vertical` で独立に回す。実装上のサンプル値は方位角 `[30,60,...,330]`、仰角 `[15,345]`、`scale_factor=1.25` 等（`libero_tabletop_manipulation.py:305-376` のコメントに残る掃引の例） |
| **Robot Initial States** | アーム初期関節角 `qpos` に固定長の摂動を加える | 基準姿勢 `[0, -0.161, 0, -2.445, 0, 2.227, π/4]` に、**ランダムな単位ベクトル方向へ大きさ 0.1〜0.5（5 段階・各 100 個体）を加える**（`robots/new_init.py`。単位はコード上ラジアン相当と読める） |
| **Objects Layout** | 邪魔物体の追加（`_add_N`）／対象物体の位置ずらし（`_levelN_sampleM`） | 邪魔物体は既定の物体プールから追加。対象物体のずらし幅は難易度レベル 1〜5 に対応（コードからは正確な cm 数値まで追えていない） |
| **Sensor Noise** | `agentview_image` に事後的な画像劣化（ImageNet-C 系）をかける | **5 種×severity 1〜10 の合成**：`motion_blur`(1-10)・`gaussian_blur`(11-20)・`zoom_blur`(21-30)・`fog`(31-40)・`glass_blur`(41-50)。関数はほぼ Hendrycks & Dietterich の ImageNet-C 実装そのもの（`env_wrapper.py:26-174`） |

**カメラ視点とセンサーノイズは「物理を変えない」。** 位置・向き・画質の変更は
mujoco のレンダリング設定または画像後処理であり、**同じロールアウトを違う設定で
作り直しても行動ラベル（action）は変わらない。** 一方 **ロボット初期姿勢と物体配置は
物理そのものを変える**ため、既存の行動列をそのまま再生しても正しい観測・行動対にはならない
（1.3 節・2.1 節で対策の違いとして戻ってくる）。

### 1.3 関連研究

#### 1.3.1 LIBERO-plus 論文本体（arXiv:2510.13626）の知見

エージェントに委任し、arXiv の HTML 版を複数回取得して事実だけを抜き出した
（PDF はテキスト層が壊れており不採用。数値の一部は再取得でも食い違いが残るため、
**以下は「確認できた」ものと「食い違いが残る」ものを分けて書く**）。

**確認できた・複数回の取得で一致した数値**

| モデル | 素の成功率 | Camera | Robot | Noise | Layout |
|---|---|---|---|---|---|
| OpenVLA | 76.5% | **1.1%** | **4.1%** | 19.3% | 31.6% |
| OpenVLA-OFT | 97.1% | **59.7%** | **37.2%** | 76.7% | 77.1% |
| π0 | 94.2% | **15.8%** | **6.6%** | 79.4% | 70.4% |

**Camera・Robot の 2 カテゴリだけが、他の摂動（Language・Light・Background・Noise・Layout）
より一段深く成功率を落とす。** OpenVLA-OFT でも Camera −37.4pt・Robot −59.9pt に対し、
他カテゴリは −4.7〜−20.4pt に収まる。論文の abstract も「95% から 30% 未満まで落ちる」と
Camera・Robot を名指ししており、README の leaderboard（他文書で確認済み）とも整合する。

**mix-SFT（LIBERO-plus データを混ぜた追加学習）の効果**（OpenVLA-OFT+、複数回の取得で
Camera 92.8%・Robot 30.3%・総合 79.5% は一致。素の Camera 値は 55.6%/57.9% で取得ごとに
食い違いが残る）:

| | 追加学習前 | 追加学習後 | 差分 |
|---|---|---|---|
| Camera | 約 56〜58% | **92.8%** | **+35〜37pt** |
| Robot | 21.7% | **30.3%** | **+8.6pt（絶対値は依然低い）** |
| Noise | 78.6% | 89.3% | +10.7pt |
| Layout | 68.7% | 77.6% | +8.9pt |

**Camera は「対象ドメインのデータを混ぜて追加学習する」だけで大きく改善するが、
Robot（初期姿勢）は同じ処方箋では伸びが小さい。** これは 1.2 節で見た「Camera は
作り直しで済むが、Robot は物理からやり直しになる」という構造上の違いと符合する。

**その他の知見**（1 回の取得のみ・食い違いなし）:
- **Language Ignorance**: 指示文を空白にしても Object suite の成功率がほぼ変わらない、
  対象物体名を別物に書き換えても元の物体への動作を続ける、という 2 つの実験で
  「モデルは言語をほとんど使わず、視覚→行動の固定写像で動いている」と結論している。
- **手首カメラの有無が Camera 摂動への耐性を左右する**（原文は wrist camera を持つ
  モデルほど viewpoint 変化に強いと明記。OpenVLA-OFT と wrist camera を外した ablation
  版で Camera スコアに大差、59.7% 対 16.8%）。
- **Negative Compositional Generalization**: 複合摂動（例 Layout+Camera・Robot+Noise）の
  成功率は、単独効果の積より低い組がある（統計的有意性を χ² 検定で確認したとの記述）。

**確認できなかった・食い違いが残ったもの**（数値を使うときは要再確認）:
Camera の難易度 3 段階の厳密な角度境界、Sensor Noise の severity 1〜10 と論文側の
記法の対応、Objects Layout の cm 単位の範囲、SRPO の Robot 列の値（取得ごとに
54.2/43.6 と 81.8/73.6 で矛盾）。

#### 1.3.2 LIBERO-plus を使った後続研究 3 件

README に載る 3 件を同エージェントが調査した（要旨のみ、数値は上記と同様に
1〜2 回の取得なので参考値）。

| 論文 | LIBERO-plus 平均 | Track2 に関係しそうな要素 |
|---|---|---|
| **AVA-VLA**（arXiv:2511.18960） | 74.7%（Camera 69.4・Robot 34.9） | 行動生成を POMDP として再構成し、指令と実行履歴で現在の視覚トークンを動的に再重み付け（"Active Visual Attention"） |
| **MergeVLA**（arXiv:2511.18810） | 72.4%（設定により 62.5%） | 複数タスク特化 LoRA の直接マージが失敗する原因（LoRA のタスク方向への発散・アクションエキスパートの層間依存）を分析し、疎活性化 LoRA で対処。Camera/Robot 特化の記述は確認できなかった |
| **SRPO**（arXiv:2511.15605） | 数値に矛盾あり（本文参照） | 訓練バッチ内の成功軌跡を自己参照し、失敗ロールアウトに進捗ベースの報酬を与える。世界モデルの潜在空間で進捗を測るため生画像への依存を減らす、という設計思想自体は Camera/Robot のような視覚依存の脆さに間接的に効く可能性がある |

**3 件とも Camera・Robot だけを狙い撃ちした専用手法ではない。** 汎用的なロバスト性向上
（注意機構・データ拡張・報酬設計）の副産物として Camera が伸びている構図で、
**Track2 専用の決定打が既に存在するわけではない**、という理解が実務上重要である。

#### 1.3.3 より広い文献（視点・ノイズ・位置のロバスト性）

別エージェントに Web 調査を委任した。**タイトル・要旨のみ確認したものと、本文まで
確認したものを分けて書く**（詳細度が違うため）。

**視点（Camera）への対策**

| 手法 | 年 | 中身 | 確認度 |
|---|---|---|---|
| **VISTA**（arXiv:2409.03685） | 2024 | 単一視点デモから novel view synthesis（新しい視点の画像を 1 枚から合成する技術）で別視点画像を合成し、**同じ行動ラベルのまま**デモを拡張。視点の未知条件で既存手法を上回る | 本文まで確認 |
| **RoboSplat**（RSS 2025・arXiv:2504.13175） | 2025 | 1 実演＋多視点画像から 3D Gaussian Splatting でシーンを再構成し、視点変更を含む 5 技法でデモを増産 | 要旨まで確認 |
| **3D Diffuser Actor**（arXiv:2402.10885）・RVT・GNFactor 等 | 2023-24 | 観測を 3D 特徴／point cloud にしてから処理し、並行移動同変性で視点に頑健にする系譜 | 要旨まで確認（原論文未直接確認のものを含む） |
| **Point Cloud Models Improve Visual Robustness**（arXiv:2404.18926） | 2024 | point cloud を明示的に使う方策は RGB-D 方策より照明・カメラ位置の変化に**著しく頑健** | 本文まで確認 |

**視点・位置（空間的摂動）についての最も具体的な数値**（本文まで確認）:
**「Grounding Sim-to-Real Generalization in Robotic Manipulation」（arXiv:2603.22876、2026）**は、
ドメインランダマイゼーションを背景・無関係物体・**カメラ姿勢（±0.01m）**・照明・
**テーブル高さ（±3cm）**の 5 要素に分解して実機評価した。

| | Clean | カメラ姿勢のみ | テーブル高さのみ | 全要素 |
|---|---|---|---|---|
| Place Cup | 5.4% | 17.5% | 24.8% | **41.0%** |
| Stack Bowls | 26.2% | 42.3% | 49.6% | **63.1%** |

**カメラ姿勢とテーブル高さという「幾何・視点の摂動」が、見た目（背景・照明）の摂動より
効果が大きかった**、と結論している。さらに**ランダム化を 1 エピソードで固定するより
1 ステップごとに再サンプリングする方が効く**（カメラ姿勢で +3〜8pt・背景で最大 +13pt）
という知見も報告されている。**これは Track2（視点・位置）が Track1（見た目）より
学習側のドメインランダマイゼーションで対処しやすい可能性を示す**、1.4 節の総論を
補強する材料である。

**ノイズ（Sensor Noise）への対策**

| 手法 | 年 | 中身 | 確認度 |
|---|---|---|---|
| **CRT**（Corruption Restoration Transformer、arXiv:2602.01158） | 2026 | **π0.5・SmolVLA が電子ノイズ・デッドピクセル等のセンサ劣化で成功率 90%→2% まで崩れる**と報告。VLA の手前に画質復元モジュールを置いてベースライン近くまで回復 | 要旨まで確認 |
| **StableVLA**（arXiv:2605.18287） | 2026 | 情報理論に基づく軽量アダプタ（1000 万パラメータ未満）を追加。**追加データ・拡張なしで平均 +30%**改善したと報告 | 要旨まで確認 |
| **RobustVLA**（arXiv:2510.00037） | 2025 | 4 モダリティ（行動・指示・環境・観測）の摂動を比較し、**行動モダリティが最も脆弱**・π0 が他より頑健と報告。行動ノイズに対するオフライン最悪ケース最適化で LIBERO +10〜13pt | 要旨まで確認 |

**我々が使っている π0.5・SmolVLA そのものがセンサ劣化に極めて脆弱である**（CRT の
90%→2%）という報告は重い。**Track1 で確認済みの「Sensor Noise も Track1 候補になりうる」
という推測**（[05_perturbation_categories.md](../../reference/05_perturbation_categories.md)）
と合わせて読むと、Noise 対策は Track1・Track2 の両方に効く可能性がある。

**位置（Robot Initial States・Objects Layout）への対策**

| 手法 | 年 | 中身 | 確認度 |
|---|---|---|---|
| **ADR**（OpenAI Dactyl） | 2019 | ランダム化の範囲を、方策の成功率を見ながら適応的に広げる／狭めるカリキュラム | 公式記事・解説で確認 |
| **MimicGen**（arXiv:2310.17596） | 2023 | 少数の人間デモから、物体中心の動作を新しい物体姿勢に合わせて変形・再接続し、**広い初期状態分布**の大量デモを合成。長期・高精度タスクでも有効 | 要旨まで確認 |
| **「データ拡張による視覚運動方策の汎化」**（arXiv:2511.09932） | 2025 | カメラ姿勢・照明・テーブル質感・テーブル高さをランダム化する自動データ生成。低コストアームへのゼロショット転移を確認 | 要旨まで確認 |

**MimicGen の手法は、2.1 節で述べた「閉ループ scripted policy」の考え方と同系統である**
（物体中心の動作を新しい配置に合わせて変形・再接続する = 「今の状態から動く」scripted policy の
一般化）。**Tier 2（Robot・Layout）のデータ増産を検討する際、MimicGen の変形・再接続の
考え方を scripted policy の書き方に取り込める可能性がある。**

**未確認・要注意な点**（エージェントの報告からそのまま引く）: AugMix・RandAugment
のような汎用画像拡張をロボット方策学習・VLA に直接適用した効果を示す一次資料は
見つかっていない。RVT・RVT-2・GNFactor・RoboTransfer・VistaBot・EquiForm・STRONG-VLA
は要旨・タイトルレベルの確認に留まる。「SAFER」という推論時アンサンブル手法は
出典を特定できなかった。

#### 1.3.4 2026-08-25 の追加調査（本選開始後）

**variant** = 元のタスク 1 つに摂動を 1 つ当てたもの（`.bddl` 1 個）。初期配置は元タスクのものを共有するので、**1 つの variant から最大 50 エピソード作れる。**

**まず 1.1 節の推測が確定した。** 本選の配布キットの `compe/t2/T2_TASKS.csv`（8 行）は
LIBERO-plus の variant で、`category` 列は **Sensor Noise 2・Camera Viewpoints 2・
Objects Layout 2・Robot Initial States 2**、`difficulty_level` は L3 が 2・L4 が 3・L5 が 3 である。
**Track2 が 4 カテゴリだという推測は当たっていた。**

**LIBERO-plus の順位表（README、2026-08-24 取得）は、手首カメラの重さを同じ表の中で示している。**

| モデル | Camera | Robot | Noise | Layout | 総合 |
|---|---|---|---|---|---|
| π0 | 13.8 | 6.0 | 79.0 | 68.9 | 53.6 |
| π0-Fast | **65.1** | 21.6 | 74.4 | 68.8 | 61.6 |
| OpenVLA-OFT | 56.4 | 31.9 | 75.8 | 74.2 | 69.6 |
| OpenVLA-OFT（**手首カメラを外した版**） | **10.4** | 38.7 | 49.9 | 69.9 | 55.8 |
| OpenVLA-OFT+（LIBERO-plus を混ぜて追加学習） | **92.8** | 30.3 | 89.3 | 77.6 | **79.6** |

**手首カメラを外すと Camera が 56.4 から 10.4 へ落ちる。** 視点が変わったときに頼れるのは
手首カメラだという読みの裏づけになる。**そこから、学習中に一定の確率で場面カメラの画像を
潰す（modality dropout）という安い手が出てくる** ── 手首カメラだけで動く経路が育つ。

**外部の手法で、数字が出ていて実装量が現実的なものは 3 つである。**

| 手法 | 中身 | 報告値 | 実装量 |
|---|---|---|---|
| **対の視点で velocity をそろえる**（arXiv 2608.06965） | 同じ MuJoCo の状態に戻して、揺らしていないカメラと揺らしたカメラの 2 枚を描き直し、**同じ流れ座標で 2 枚の velocity（行動を形にしていく流れの向き）が一致するよう罰則を掛ける。**手首カメラの流れは学習中ずっと潰す | Camera 部門 **87.2 ± 0.4%**。ただ混ぜる学習に対して **+12.5 ポイント**。無摂動は 95.0 で落ちない。対を崩すと 25.8% へ崩壊 | 中。**コードは非公開。**2.1 節の Tier 1 の上位版にあたる |
| **なめらかな曲線を学習中の罰則にする**（arXiv 2608.01265） | 行動の塊を端点の位置と速度で決まる曲線（piecewise cubic Hermite curve）として書き直し、**学習時の罰則としてだけ使う** | **π0.5 で LIBERO-plus 85.7 → 90.9。**LIBERO 95.9 → 98.7。実機 4 タスク 63.4 → 90.0 | 中。**推論のコストは増えない。**罰則の式は要旨に無いので本文を読む必要がある |
| **幾何の下地を借りる**（arXiv 2509.14117・GeoAware-VLA） | 幾何を学習済みの視覚モデルを凍結して足し、**小さな投影層だけを学習する** | LIBERO の**未知視点で平均 +35 ポイント**。RGB だけで動き、深度も校正も要らない | 中〜高。学習するのは投影層だけだが、提出物の起動時間（本番 1200 秒）への影響を測り直すことになる |

**スコアそのものを目標にする道（強化学習）も開いた。** 本選 PDF が
**「配布ローカル評価環境を使った強化学習は禁止に含まれない」**と明言した。模倣で学べるのは
「手本と同じ行動」であって「短いステップ数で終わること」ではないので、ここだけが
ステップ数を直接の目標にできる。

| 手法 | 中身 | 報告値 |
|---|---|---|
| Q-VGM（arXiv 2606.08015） | 自分のロールアウトから作った固定の記録だけで学ぶ。推論時に評価器は不要 | **π0.5 で LIBERO 79.0 → 92.5** |
| BCP（arXiv 2608.03483） | 元のモデルは凍結し、小さなヘッドだけを結果報酬で学ぶ。**報酬に効率が入っている** | LIBERO +1.7・LIBERO-PRO +6.8・実機 74 → 92% |
| SRPO（arXiv 2511.15605） | バッチ内の成功軌跡を自分で参照し、失敗に進捗の報酬を与える | **LIBERO-plus 平均 82.1**（第三者の手法で最高） |

**共通の前提はロールアウトを大量に回せることで、描画が CPU の 2 コアに載っている手元の
マシンでは成立しない。** 評価の回転を上げることが入場料になる。

**見送ると決めたもの**: ベースモデルの差し替え（提出・学習・評価の 3 経路を作り直す）、
別の視点の画像を作って学習時のカメラに合わせる系（AnyCamVLA・GS-VLA。視点合成のモデルが要る）、
世界モデルで先を想像する系（数字は大きいがモデルの構造を作り直す）、
ロールアウトを作り直して選ぶ系（採点は 1 タスク 1 回でやり直しの機会が無い）。

### 1.4 今回取り組むべき施策の方向性（総論）

1.3 節までの理解から、以下が言える。

- **Camera（視点）と Sensor Noise（画質）は「レンダリング設定・画像後処理」の問題であり、
  物理を変えずに作り直し／後処理で学習データを増やせる。** 論文の mix-SFT でも Camera は
  最も伸びが大きい（+35〜37pt）カテゴリであり、**投資対効果が最も高い。**
- **Robot Initial States（ロボット位置）と Objects Layout（物体位置）は物理そのものが
  変わるため、既存の行動列を作り直すだけでは正しいデータにならない。** 論文でも Robot は
  mix-SFT の伸びが最も小さい（+8.6pt、絶対値 30.3%）。**単純な追加学習では届きにくい
  領域であり、優先順位を上げすぎない。**
- **言語指示への依存が薄い（Language Ignorance）ことと、視点・初期姿勢への脆さは
  無関係ではない可能性がある。** 見た目のパターンマッチに近いほど、視点が変わって
  パターンが崩れると総崩れしやすい。
- **我々が使っている π0.5・SmolVLA そのものが、センサ劣化（Sensor Noise）に極めて
  脆弱だという外部報告がある**（CRT 論文、成功率 90%→2%）。Noise 対策は Track1・
  Track2 の両方に効きうる、優先度の高い項目である。
- **「幾何・視点の摂動（カメラ姿勢・位置）」は「見た目の摂動（背景・照明）」より、
  学習時のドメインランダマイゼーションでの改善効果が大きいという実機報告がある**
  （arXiv:2603.22876）。**これは Track1 で苦戦した見た目対策より、Track2 の視点・位置
  対策のほうが、ドメインランダマイゼーションという同じ武器でも効きやすい可能性を
  示す。** さらに「1 エピソード固定でなく 1 ステップごとに再サンプリングする」方が
  効くという知見は、2.1 節の Tier 1/Tier 2 のデータ増産をどう作るかに直接効いてくる。

### 2.1 データを作成する手法と、実現可能性

自チームの手元には Track1 対応で作った **scripted policy によるエピソード作成パイプライン**
が既にある（[05_scripted_demos.md](../../howto/05_scripted_demos.md)）。`solution/tools/scripted_demo/scripted_demo.py`
を読むと、この scripted policy は各ステップで `obs["<object>_pos"]` などの**実測の物体位置・EE位置から
目標への差分**を計算して行動を出している（`follow()` の
`delta = targets[index] - self.eef_position`）。**つまり新しい観測を見ながらそのつど
動き先を決め直す（閉ループ）scripted policy であり、事前に決めた絶対時刻・絶対軌道をなぞるだけの、
新しい観測を見ずに動き続ける（オープンループ）scripted policy ではない。**

これが決定的に重要である。**閉ループの scripted policy は「今どこにいるか」から動くので、
ロボットの初期姿勢や物体の位置が変わっても、同じ scripted policy をそのまま再実行すれば
（多くの場合）タスクを解ける新しい実演になる。** 一方、既に録れた行動列を
そのまま別条件で再生する（オープンループ再生）のは、**カメラ・ノイズのような
「観測だけが変わる」条件に対してのみ有効**で、初期姿勢や物体配置のような
「物理が変わる」条件には使えない。

この違いから、データ作成の手段を 2 層に分ける。

| 層 | 対象カテゴリ | 手段 | コスト | 実現可能性 |
|---|---|---|---|---|
| **Tier 1** | Camera Viewpoints・Sensor Noise | 既存の実演（成功ロールアウト）を **同じ物理・別のカメラ設定／画像後処理で作り直す**、または既存動画に **後処理でノイズを合成**する | **物理シミュレーションは 1 回分のみ。** カメラ設定の変更・画像劣化は render／後処理のコストだけ | **高い。** `scripted_demo.py` の `--variant` 相当の仕組みを流用でき、CPU（osmesa）だけで回る。ノイズは動画に後処理で足すだけなら新規の物理シミュレーションすら不要 |
| **Tier 2** | Robot Initial States・Objects Layout | **閉ループ scripted policy を、異なる初期関節角／異なる物体配置から再実行**して新しい実演を作る | scripted policy のあるタスクごとに、初期姿勢・配置の数だけ物理シミュレーションを回す（CPU・GPU 不要） | **中程度。** scripted policy が「今の状態から動く」設計であることが前提。**scripted policy があるのは現時点で `KITCHEN_SCENE8_put_both_moka_pots_on_the_stove` の 1 タスクのみ**なので、対象タスクを増やすには scripted policy を書く作業が別途要る |

#### 2.1.1 Tier 0（新設）: ノイズを乗せて「ずれから戻る」データを作る

**Tier 1/Tier 2 は「どんな条件でエピソードを作るか」を変える話であり、「何を教えるか」は成功軌道の
ままである。** これとは別に、**「ずれた状態から立て直す行動」を教えるデータが必要である**
（[08](../08_training_data_creation_cautions.md) 1.1 節・3.1 節）。これを Tier 0 と呼ぶ。

**作り方**: scripted policy が出力する action に、実行直前にノイズを加える。scripted policy は
**実測の位置から目標への差分を計算する閉ループ制御**なので、ノイズで目標からずれても、
**次のステップで scripted policy 自身がそのずれを埋めようとする行動を出す。** 結果として、
**「ずれた観測」と「そこから戻る行動」の対が、scripted policy を 1 行も書き換えずに手に入る**
（DART の発想。[08](../08_training_data_creation_cautions.md) 3.2 節）。

| | コスト | 実現可能性 |
|---|---|---|
| **Tier 0** | 物理シミュレーションを条件の数だけ回す（Tier 2 と同等）。**scripted policy の改修はノイズを足す 1 箇所だけ** | **高い。** scripted policy が閉ループであることが前提で、これは確認済み |

**必ず一緒に決めること（文献が明示している注意点）**:

- **ノイズの大きさは、多いほど良いわけではない。** DART の実機実験では最適値 α=3 で
  成功率 79%、過大な α=6 では 72% に低下している。**数段階振って比較する工程を、
  最初から作業に含める。**
- **「ずれ始めた区間」を正例として学習させるかを決める。** SIRIUS は、人が介入する直前の
  15 ステップ（方策が既におかしくなっている区間）を**学習から完全に除外**している
  （[08](../08_training_data_creation_cautions.md) 3.3 節）。**Tier 0 でも、ノイズで大きく
  ずれた直後の区間をそのまま模範として学習させると、「ずれる動き」まで覚えさせる
  リスクがある。** 少なくとも、ノイズを加えたステップ自身を教師信号にするのか、
  それとも「ノイズ後の観測 → scripted policy が出した復帰行動」の対だけを教師信号にするのかを、
  実装時に明確に区別する。**後者が意図した設計である。**
- **同じ失敗状態に対して複数の異なる復帰のやり方を混ぜない。** 混ぜると平均されて
  どちらでもない誤った軌道を学ぶ（[08](../08_training_data_creation_cautions.md) 3.4 節）。
  scripted policy は決まった手順で動くので自然にこの条件を満たすが、**将来複数の scripted policy を併用する
  場合は注意する。**

**Tier 1 のもう一段安い代替**として、画像空間の 2D 変換でカメラ視点の変化を
**近似**する手がある。

> **【2026-08-25 訂正】ここに「2D 変換では 3 次元的な視点回転を再現できない
> （2D 変換は光軸沿いの並進・回転しか表現できない）」と書いていたのは誤りだった。**
> それは平行投影の話である。実際のカメラは中心投影なので、**テーブル面という 1 枚の
> 平面に限れば、平面を別の視点から見た形に写す変換（homography）でカメラの回転と
> 厳密に一致する。** 台形にゆがめる `RandomPerspective` がそれで、切り抜きやズームより
> はるかに近い近似である。**壊れるのは高さのある物体の見え方の分だけである。**

**しかも必要な変換は既に手元にある。** 学習設定の `image_transforms.tfs` の `type` には
**torchvision の v2 にあるクラス名をそのまま書ける**（`lerobot/transforms/transforms.py` の
実装で確認）。学習コンテナの torchvision 0.26.0 に `RandomPerspective`・`GaussianBlur`・
`GaussianNoise`・`JPEG`・`RandomResizedCrop`・`RandomRotation` が入っていることを確認した。
**コードを 1 行も書かずに、設定ファイルへ項目を足すだけで済む。**

**ただし Sensor Noise に合わせる先を間違えないこと。** LIBERO-plus の Sensor Noise は
`motion_blur`・`gaussian_blur`・`zoom_blur`・`fog`・`glass_blur` の 5 種（1.2 節）であって、
**画素ごとの加算ノイズではない。** したがって近いのは `GaussianBlur` で、
`GaussianNoise` は的が外れている。

**カメラごとに掛かるかは別に確かめること。** lerobot は画像のキーごとに変換を呼ぶ
（`streaming_dataset.py` がカメラごとに `image_transforms` を呼んでいる）が、
**設定でカメラを選ぶ仕組みは無い。** 手首カメラは評価で視点をずらされないので、
**手首カメラまで台形にゆがめると、掴む直前の細かい位置合わせの手がかりを壊す恐れがある。**
場面カメラだけに掛けたい場合は小さな改修が要る。

**確認が必要な前提**: 学習データ（`lerobot/libero_plus`、14,347 本）の各エピソードが
「どの初期状態（`pruned_init` の何番目）で作られたか」の対応が、以前の調査
（`02_appearance_and_data.md`（削除済み））で**未確認のまま**残っている。
Tier 1 を「既存の学習データを別カメラ設定で作り直す」に使う場合、この対応が
分からないと作り直しの初期状態を再現できない。**着手前に確認する。**

**Tier 0/1/2 のどれでも先にやること（2026-08-21 追記）**: **タスクを増量する前に、
少数サンプルで成功判定・接触の安定性を確認し、不安定なタスクは対象から外すか、
原因を切り分けてから増量する。** Qiita 記事は条件を変えたら `push` の接触方向と
`drawer-open` の collision が安定せず、この 2 タスクを追加データの対象から明示的に
外している（[08](../08_training_data_creation_cautions.md) 1.4 節）。**「成功率が低いタスクほど
多くデータを作る」を機械的にやると、シミュレータ側の不安定さまで学習データに焼き込む。**
また、失敗した生成試行を「成功のみ採用」で捨てる操作自体にもバイアスが乗りうる
（MimicGen が自ら認めている限界。[08](../08_training_data_creation_cautions.md) 3.6 節）ので、
**除外した試行とその理由を記録に残す。**

### 2.2 どのような学習データ・評価データを用意すべきか

**評価データ（ローカルの Track2 疑似検証スイート）**

**運営配布の Track2 用検証キットはまだ無い**（`pipeline/`・`compe/` に track2 の
仕組みは無いことを確認済み）。しかし **Track1 用に作った `solution/tools/suite/make_task_suite.py`
は、摂動カテゴリを引数で選べる汎用の道具である**ことをコードで確認した
（`--categories` 引数。既定は Track1 の 2 カテゴリだが、上書きできる）。

実際に動かして確認した。

```bash
python3 solution/tools/suite/make_task_suite.py \
    --instruction "put both moka pots on the stove" \
    --categories "Camera Viewpoints" "Robot Initial States" "Sensor Noise" "Objects Layout" \
    --count 8 --output compe/val/TRACK2_PROBE_MOKA.csv
```

→ 148 件の候補から 8 件（Camera 3・Layout 2・Robot 1・Noise 2）を等間隔に選んで
CSV を作れることを確認した（`--dry-run` で実行・GPU 不要）。**運営の実際に採点で使われるタスクを
知る前でも、LIBERO-plus 原典の分類表さえあれば「Track2 らしい」ローカル検証セットは
今すぐ作れる。** これを scripted policy のあるタスク・既存 36 件評価タスクの一部に対して作り、
**現行の提出モデルが Camera / Robot / Noise / Layout のどこで一番崩れるかを先に
測る**のが、対策より先にやるべき最初の一歩である（3 節）。

**評価スイートの設計要件（2026-08-21 追記）**

上のコマンドで CSV を作るだけでは足りない。**次の 2 点を設計に入れる**
（[08](../08_training_data_creation_cautions.md) 1.3 節・2.8 節・4.3 節）。

1. **成績をカテゴリ平均だけで出さず、タスク×カテゴリの粒度で記録する。** カテゴリ平均だけを
   見ると、少数派のタスクの崩れが埋もれる。Qiita 記事も「全体平均だけでは Background、
   Light、multi-object の悪化が埋もれる」と実データで示している。
2. **学習で見せた条件と、検証で使う条件を明示的に分離する。** Tier 0/1/2 で増産した
   学習データに使ったカメラ角度・初期姿勢・物体配置の集合と、この検証スイートで使う集合を
   分けておく。**分けないと、Track2 が測ろうとしている「未知ドメインへの汎化」ではなく
   「見たことのある条件を再現できたか」を測っているだけになり、成績を過大に見積もる**
   （講義第6回 p59 のデータ分割とリークの議論）。この分離は
   **`make_task_suite.py` に CSV を作らせる時点で、学習用に使う variant 番号と
   検証用に使う variant 番号を排他にしておく**ことで実現できる。

**学習データ**

- **Tier 0（ノイズ注入による復帰データ）は、scripted policy を持つタスクに限られるが、
  カテゴリを問わず効く**（2.1.1 節）。**最初に試すのはここである**（3 節）。
- Tier 1（Camera・Noise）で増産したデータは、既存の `lerobot/libero_plus` に
  `merge`（[05_scripted_demos.md](../../howto/05_scripted_demos.md) 8 節と同じ仕組み）で
  混ぜ込む。**ただし全部混ぜて増量するのではなく、混合比（既存データ：Tier 0：Tier 1：
  Tier 2）を検証成績を見ながら調整する余地を残す。** 異種データを単純にプールすると
  性能が下がる場合がある（負の転移。講義第6回 p47・p80）。
- Tier 2（Robot・Layout）で増産したデータは、scripted policy を持つタスクに限られる。
  **全 36〜40 タスクに scripted policy を用意するのは今回のスコープでは重い**ので、
  「学習データを増やす」より「評価で弱点を特定し、優先度の高いタスクだけ scripted policy を書く」
  という順番が現実的である。
- **どのデータ区分でも、条件（カテゴリ・視点・初期姿勢・ノイズ量）をメタデータとして
  各エピソードに残す。** 残さないと、上の混合比の調整も、条件別の検証も、後からできない
  （講義第6回 p39・p55 のログ規律）。Qiita 記事が 42 列のメタデータを持たせていたのは
  これを可能にするためである。

### 2.4 推論時に行いうる工夫

Track2 の「位置・視点・ノイズ」は **観測側の摂動**であり、講義第7回で扱われた
action chunk の繋ぎ目・非同期実行・RTC のような**時間軸の問題とは別種**である。
そのため講義第7回の推論時工夫（RTC・VLASH・A2C2）は直接の対策にはならないが、
**考え方として転用できる部分がある。**

| 工夫 | 転用元 | 内容 | 実現可能性 |
|---|---|---|---|
| **複数の仮想視点で推論しアンサンブルする** | （一般的な test-time augmentation の発想） | 1 枚の観測画像に対し、想定される視点摂動の逆変換に近い 2D 変換を複数かけて推論し、行動を平均・多数決する | 中。3D 回転の逆変換は近似に留まるが、実装コストは低い |
| **観測の前処理段で画質補正（デブラー・デノイズ）をかける** | Sensor Noise 対策の一般形 | 推論直前に軽量なデノイズ・デブラーを通す | 低〜中。ただし学習時の見た目と前処理後の見た目がずれると逆効果になりうるので、**学習側にも同じ前処理を入れて整合させる必要がある**（講義第7回「前処理が学習時と推論時で一致しているか」） |
| **A2C2 的な軽量残差ヘッドで観測ズレを補正** | 講義第7回 S16 | 最新観測＋実行中の行動を入力に高頻度で行動を補正するヘッドを追加 | 本来は obs timing gap 対策だが、**視点・ノイズで生じる「観測は変わったが行動が追従できていない」ずれにも同型の補正が効く可能性**はある。ただし今回のスコープでは大掛かり |

**結論として、Track2 対策の主戦場は推論時ではなく、2.1〜2.3 節のデータ・学習側である。**
推論時にできることは限定的で、投資対効果は低い。

**Web 調査で見つかった推論時ロバスト化手法**（VLS・TT-VLA・RL²-VLA・Guided Action Flow
など、2026 年の比較的新しい研究群）は、いずれも**学習済み方策の推論過程を誘導・適応させる**
という方向性だが、**要旨レベルの確認に留まり、単一 GPU での推論コスト・Track2 の
評価プロトコル（推論中に複数視点を露出できるか等）との整合が未確認**である。
「SAFER」という複数視点統合の手法名も検索結果に出たが出典を特定できなかった。
**今回のスコープでは採用を見送り、データ・学習側の対策を優先する。**

### 3.1 完了条件に使う指標（2026-08-22 追記）

**上の表の「終わったと言える条件」は、どれも成功率の表を求めている。これは足りない。**

[../knowledge/07_local_eval_cannot_rank.md](../../knowledge/07_local_eval_cannot_rank.md) が
決定的な 2 例で確立したのは、**手元の成功率は本番の順位を付けられない**ことである。

| | 手元 36 件 | 本番 |
|---|---|---|
| 3.10.0（blend4） | 25 → **28**（+3） | 0.264 → **0.169** |
| 4.2.0（全パラメータ学習） | 25 → **28**（+3） | 0.264 → **0.485** |

**手元の +3 件はまったく同じ数字で、本番は正反対に動いた。** 本番と繋がっている量は
**ステップ数**、とくに「基準で完走していた件だけのステップ数」である
（[../knowledge/06_step_count_drives_score.md](../../knowledge/06_step_count_drives_score.md)、
r = −0.868）。

**したがって、上の表のどの項目でも、比較の表は次の 3 列で作る。**

| 列 | 何に使うか | 出し方 |
|---|---|---|
| 成功率（カテゴリ × タスク） | **壊れていないことの確認にだけ使う。採否の判断には使わない** | 従来どおり |
| **基準で完走していた件だけのステップ数** | **採否の判断に使う唯一の量** | `solution/tools/analysis/compare_steps.py`（`_MAX_STEPS = 300` と当該指標を実装済み） |
| **300 ステップの打ち切りに達した件の割合**（カテゴリ別） | ステップ数が足りなくなっていないかの見張り | 同上 |

**打ち切りに達した件を全体の合計に混ぜてはいけない。** 救われると大きく減るので、
合計が相殺されて読めなくなる（knowledge/06 の「打ち消し合い」の節）。

**Tier 0 はこの 3 列がとくに重要である。** ずれから戻る行動を教えると、エピソードは
定義上必ず長くなる。戻れなければ失敗（0 点）、戻れれば成功だが遅い、そして 300 を
越えたらその成功も消える。**つまり Tier 0 の効果と副作用は、両方ともステップ数に現れる。**
成功率だけの表では副作用が見えず、予選の blend4 とまったく同じ形になる。

**探査 40 行の表からも、カテゴリ別の打ち切り率を必ず読む。** 手元 36 件には打ち切りが
6 件（17%）あり、本番 Track1 の 4 タスクには 0 件だった。Track2 は摂動でタスクが
難しくなるので、本番側に打ち切りが出る可能性がある。もし出るなら、
**「blend と RTC の軸は閉じた」の根拠は方法の性質ではなく Track1 の評価セットの性質**
だったことになる（knowledge/06 に注記を足した）。**今すぐ開け直す必要はないが、
打ち切り率が高ければ本戦期間中の再検討材料になる。**

**全項目に共通する原則（2026-08-21 追記、[08](../08_training_data_creation_cautions.md) 4.2・4.5 節）**

- **どのデータ生成でも、増量の前に少数サンプルで成功判定・接触の安定性を確認する。**
  不安定なタスクは対象から外すか、原因を切り分けてから増やす。**除外した試行と理由を残す。**
- **「何本作ったか」を成果として報告しない。** 判断は必ず、**追加学習前後で条件を揃えた
  比較評価**で行う（講義第6回 p48「人が見た品質 ≠ 方策性能への寄与」）。
- **チェックポイントは training loss ではなく、条件別・タスク別の検証成績で選ぶ。**
  Qiita 記事の実例では、training loss が下がり続ける一方で検証指標は
  step 800・1,400・1,800 付近で一時的に悪化していた。
- **生成データの前処理（回転・crop・resize・カメラの順序）が `policy_server.py` の
  前処理と一致しているかを確認する工程を、パイプラインに組み込む。** Qiita 記事は
  ここが食い違って把持点がずれるバグを踏んでいる。
- **生成した action 列を別プロセスで同じシミュレータに流し込み、同じ結果になるかを
  確認する**（実機の `lerobot-replay` に相当するサニティチェック。講義第6回 p60）。
  単位・座標系・関節順序・絶対／相対の取り違えは、学習では隠れてここで露見する。

**この優先順位は「予選 PDF の図の文言と LIBERO-plus のカテゴリ名を対応付けた推測」の上に
立っている。** 4 節の確認が取れるまでは、1 の疑似検証スイートを使った実測を
判断の主軸に置き、推測だけで大きな投資をしないこと。**ただし 2 番目の Tier 0 は、
Track2 の実際に採点で使われるタスクがどの 4 カテゴリであっても（あるいは推測が外れていても）「ずれから戻れない」
という弱点に共通に効くため、推測の当たり外れに依存しない。** そのため優先順位を上げている。

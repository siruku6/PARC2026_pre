## 2. 順位の形 —— 以下すべての根拠

**9/2 の夜に順位が分かった。これが 1 分でいちばん多くを変えた。**
出典はリーダーボードの画面 3 枚（アカウント名 `sirukufarios`）。

| トラック | 順位 | 出ている点 | すぐ上と下 |
|---|---|---|---|
| Track1 | 36 位 | 0.47768 | 35 位 0.4793 / 37 位 0.47681 |
| Track2 | 91 位 | 0.19151 | 90 位 0.19574 / 92 位 0.19055 |
| **Track3** | **11 位以下**（0 点の同着） | 0 | **10 位が 0.00698。11 位から下は全員 0** |

**本選 1 の関門は「200 人 → 100 人」の絞り込みである**（本選資料 v1.1 p.8）。
**勝つ必要はなく、上半分に入ればよい。**

**Track1 と Track2 では、点を絞り出しても順位はほとんど動かない。**
Track1 は 26 位から 39 位までが **0.025 の幅**に入っている。仮に 0.02 上げても
十数人を抜くだけである。

**Track3 は形がまったく違う。**

| 順位 | 点 | 1 本ぶんの質に直すと |
|---|---|---|
| 1 位 | 0.11865 | 1 本を質 0.95 で届かせた程度 |
| 2 位 | 0.06657 | 1 本を質 0.53 |
| 3 位 | 0.04331 | 1 本を質 0.35 |
| **10 位** | **0.00698** | **1 本を質 0.056**——**目標にやっと触った程度** |

**この「1 本ぶんの質」の出し方。****公開点は 8 エピソードの平均である。**
だから **1 本だけ届いて、その 1 本の質が q なら、点は q / 8 になる。**10 位の 0.00698 に
8 を掛けると 0.056 で、**これは「目標に触ったが、ぶつかりながら、ぎくしゃく動いた」水準**である。

**質 q が何で決まるかは、配布物からは読めない。****配布された採点コードには
重みと正規化の基準が入っていない**（`pipeline/total_score.py` の
`"weights": {}` と `"references": {}`。**コメントに「配布版: 本番の採点ロジック
（正規化・重み付き合成）は含まれない」と明記されている**）。
**読めるのは、成功の判定に衝突が入っていることである**——`rollout.py:234` は
`success = bool(done) and not collided` で、**ぶつかった回は届いても成功にならない。**

**つまり Track3 は、1 本届かせれば、質が最低水準でも 10 位以内に入る計算になる。**
**ただし「届いたがぶつかった」回が点になるかは、配布物からは読めない**（上のとおり成功判定には衝突が入っている）。**10 位の 0.00698 が 1/8 = 0.125 の倍数で
ないことから、部分的な点は付いていると読める**——そこまでが言えることである。

**関門そのものは、Track3 では決まらない。****Track3 は 190 人が 0 点の同着なので、
200 人 → 100 人の絞り込みは実質 Track1 と Track2 で決まる。**
そして**そちらは通っている見込みが高い**——Track1 が 36 位で、Track2 も
**最良（0.261）なら 80 位（0.20986）より上に出る。**
**ただしこれは推定である**——**3 トラックを合わせた順位表は見ていない。**

**だから Track3 の位置づけはこうなる。****関門を通るために要るのではなく、
上積みが取れる唯一の場所である。**Track1 で 0.014 稼いでも 36 位 → 29 位だが、
**Track3 は 0 → 0.007 で 90 人ぶん上がる。**

**注意が 2 つ。**

- **リーダーボードは「最良」ではなく「最後に出したもの」を載せている。**Track1 の 0.47768 も
  Track2 の 0.19151 も 9/2 に出した版の点で、**最良は 0.492 と 0.261 である。**
  **それでも枠を使って戻さない**——**順位を決めるのは最終提出フォームのほうで、
  そちらには既に最良が入っている。**
- **上の「1 本ぶんの質」は、リーダーボードの 8 エピソードの話である。**最終評価は
  タスクもエピソードも多い（資料 p.12・p.34）ので、**8 本の順位は代用品にすぎない。**

## 4. ① Track3 の指示文を、学習側の言い方へ一般規則で書き換える

### 背景 —— 学習データに、この言い方がほとんど無い

**Track3 は「逆向きのタスク」である**（例:「A を B に置く」に対して「B から A に戻す」）。
**配布されている 4 件の指示文はすべて「take … off / out of」の形をしている。**

**9/2 に学習データの指示文を全部走査した。**元になっている課題定義ファイル
（BDDL。シミュレータに「どの物をどこへ運べば成功か」を書いた設定ファイル）の
`(:language …)` を全件読んだ結果である。

| 数えたもの | 結果 |
|---|---|
| 指示文の種類 | **2,066 種** |
| そのうち「take … off / out of」 | **1 件**（0.05%） |
| 先頭の語の内訳 | place 228・could 199・pick 191・lift 145・grasp 136 |

**言い換えは豊富なのに、「取り出す・下ろす」系だけがほぼ無い。**
**モデルは「take the X out of Y」という言い方をほぼ見たことがない。**

### 狙いと、規約の線

**`take the X off/out of Y …` を `pick up the X …` へ写す一般規則を入れる。**
**手元で 1 回測れば、提出枠を使わずに採否が決まる。**

**規約上は許されている。**運営 Q&A No.29 が「`Pick the` → `pick up the` のような
言い換えの統一」を、No.31 が「学習データの指示文集合への埋め込み最近傍（意味の近い文へ
寄せる処理）を用いた入力正規化」を名指しで許容している。

**ただし No.31 は「最近傍の結果をタスク ID として分岐に使わないこと」と書いている。**
だから**Track3 の 4 文をべた書きした対応表は作らない。**文の形だけを見る一般規則にする。

### 外れる見込みのほうが高い、と先に書いておく

**動画で見えているのはもっと重い。**`alphabet soup`（**学習データにそのまま在る名前**）を
指示しても**別の物（クリームチーズ）を掴み、しかもトレイの中へ入れている。**

**学習データでは容器は常に「置き先」である。**だから欠けているのは言い方だけでなく
**「容器から出す」動作そのもの**である可能性が高い。

## 7. ④ 手元の評価を EGL に替えて、採点との食い違いが縮むかを見る

### 背景 —— 採点側と手元で、画像の作り方が違っていた

**9/2 に気づいた。****配布キットの `Dockerfile` の 17 行目は `ENV MUJOCO_GL=egl` である。**

**MuJoCo**（このコンペのシミュレータ）は**画像の描き方を 2 通り持っている。**

| 描き方 | 何を使うか | 1 コマ | 本選 1 エピソード |
|---|---|---|---|
| **EGL** | **GPU で描く** | **0.6 ms** | **30.6 秒**（RTX6000） |
| osmesa | CPU で描く（ソフトウェア描画） | 9.7 ms | 60.6 秒（JAIST サーバ） |

**エピソードの秒数はマシンも違うので、描き方だけの差ではない**（1 コマの 0.6 ms 対
9.7 ms は同じ 8/26 の実測である）。

**採点側は EGL で描いている。ところが手元の評価は、これまで全部 osmesa で測っていた。**
**osmesa を既定にしたのは JAIST のサーバが EGL を通せないためで、本番に近いからではない。**

**描画はモデルが見る画像そのものを作る。**実装が違えば画素が違う。
**8 本しかない集合では、1 本が入れ替わるだけで点が 0.06〜0.125 動く。**

### 狙い —— 当たれば残り 15 日の進み方が変わる

**1 変数の対照がすでに手元にある。****同じ重み**（累計 1,500 歩のもの）**を osmesa で
測った回が残っていて、その重みの採点側の点も分かっている**（Track2 で 0.233）。
**だから EGL で測り直して、どちらが 0.233 に近いかを直接比べられる。**

**縮めば、以後は提出枠を待たずに手元で重みを選べる。**
**枠が取り合いになった今、これは特に効く**——学習が 1 本しか回せない日に、
**「その 1 本が良くなったか」を翌日の提出まで待たずに判定できる。**

**縮まなければ、手元は診断だけに使うという今の線が裏づく**（それも収穫である）。

### 見込みは、縮まない側が高い

**これまでの食い違いは、成功したタスクの中身まで入れ替わる大きさだった**——
72 行で測った回では、**成功率が一致していても 36 本中 16 本は中身が入れ替わっていた。**
**描画の実装差で説明が付く幅を超えている。**

## 12. 言葉の説明

| 言葉 | 意味 |
|---|---|
| **π0.5** | 使っている基盤モデル。画像と言葉を受け取って動きを出す作り。41 億パラメータ |
| **Track1 / 2 / 3** | 1 = 学習済みの課題で背景と照明が変わる／2 = 視点・姿勢・配置・雑音が変わる／**3 = 逆向きの課題** |
| **摂動**（せつどう） | 元の課題に少しだけ変化を加えること（視点を振る、物の位置をずらす） |
| **EGL / osmesa** | シミュレータが画像を描く 2 通りの方法。**EGL は GPU で、osmesa は CPU で描く** |
| **BDDL** | シミュレータに「どの物をどこへ運べば成功か」を書いた設定ファイル |
| **fixture** | コンロ・棚・引き出しのように、シーンに据え置かれた物。掴んで運ぶ対象とは別 |
| **scripted policy** | 学習ではなく手で書いた手続きでロボットを動かすもの。デモを作るのに使う |
| **埋め込み最近傍** | 入力の文を、意味が近い学習データの文へ寄せる処理 |
| **提出枠** | リーダーボードへ出せる回数。**トラックごとに 1 日 1 回で、使わないと消える** |
| **最終提出フォーム** | 本選 1 の成績そのものを決める提出先。**期限内は何度でも差し替えられる** |
| **一時領域** | Blackwell の `/opt/dlami/nvme`。**セッションが終わると消える** |

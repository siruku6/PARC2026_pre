# 検証集合の作り直しへの申し送り（λ=0.25 の提出結果から）

**宛先**: `compare_with_production.py` と `docs/howto/04_proxy_eval.md` を書いている側。
**日付**: 2026-08-12。**根拠**: 8/12 04:04 に採点が返った提出（λ=0.25）のログ。

## 結論を 3 つ先に

1. **84 件を減らすのは必要。** 本番は 8 エピソードしか走らないので、手元も
   その規模でよい。ここは今の方針のままで良い。
2. **ただし件数だけ直しても、手元と本番が逆になる現象は消えない。**
   原因は件数ではなく、**学習に使ったタスクを検証にも使っていること**である。
   減らすだけだと、同じ向きに間違った数字が安く速く出るようになる。
3. **本番スコアを「答え合わせ」に使うときの分解能に注意。**
   0.1409 と 0.09507 は**同じと見なすしかない**（下の 2 節）。

---

## 1. 新しく分かった事実

出典はすべて `outputs/prod_eval_results/` の採点ログ本文である。
`POST /reset` の回数がエピソード本数、`/reset` から次の `/reset` までの
`POST /act` の回数がそのエピソードの歩数（`compare_with_production.py` の
冒頭に書いてある読み方と同じ）。

| 提出 | 重み | 本番スコア | 8 本の歩数（上限 300） | 打ち切り |
|---|---|---|---|---|
| 8/10 | 素 | **0.1409** | 300, 300, 300, 300, 138, 132, 174, 182 | 4/8 |
| 8/12 | 素 75% ＋ 学習 25% | **0.09507** | 300, 300, 300, 300, 143, 177, **300**, 168 | 5/8 |
| 8/11 | 学習のみ | **0.016** | 300, 300, 300, 300, 234, **300**, 139, **300** | 6/8 |

出典は順に `260810_評価結果_ema=0.3あり.md` /
`260812_040403_評価結果_lambda=0.25.md` /
`260811_評価結果_ema=0.3あり_初回学習後.md`。

**スコアは 0.125 の倍数になっていない**（0.1409 / 0.125 = 1.127）。
8 本なら成功率の刻みは 0.125 なので、**総合スコアは成功率そのものではなく
合成値**である。配点表（`total_score_config.json`）は配布されていないため、
**手元で同じ値は計算できない。**

## 2. 本番の分解能。`compare_with_production.py` の判定に効く

**8 本のうち 1〜4 本目は、3 種類の重みすべてで 300 歩に張り付いている。**
どの重みでも終われないタスクなので、**差がつくのは残り 4 本だけ**である。

そして **0.1409 と 0.09507 の違いは、エピソード 7 が 174 歩で終わったか
300 歩まで走ったかの 1 本だけ**である。

| 判定 | 使えるか |
|---|---|
| 「素の系統（0.09〜0.14）」と「崩壊（0.016）」を区別する | **使える。** 打ち切り 4/8 対 6/8 で歩数にも出ている |
| **0.1409 > 0.09507 の順序を再現できたかで代理集合を合格にする** | **使えない。** 1 本の差で、8 本では偶然と区別できない |

**お願い**: 順序の一致を見るとき、**この 2 つは同順として扱ってほしい。**
「手元でも 0.1409 > 0.095 になった」を根拠に代理集合を合格にすると、
偶然を再現できたことを実力と読み違える。

**1 つのスコアより 8 本の歩数のほうが情報が多い。** 打ち切りに張り付いた本数
（4 / 5 / 6）は単調に増えていて、こちらは合成スコアより素直な信号である。
判定材料に加えることを勧める。

## 3. 方向の修正（これが本題）

### 学習と検証が同じタスクを見ている

- **学習側**: [train.py](../../solution/train/train.py) の `_select_episodes` は
  `frame.groupby("task")` で回しており、docstring も「**全 40 タスクから**」と
  書いている。**タスクを外す引数が無い。**
- **検証側**: `make_validation_suite.py` は LIBERO-plus の
  `task_classification.json` から 84 件を作る。これは**同じ 40 タスクの
  摂動版**である（`task_id` の `_table_1` や `_view_0_0_...` が摂動、
  `instruction` は元のタスクのまま）。

つまり**検証に使っているタスクは学習済み**である。だから手元の数字は
「覚えた度合い」を測っていて、8/11 の
`outputs/0811_142300_lora20k_n5_ep1_max300/summary.txt`（学習後 0.500）と
`outputs/0811_101824_base_n5_ep1_max300/summary.txt`（素 0.476）が
本番の順序と逆になった。**どちらの数字も正しく、測っているものが違う。**

さらに [train.py の 108 行目](../../solution/train/train.py#L108) にこう書いてある。

> **苦手タスクの割合を上げる。** 84 件の検証用データで切り分けたら…

**検証結果が学習データの配分を決めている。** 二重に混ざっている。

### `libero_plus_id` で 84 件を外すだけでは足りない

**摂動版は元タスクの実演データを共有する。** 84 件の id を学習から抜いても、
同じ指示文の別の摂動版が学習に残るので、実演の中身は見たままになる。

**タスク（指示文）単位で丸ごと分ける必要がある。** 40 タスクを学習用と
検証用に割る。検証を 8 タスク分にすれば本番の規模（8 エピソード）と揃い、
**件数を減らす目的とも両立する。**

### 口はまだ無い

`make_validation_suite.py` には `--exclude` がある（既定は
`compe/t1/T1_TASKS.csv` の 4 件）。ただし**向きが逆**で、これは
「検証集合から例示を外す」ためのものである。

必要なのは **`train.py` 側に「このタスクは学習に使わない」という引数**で、
いま存在しない。両者が同じ CSV を読む形にすれば、片方だけ古くなる事故を防げる。

なお **`compe/t1/T1_TASKS.csv` の 4 件も学習に入っている**（id 80 / 241 /
2408 / 2467）。T1 を代理集合に使うなら、**この 4 タスクも学習から外す**必要がある。

## 4. 背景：なぜ学習すると本番で下がるのか

素の重み `lerobot/smolvla_libero_plus` に同梱されている `train_config.json` は
こう書いている。

| 項目 | 値 |
|---|---|
| `pretrained_path` | `lerobot/smolvla_base` |
| `steps` | 20,000 |
| `batch_size` | 32 |

**素の重みは、すでに LIBERO-plus で 20,000 歩学習し終えたものである。**
そこへ同じ LIBERO-plus で LoRA 20,000 歩を重ねている。**吸収済みのデータを
もう一度当てている**ので、得るものは小さく、重みがずれる損だけが残る。

λ の 3 点（0 → 0.1409、0.25 → 0.09507、1.0 → 0.016）は
**混ぜるほど悪くなる形で、素を超える点が無い。**

**だから検証集合の役目が変わる。** 「LIBERO-plus で成功率が上がったか」では
なく、**「学習に使っていないタスクで上がったか」**を測るものにしてほしい。
前者はもう素の重みが達成しており、測っても差が出ない（あるいは覚えた分だけ
上がって見える）。

## 5. やらないでほしいこと

**採点ログから本番の 8 タスクを特定して、手元に同じものを揃えること。**

- ログにタスク名は出ていない（`タスク用途: 3_Omni` だけ）。`/reset` で届く
  指示文を `policy_server.py` に出力させれば特定できてしまう。
- **ルール上の可否が未確定である。** 禁止事項は「評価結果を利用した追加学習や，
  評価観測を保存して後続の学習に利用すること」で、
  **質問 CSV の No.33（motofukao）が「何を学習するかの選定に自己評価の結果を
  使ってよいか」を聞いたまま未対応**である。
- 一方、**`/reset` と `/act` の回数から歩数を読むのは追加学習ではない**ので、
  `compare_with_production.py` の今のやり方は別扱いと考えている。
  **タスクの同一性まで踏み込まない線は守りたい。**

判断が必要なら、運営へ質問を出すのが先である。

## 6. 具体的な依頼

| # | やること | 対象 |
|---|---|---|
| 1 | **タスクを丸ごと外す引数を足す**（例 `--holdout-tasks <CSV>`）。指示文単位で外す | `solution/train/train.py` |
| 2 | 検証集合と学習の除外リストを**同じ CSV** から読む | `make_validation_suite.py` と 1 |
| 3 | **順序の判定で 0.1409 と 0.09507 を同順として扱う。** 合成スコアだけでなく**打ち切り本数**も判定に使う | `compare_with_production.py` |
| 4 | 件数削減は続けてよい。**ただし残す集合は「学習に使っていないタスクだけ」**にする | 検証集合の設計 |

**1 と 2 が入るまで、手元の成功率で重みの採否を決めないほうがよい。**
そこが入れば、いまの「84 件は時間がかかりすぎる」という動機と、
「本番の代理になる」という目的が同じ方向を向く。

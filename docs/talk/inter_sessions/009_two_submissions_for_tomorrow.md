### この依頼が効くところ —— **2 本とも「1 変数」の提出である**

**枠は 1 日 1 トラック 1 回しかない。だから 1 回の提出で 1 つだけ変える。**

| | 変えるもの | **答える問い** |

**なぜ Track1 でなめらかさを狙うのか。**5.0.1 の Track1 は
**8 エピソードすべてが打ち切り（300 歩）に達していない。**

**つまり成功の側はもう埋まっていて、残り（最高点 0.65）はなめらかさ 5 項でしか取れない。**

**採点式は公開されている。**

```
smooth metrics = w1·time + w2·jerk + w3·SPARC + w4·trajectory + w5·rotation   (Σw = 1)
Total Score    = (1/N) · Σ successᵢ · (1 − collision penaltyᵢ) · smooth metricsᵢ
```

**重みは非公開。**`time` は壁時計ではなく歩数である（運営 Q&A No.23）。

**`ema_alpha` は jerk の項を単調に動かす。**手元の 12 行での実測——
`ema_alpha` 0 / 0.3 / 0.5 に対して jerk の項が **0.437 / 0.478 / 0.508**。
**摘みは看板どおりに効いている。**

**ただし手元では合計点が下がった**（0.1436 / 0.2055 / 0.2011）。
**それは成功率が落ちたからで、その 12 行は衝突が集まるように選んだ集合である**
（衝突率 0.611。72 行全体は 0.227）。
**Track1 は衝突も打ち切りも出ていないので、同じ落ち方はしないと読んでいる。**
**これは読みであって、測った事実ではない。**

**なぜ Track2 で 1,000 歩を出すのか。**`001500` が 0.233 で、**その 1,000 歩版が
それより下なら「歩数を増やすほど上がる」と言える。**
**手元の評価では 500 歩の差を分けられない**——同じ重みを 2 回測るだけで
成功率が 0.667 と 0.722 の間を動く。**提出でしか測れない。**
**この結果が、いま回している長い学習（依頼 008）をどこまで伸ばすかを決める。**

### 長さが同じなら、9.4 GB を組み直さなくてよい

**`build_submission.py` が作る zip では `policy_server.py` が無圧縮（method=0）で入っている。**
**だから同じ長さの置き換えなら、バイトを差し替えて CRC を直すだけで済む。**
**5.1.0 の 3 か所は全部桁数が同じである。**

```bash
python3 solution/tools/build/patch_zip_policy_server.py <zip> --show   # まず中を見る

python3 solution/tools/build/patch_zip_policy_server.py <zip> \
    --replace '_MIN_LEXICAL = 0.65' '_MIN_LEXICAL = 0.50' \
    --replace '"PARC_EMA_ALPHA", "0.3"' '"PARC_EMA_ALPHA", "0.5"' \
    --replace '__version__ = "4.6.0"' '__version__ = "5.1.0"' \
    --in-place
```

**道具は書き換えの前後の設定を印字し、`zipfile` で読み直して `testzip()` まで通す。
通らなければ書かない。**`--in-place` を付けない限り 1 バイトも書かない。
**`policy_server.py` が無圧縮でなければその場で止まる。**

**`--replace` の左辺が zip の中に 1 か所だけあることを道具が確かめる。**
2 か所あると止まるので、そのときは**リポジトリを一時的に書き換えて組み直し、
`git checkout` で戻す**ほうへ切り替えること。

### なぜこの割り当てにしたか

**Track2 に `001000`（親案どおり）。**Track2 は 5.0.1 で逆算 3.93 本・打ち切り 2 本と、
**3 トラックで唯一、成功の側が天井に当たっていない**
（[../../reference/26_score_formula_fit.md](../../reference/26_score_formula_fit.md) 5 節）。
**歩数と点が連動するかは、上にも下にも動ける場所で測る。**
板 `F37` が計画した梯子（`001500` → `001000` → `000500`）の 2 段目でもあり、
**8/30 に Track2 へ `000500` を出せば、3 点の曲線が Track2 の上で閉じる。**

**Track1 に `000500`（親案どおり。ただし狙いを言い直す）。**Track1 は 5.0.1 で
**8 本すべて成功・打ち切り 0 本**、手元の目盛りの上限 0.492 にぴたりと乗っている（同 5 節）。
**上へは動かない。だから Track1 は「下がるかどうか」だけを見る計器である。**
成功が満点の状態は二項分布の分散が 0 なので、**1 本でも落ちれば −0.061 が雑音なしで出る。**
梯子のいちばん端（500 歩）をここへ当てたのは、**いちばん大きい差を、いちばん雑音の少ない
計器に通すため**である。

**Track3 にも `000500` を出す。親案の「出さない」を変えた。**

| なぜ変えたか | 中身 |
|---|---|
| **費用がほぼ無い** | **Track1 のために Mac へ降ろした zip を、もう 1 回上げるだけ。**組み直しも転送も増えない |
| **下振れが原理的に無い** | **リーダーボードの枠と最終評価の枠は別**で、最終評価は最後にアップロードした 1 本だけが採点される（[../260825_briefing.md](../260825_briefing.md)「提出のしくみ」）。**リーダーボードに何を出しても最終の点は動かない** |
| **枠は翌日に持ち越せない** | 出さなければ消える |

**ただし返ってくるのは 0.000 の見込みが高い。**`pi05_trial1500` は
**`rp3000` から続けた学習である**——HF `siruku6/pi05_trial1500` の
`001000/train_config.json` に `policy.pretrained_path = /workspace/rp3000`・`steps = 1500`
と書かれている（8/29 に `hf_hub_download` で取って確認）。
**その `rp3000`（4.2.0・8/24）も `001500`（5.0.1・8/28）も Track3 は 0.000 だった**
（`b_PARC2026_final/outputs/submission_logs/track3/260824_pi0.5_4.2.0.txt:2441` と
`.../260828_pi0.5_5.0.1.txt:2441`）。**`000500` はその 2 点の間にある。**

**それでも出すのは、「Track3 は学習の歩数では動かない」を 3 点で閉じるためである。**
逆向きのデータを作る数日（[../../plan/17_after_track3_disclosure.md](../../plan/17_after_track3_disclosure.md)
4 節・順 1）に踏み出す前の、最後の確認になる。
**当日の時間が足りなければ、3 枠のうち落とすのはこれである。**

**メジャー番号は重みのチェックポイントを指す**（4 = `rp3000`、5 = `001500`、
6 = `001000`、**7 = `000500`**）。これは `howto/02` の「版の上げ方」の表
（major は重みが変わったとき）と同じ決まりである。

- **`6.1.0`** = `001000` ＋ しきい値 0.50（`6.0.0` は `001000` ＋ 0.65。組んだが未提出）
- **`7.0.0`** = `000500` ＋ しきい値 0.50

**台帳の `6.0.1`（`000500` ＋ 0.65）は使わない。**未提出のまま 8/29 に zip を消しており、
**「メジャー番号は重み」に反する**（6 は 1,000 歩である）。**500 歩は 7 系に統一した。**

# はじめに：PARC2026って何？
PARC2026（AIRoA × 東京大学松尾・岩澤研究室 Physical AI Robot Challenge 2026）は、
ロボットに言葉で指示を出すと、その指示通りに体を動かすAI——専門用語では
VLA（Vision-Language-Action）モデル——の性能を競うコンペティションです。

カメラ映像（Vision）と指示文（Language）を入力として受け取り、
ロボットアームの動き（Action）を出力するモデルを作る競技です。
関連する事前講座への応募だけで4000人以上が集まっており、決して小規模なコンペではありません。

この記事では、PARC2026予選（Track1）に挑戦した記録を、
本格的なPhysical AI開発は今回が初めてという立場から、技術的な試行錯誤を中心にまとめます。

# 要約
先に全体の流れとスコアの推移を書いておきます。

配布されているサンプルモデル（何も工夫しない状態）の参考スコアは 0.0633
開発初期は主要タスクの成功率0%、スコア 0.000 からのスタート
モデルの推論結果をつなぐ部分に工夫を入れた（temporal ensemble）ところ、公式スコア 0.28844 に到達
（配布baselineの約4.5倍）
モデル自体には手を加えず、モデルの出力をどう扱うかという工夫で性能を伸ばしていった過程と、
その中で踏んだ失敗を中心に書いていきます。

# 1. 何を作ろうとしたか
Track1のタスクはシンプルです。牛乳をカゴに入れる、トマトソースを掴む、
鍋をコンロに置く、といった日常のちょっとした動作をロボットアームにやらせます。

シミュレーション環境（LIBERO-Plus）上で、カメラ映像とロボットの関節角度などの情報を受け取り、
次にどう動くかを7次元の数値（アームの移動方向・回転・グリッパーの開閉）として
0.1秒ごとくらいのペースで返し続ける、というのがモデルに求められる仕事です。

評価は成功・失敗だけでなく、動きが滑らかか、効率的に動けているか、
物にぶつかっていないか（安全性）も加味されます。
タスクを終えればいいのではなく、動きの質そのものが問われる競技です。

#2. 使用したモデル——SmolVLAからpi0.5へ
開発の最初期、公式配布baselineであるpi0.5というモデルを使いたかったのですが、
このモデルはPaliGemmaという基盤モデルをベースにしており、
利用には申請してアクセス権をもらう必要がありました（いわゆるgated repo）。

申請の順番待ちをしている間、先に別の軽量モデルSmolVLAを使って、
どこでモデルが失敗するのかを見極める作業を進めていました。

アクセス権が下りた後は、正式にpi0.5に切り替えました。
先に診断のやり方を確立しておいたことで、モデルの切り替え自体はスムーズに進みました。

v19以降のバージョンはこのpi0.5がベースで、v22以降、
モデルの中身（重み）は一切変わっていません
（v17・v18時点で使っていたモデルについては、正確な記録が残っておらず特定できていません）。
以降のバージョンで変わったのは、モデルが出した答えをどう使うかという部分です。
これについては後述の5・6で説明します。

# 3. データをどう集めたか
学習データをどう用意するかについては、3つのやり方を試して、2つは不採用にしています。

自動で成功記録だけ集める。 まず試したのは、既存のモデルにタスクを50回ずつ挑戦させて、
成功した回だけを記録して学習データにするというやり方です。

タスク	成功数（/50回）
黒いボウルを引き出しから出す	14回
トマトソースを掴む	42回
牛乳をカゴに入れる	35回
鍋をコンロに置く	47回
タスクによって成功率が28%〜94%とばらついており、
タスクごとの得意・不得意の差が大きいことが、この時点で見えていました。

失敗した方法：過去の動きを別の場面で再生する。 過去に成功した動きの記録（アームの移動データ）を、
別の初期配置で再生すればデータを増やせるのではと考え、試しました。
しかしこれは失敗しました。保存されていた記録にはロボットの手の位置や向きは入っていたものの、
牛乳パックやボウルが最初どこに置かれていたかという情報が入っていなかったからです。
動きの記録だけを再生しても、物体の位置が記録時と異なれば意味がありません。
この方法は早い段階で見切りをつけました。

teleopデータの追加。 人が直接コントローラーでロボットを操作して動きを記録するteleopというデータも、
約50本ほど追加してみました。ただ、動きの滑らかさを表す指標（ジャークなど）を確認したところ、
既存のデータより動きが粗く、無駄な往復も多いことが分かりました。
データの量を増やせば性能も上がるという想定で試したのですが、
確認した結果、質が伴っていないと判断し、最終的には使わないことにしました。

最終的に選んだ方法。 3つ試した結果、最終的にはLIBERO-Plusが公式に用意しているデータを、
そのまま選別して使うという方法に落ち着きました。
自分でデータを作り込むより、既にあるデータの中から質の良いものを選ぶ方に時間をかけた形です。

# 4. 学習方法——LoRA
限られたGPU時間という制約の中で、モデルの中身を全部書き換えるフルファインチューニングは
現実的ではありませんでした。そこで使ったのがLoRA（Low-Rank Adaptation）という手法です。
モデル全体を書き換えるのではなく、小さな追加パラメータだけを学習させることで、
元のモデルの大部分はそのまま保持しつつ、必要な部分だけを調整できます。

さらに、モデルの画像認識部分は凍結（固定）し、動きの決定に関わる部分だけを学習対象にすることで、
計算コストを抑えながらロボット制御に直接関わる部分を調整しました。

# 5. temporal ensemble
ここからが、このプロジェクトで一番の転換点です。

モデルは0.1秒ごとにアームの次の動きを決めているわけではなく、
今後50ステップ分の動きをまとめて予測し、そのうち先頭の10ステップ分だけ実行してから、
また新しく50ステップ分を予測し直す、という動き方をしています。

問題は、この予測し直すタイミングで動きが不連続になることがある点でした。
新しい予測と、直前の予測の続きにズレがあると、動きが一瞬不自然になります。

これを解消するために導入したのがtemporal ensembleという手法です。
新しい予測と、直前の予測のまだ使っていなかった部分を、7:3くらいの比率でブレンドして使います。
実装は次の通りです。

def _blended_action(policy, batch, te_state, alpha):
    if len(te_state["queue"]) == 0:
        new_chunk = policy.predict_action_chunk(batch)  # (B, chunk_size, D)
        n_act = policy.config.n_action_steps
        if te_state["prev_chunk"] is not None:
            old_remaining = te_state["prev_chunk"][:, n_act:, :]
            overlap = min(old_remaining.shape[1], new_chunk.shape[1])
            blended = new_chunk.clone()
            if overlap > 0:
                blended[:, :overlap, :] = (
                    alpha * new_chunk[:, :overlap, :]
                    + (1 - alpha) * old_remaining[:, :overlap, :]
                )
        else:
            blended = new_chunk
        te_state["prev_chunk"] = new_chunk
        te_state["queue"] = list(blended[:, :n_act, :].transpose(0, 1))
    return te_state["queue"].pop(0)

新しいchunkの予測と、直前chunkのまだ使っていなかった部分（old_remaining）を、
alphaと1 - alphaの比率で混ぜているだけの、数行の変更です。
alphaを0.60から0.70に上げた変更だけを対象にした同一シードでの比較では、
20エピソード中の成功数が17/20から18/20に改善しています。

モデルの中身は一切変えず、答えのつなぎ方を変えただけで、
公式スコアは0.28844まで到達しました。開発の中でも一番の発見でした。

# 6. adaptive replanning
temporal ensembleの成功を受けて、失敗した場面を細かく見直したところ、
興味深いパターンが見つかりました。同じ場面に対してモデルに何度か予測をさせてみると、
タスクに失敗した場面ほど予測結果のばらつきが大きいという傾向があったのです。
成功した場面の2.6〜3.4倍ほど、予測がばらついていました。
モデルの出力のばらつき自体が、その場面での不確実性を反映している可能性を示しています。

そこで、次のような仕組みを追加しました。

予測のたびに3パターンの候補を出す
実際に動かすのは1パターン目だけで、他の2つはばらつきの計測にのみ使う
3パターンのばらつき（disagreement）を計算する
ばらつきが小さい場合は、いつも通り10ステップ分まとめて進む
ばらつきが大きい場合は、4ステップだけ進んで再度予測し直す
不確実性が低い場面では効率を優先し、不確実性が高い場面だけ確認の頻度を上げる設計です。
しきい値は次のように決めています。

DISAGREEMENT_LOW_TH = 0.669   # 以下: v22と同じ10ステップ
DISAGREEMENT_HIGH_TH = 1.570  # 以下: 7ステップ／超えたら4ステップ

def _pick_cadence(pairwise_l2: float) -> int:
    if pairwise_l2 <= DISAGREEMENT_LOW_TH:
        return N_CADENCE_LOW   # 10
    if pairwise_l2 <= DISAGREEMENT_HIGH_TH:
        return N_CADENCE_MED   # 7
    return N_CADENCE_HIGH      # 4

このしきい値（0.669、1.570）は勘で決めたものではなく、28エピソード分のオフライン診断データにおける、
成功群と失敗群それぞれのばらつきの分布（p75/p90）から決めています。

同じモデルの中身のまま、この工夫だけで、80回のテストで成功率が87.5%から92.5%に改善し、
特に元々0/6だった難しいケースが2/6まで改善しました。衝突のリスクもほぼ半減しています。

# 8. うまくいかなかったこと
サーバーが正常に動くことと、タスクができることは別だった。 開発初期、
モデルを組み込んだサーバーは/healthにも/actにも正常に応答していました。
しかし実際のタスク成功率は0%でした。
エラーなく動いていることだけを確認し、出力されたactionの中身を見ていなかったことが、
この時点での根本的な原因でした。

データを増やしたら、逆に動きが悪化した。 前述の3で触れたteleopデータの追加は、
量を増やしたはずなのに、動きの滑らかさがかえって悪化するという結果になりました。
「量が増えれば性能も上がる」という前提のまま、追加前にデータの質（ジャークや無駄な往復）を
確認していなかったことが原因でした。この一件以降、データを追加する前に必ず質を確認する
運用に変えています。

# セッション間の依頼のやり取り

**このセッション（施策の優先順位を決める側）が、具体的な作業を別のセッションへ渡すための場所である。**
2026-08-28 に作った。狙いは 1 つ——**1 つのセッションが抱える文脈を減らし、
判断する側が結果だけを読めるようにする。**

## 1 依頼 1 ファイル。往復も同じファイルに書く

`NNN_<英語のスラッグ>.md` という名前にする。番号は通し番号で、使い回さない。

**依頼と報告を同じファイルに置く。** 別ファイルにすると対応付けが必ず崩れる。
ファイルの上から順に「依頼」「報告」と並ぶ。

## 状態はファイルの 1 行目に書く

```
> **状態: 依頼中** ／ 受け側: 未定 ／ 更新: 2026-08-28
```

状態は **依頼中 → 着手 → 報告済み → 閉じた** の 4 つだけ。
**閉じたものは消さずに残す**——同じことを二度依頼しないための記録である。

## 依頼を書くときの決まり

**受け側は聞き返せない。** 別のセッションなので、こちらの会話も、いま何を測っているかも
見えない。だから `decision-request` スキルと同じ前提で書く——**そのファイルだけで作業が終わること。**

| 節 | 中身 |
|---|---|
| **何をしてほしいか** | 1〜2 行。**成果物の形**（ファイルか、数値か、判断か）をここで名指しする |
| **なぜ要るか** | この結果が**どの判断を変えるか**。これが書けない依頼は出さない |
| **前提となる事実** | 受け側が知らない数値・ファイルの場所・すでに分かっていること。**リンクではなく本文に書き写す** |
| **やること** | 番号付き。コマンドは省略せずそのまま打てる形で |
| **できあがりの条件** | 何が揃ったら終わりか。**受け側が自分で判定できる形にする** |
| **やらなくてよいこと** | 範囲を広げさせないために書く |
| **報告の書き方** | 数値の並べ方の指定。**長い説明は要らない、表と数値がほしい** |

## 受け側が守ること

- **勝手に範囲を広げない。** 気づいたことは「報告」の末尾に 1 行で書き、実行はしない。
- **`docker run` はこのマシンでは通らない**（組織の制約・解除不可）。既に起動しているコンテナへの
  `docker exec` は通る。GPU の評価は会社の RTX6000 でユーザが回す。
- **`NOW.md` は書き換えない。** 書き換えるのはユーザである。
- 報告には**実測値と、それを出したコマンドかファイルの場所**を必ず添える。

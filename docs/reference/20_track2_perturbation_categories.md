**Camera・Noise は「物理を変えない」（レンダリング設定・画像後処理）が、Robot・Layout は
物理そのものを変える。** 同じロールアウトを別のカメラ設定・画質で撮り直しても行動ラベル
（action）は変わらないが、初期姿勢や物体配置が変わると既存の行動列をそのまま再生しても
正しい観測・行動対にはならない。この違いが学習データの作り方（Tier 1 と Tier 2 の区別、
[09 §2](../plan/09_demo_perturbation_pipeline.md#2-シナリオ--摂動--程度)）に直結する。

### 2.1 Sensor Noise は「いつ・どこで」画像にかかるか

**MuJoCo が描いたきれいな画像を、Python 側で毎フレーム後処理して汚す。** シミュレータの
物理・レンダリング設定は一切変えず、`ControlEnv.step()` と `ControlEnv.reset()` が返す
観測の中の `agentview_image` だけを、返す直前に配列ごと差し替える
（`env_wrapper.py:285-309`・`311-348`）。

| 観点 | 中身 |
|---|---|
| **いつ** | 毎ステップ（`step()` 内）と、エピソード先頭の 1 枚（`reset()` 内）の両方。1 エピソードにつき 1 回だけかかる摂動ではなく、**全フレームにかかり続ける** |
| **どこに** | `agentview`（据え付け俯瞰カメラ）の画像だけ。**手首カメラ（`robot0_eye_in_hand_image`）は汚されない**（コード中に該当カメラへの処理が無い） |
| **何に対して** | シミュレータの出力（レンダリング後の RGB 配列）に対する後処理。ロボットの行動・物理状態・カメラの位置や向きは変えない |
| **強度の決め方** | ファイル名の末尾 `_noise_N`（N=1〜50）を `ControlEnv.__init__` が解析し、`self.noise = N` として保持する（`env_wrapper.py:207-233`） |

**N=1〜50 は、5 種類の劣化×severity 1〜10 を連番にしただけである**（`env_wrapper.py:294-307`）。

| N の範囲 | 劣化の種類 | 中身 |
|---|---|---|
| 1〜10 | `motion_blur` | 被写体ブレ。radius・sigma が severity で増加、**角度は呼び出す度に `np.random.uniform(-45, 45)` で毎回引き直す**（`env_wrapper.py:30-58`） |
| 11〜20 | `gaussian_blur` | ガウシアンぼかし。sigma=1〜10（severity と同値） |
| 21〜30 | `zoom_blur` | ズームブレ（中心から外へ複数倍率でぼかしを重ねる） |
| 31〜40 | `fog` | 霧。diamond-square 法で生成したフラクタル地形を明るさに加算 |
| 41〜50 | `glass_blur` | すりガラス。ぼかした後、近傍画素をランダムに入れ替える処理を複数回反復 |

**severity（1〜10）は劣化の強さの段階を表す整数で、確率的な「効き方」ではない。** ただし
劣化の関数自体が乱数を使うため、**同じ N（＝同じ severity）でも 1 フレームごとに見た目の
実現値は変わる**（motion_blur の角度、glass_blur の入れ替え先など）。「決まった 1 枚のノイズ
画像を貼り付ける」のではなく、「決まった強さの劣化関数を、乱数を引き直しながら毎フレーム
再適用する」という動き方をする。

**5 種の実装（`motion_blur`〜`glass_blur`・`plasma_fractal`）は Hendrycks & Dietterich が
ImageNet-C ベンチマークのために公開したコードそのものである。** コメントアウトされた
severity 5 段階の定数列（例: `motion_blur` の `# c = [(10, 3), (15, 5), ...]`）が元の
ImageNet-C の値で、LIBERO-plus は同じ関数を 10 段階に細分化して使っている。

- 論文: Hendrycks & Dietterich, *Benchmarking Neural Network Robustness to Common
  Corruptions and Perturbations*, ICLR 2019. <https://arxiv.org/abs/1903.12261>
- 公式実装: <https://github.com/hendrycks/robustness>
  （`ImageNet-C/create_c/make_imagenet_c.py` に同名の `motion_blur`・`gaussian_blur`・
  `zoom_blur`・`fog`・`glass_blur`・`plasma_fractal` がある）

### 2.2 強さを決める数値と、その幅

**摂動の強さは、タスク名の末尾に埋め込まれた整数で決まる。** カメラ系はタスク名が
`<元のタスク名>_view_<方位角>_<仰角>_<拡大率×100>_<レンズ回転>_<レンズ上下>_initstate_<番号>[_noise_<番号>]`
という形で、`ControlEnv.__init__` がこの文字列を分解して数値をそのまま設定に使う
（`env_wrapper.py:207-221`）。**`difficulty_level` 列は強さの段ではない**——同じ
`difficulty_level` の中に弱い摂動と強い摂動が混ざっているので、強さを揃えて測るときは
この整数を直接指定する必要がある（5 節の Robot Initial States で 1 度、4.1 節の
Camera で 1 度、それぞれ実際に読み違えかけた）。

`task_classification.json`（revision `4976dc3`）の全 10,030 件から、この整数の幅を
実際に数えた値である。

| カテゴリ | 強さを決める数値 | 幅 | 刻み |
|---|---|---|---|
| Camera Viewpoints | 方位角（左右の回転） | **−75〜+75°** | 150 通り |
| | 仰角（上下の回転） | **0 と 15 のみ** | 2 通り |
| | 拡大率 `scale_factor` | **100〜200%** | 84 通り |
| | レンズ回転・レンズ上下 | **−10〜+10°** | 各 11 通り |
| Robot Initial States | 初期姿勢番号 `_initstate_N` | 1〜500 | 450 通り |
| Sensor Noise | ノイズ番号 `_noise_N` | 1〜50 | 50 通り |
| Objects Layout | 邪魔物体を足した bddl の番号 `_add_N` | 1〜30 | 30 通り |

**`_add_N` の `N` は物体の数ではなく、あらかじめ用意された bddl ファイルの番号である。**
1 つの元タスクにつき 60 個（N=1〜30 が 2 系統）用意されていて、`N` が大きいほど
`(:objects)` に並ぶ物体が多い——`KITCHEN_SCENE3` で数えると N=1 で 3 個、N=30 で 10 個、
**相関 0.939**。1 対 1 ではないが、`difficulty_level` や Robot の `_initstate_N` と違って
**強さの軸としてそのまま使える**（Robot の番号は摂動量と 1 対 1 でなく、5 節で読み違えかけた）。

**方位角は生の値では 0〜75 と 285〜359 の 2 つの塊に分かれており、76〜284 には 1 件も
無い。** 285 は「反対向きに 75° 回す」を 360−75 と書いたものなので、2 つの塊は合わせて
「左右どちらかに 0〜75°」という 1 つの範囲になる。**90° や 180° といった、真横・真後ろ
からの視点は存在しない。**

**方位角の分布は二山である。** 絶対値で数えると、Camera Viewpoints 1,599 件のうち
**44.6% が 15° 未満、44.3% が 30° 以上**で、その間が薄い。

| \|方位角\| | 件数 | 割合 |
|---|---|---|
| 0°（＝拡大率かレンズ向きだけを変えた変種） | 607 | 38.0% |
| 1〜14° | 106 | 6.6% |
| 15〜29° | 177 | 11.1% |
| 30〜44° | 231 | 14.4% |
| 45〜59° | 234 | 14.6% |
| 60〜75° | 244 | 15.3% |

方位角 0° の 607 件は、313 件が拡大率だけを変えたもの（`scale_factor` ≠ 100）、
294 件がレンズの向きだけを変えたもの（レンズ回転・レンズ上下 ≠ 0）である。
**つまり「Camera Viewpoints」1 カテゴリの中に、視点を回すもの・寄り引きするもの・
カメラ自体を傾けるもの、という性質の違う 3 種類が同居している。** 4.1 節の実測が
示すとおり、この 3 種類は効き方が違うので、カテゴリ平均で読むと実像が消える。

### 2.3 一覧に無い数値の組み合わせでも評価できる

**`task_classification.json` に載っていない組み合わせを自分で書いても、評価は動く。**
`ControlEnv.__init__` が存在を確かめているのは、`_view_` より前を切り出した**元の
`.bddl` ファイルだけ**である（`env_wrapper.py:235-237` の `assert os.path.exists`）。
方位角・仰角・拡大率などの数値は一覧を参照せず、文字列から読んだ値をそのまま使う。

**これは強さを揃えて測るために必要な性質である。** 一覧に載っている組み合わせは
タスクごとに幅が違い（例: `KITCHEN_SCENE3` の方位角は 0° か 31〜45° しか無く、
`KITCHEN_SCENE8` は 0° か 16〜30° しか無い）、同じ 8 タスクを同じ強さで揃えて測ることが
一覧の中だけではできない。4.1 節の 48 行はこの性質を使って作った。

実際に 2 回確認した。高強度 Sensor Noise の 32 行のうち 4 行、方位角スイープの 40 行
すべてが一覧に無い組み合わせだが、いずれも全件が最後まで走った。

## 4. 自チームの実測（Track2 疑似検証スイート、2026-08-22。**成功率だけの読みは誤りで、
ステップ数の読みに訂正済み**）

**`compe/val/TRACK2_PROBE.csv`（8 タスク×[Base+4 摂動]=40 行）を、提出物
`work/artifacts/pi05_rp3000`（π0.5 系）で実際に評価した結果である**
（`work/gpu_eval/0822_092556_track2_probe_n16_ep1_max300_ema03_blend0_s1/summary.txt`）。
推論設定は予選最終提出 4.2.0 相当に固定（本番 0.485 と並べて読むため）。

**撤回した判断**: 最初は成功率だけを見て「Sensor Noise だけが Base より明確に低く、
Camera・Robot・Layout は Base と同率 88% で崩れていない」と判断した。この判断は誤りだった。
**手元の成功率は本番の順位を付けられない**という、このチームが予選ですでに確立していた
教訓（[knowledge/07_local_eval_cannot_rank.md](../knowledge/07_local_eval_cannot_rank.md)。
手元 +3 件が本番 0.264→0.169 にも 0.264→0.485 にもなった 2 例）を、この 40 行の
読み方には適用していなかった。本番と繋がっている量は**「基準（Base）で完走していた件
だけのステップ数」**（[knowledge/06_step_count_drives_score.md](../knowledge/06_step_count_drives_score.md)、
r=−0.868）であり、成功率は「壊れていないことの確認」にしか使えない。

**訂正後の数字**（`solution/tools/probe/summarize_probe_by_category.py`で算出）:

| カテゴリ | 成功率 | 打ち切り | ステップ中央値 | ステップ最大 | **基準完走件のステップ比** |
|---|---|---|---|---|---|
| **Camera Viewpoints** | 88%（7/8） | 0/8 | 177 | 290 | **+34.6%** |
| **Sensor Noise** | 75%（6/8） | 2/8 | 136 | 300 | **+24.4%** |
| Robot Initial States | 88%（7/8） | 1/8 | 132 | 300 | +17.5% |
| Objects Layout | 88%（7/8） | 1/8 | 136 | 300 | +15.6% |
| Base（無摂動） | 88%（7/8） | 1/8 | — | — | 基準 |

**成功率の順位とステップ数の順位が逆転している。** 成功率だけでは崩れていないように
見えた Camera Viewpoints が、ステップ数では最も大きく崩れている（+34.6%）。Robot・Layout
も +15〜18% と無視できない。**「成功はしたが遅い」「300 ステップの打ち切りに近づいている」
という、成功率には出ない副作用がカテゴリ間で異なる大きさで存在する。**

**標本数は 1 カテゴリあたり 8 件（比較は n=7）しかない。** Camera Viewpoints の +34.6% は
8 タスク中 2 タスク（衝突 1 件・290/300 ステップ 1 件）が主因であり、統計的に強い結論
ではない。**今は事前準備段階なので n=8 のまま進めるが、量子化推論の高速化で GPU 評価の
コストが下がり次第、標本数を増やして数字を確かなものにする**（2026-08-22 決定）。

### 4.1 Camera Viewpoints の方位角スイープ実測（48 行、2026-08-23）

**4 節の Camera Viewpoints 8 行は、方位角を 1 度も動かしていなかった。** 8 行すべてが
方位角 0°・仰角 0° で、4 行が拡大率だけ（121〜193%）、4 行がレンズの向きだけ（±10° 以内）を
変えたものだった。つまり +34.6% は「視点を回した」結果ではなく「寄り引きとカメラの傾き」の
結果であり、**視点を回す摂動の効き方は 4 節の時点では未測定だった。**

**測り方**: 4 節と同じ 8 タスクについて、方位角だけを 15/30/45/60/75° に変え、
仰角・拡大率・レンズ向き・初期姿勢はすべて既定値に固定した 40 行を作り、同じ 8 タスクの
無摂動（Base）8 行を並べて 48 行の CSV にした。組み合わせは 2.3 節の性質を使って
自分で書いた（一覧には 1 件も無い）。推論設定・重みは 4 節と同一に固定し
（`work/artifacts/pi05_rp3000`、1 セル 1 エピソード）、
`solution/tools/probe/summarize_probe_by_category.py` と同じ読み方——**Base 側が 300
ステップで打ち切られた組は除く**——でステップ比を出した。

| 方位角 | 成功 | 打ち切り | ステップ中央値 | **基準完走件のステップ比** |
|---|---|---|---|---|
| 0°（Base） | 6/8 | 2/8 | 160 | 基準 |
| 15° | 8/8 | 0/8 | 132 | **−0.6%**（n=6） |
| 30° | 7/8 | 1/8 | 180 | **+33.6%**（n=6） |
| 45° | 3/8 | 5/8 | 300 | **+51.1%**（n=6） |
| 60° | 4/8 | 4/8 | 216 | **+49.4%**（n=6） |
| 75° | 3/8 | 4/8 | 292 | **+66.3%**（n=6） |

#### ステップ比は 300 の打ち切りに引きずられている（読み方の訂正）

**上の表のステップ比は、そのままでは強さの指標として読めない。** 摂動側が 300 ステップで
打ち切られた組では、比が `300 ÷ Base の歩数 − 1` になり、**真の歩数（300 より大きいが
不明）ではなく「Base がどれだけ短かったか」で決まる。** 45° の 3 組は
Base 223→300（+35%）・125→300（+140%）・82→300（+266%）で、この 3 つが +51.1% の主因である。

打ち切られた組を外すと、値がこう動く。

| 方位角 | ステップ比（表のまま） | 打ち切りを外した比 | 残る組数 | **300 に達した割合（打ち切られない指標）** |
|---|---|---|---|---|
| 0°（Base） | 基準 | 基準 | — | 2/8 |
| 15° | −0.6% | −0.6% | 6 | **0/8** |
| 30° | +33.6% | **+17.3%** | 5 | **1/8** |
| 45° | +51.1% | **−11.8%** | 3 | **5/8** |
| 60° | +49.4% | **+18.7%** | 3 | **4/8** |
| 75° | +66.3% | **+68.0%** | 3 | **4/8** |

**外した比も信頼できない**——45° と 60° は 3 組しか残らず、しかも外したのは「いちばん悪い
3 組」なので、悪化を過小に見せる（`compare_steps.py` が全体と「両方成功した件だけ」の
両方を出しているのと同じ理由。[knowledge/06](../knowledge/06_step_count_drives_score.md)）。
**打ち切りに引きずられない量は「300 に達した割合」で、こちらを主に読む。**

タスクごとに割ると、1 タスクの跳ねに強く依存していることも分かる（Base が打ち切られた
2 タスクを外した 6 タスクのステップ比の中央値）。

| 方位角 | 15° | 30° | 45° | 60° | 75° |
|---|---|---|---|---|---|
| タスク別ステップ比の中央値 | +3.8% | +5.1% | +18.6% | +50.6% | +50.6% |
| 悪化したタスク数 | 4/6 | 4/6 | 4/6 | 5/6 | 4/6 |

#### 読み取れること

1. **方向は残る。** 「300 に達した割合」で見ると、15°・30° は Base（2/8）と同じか良い
   （0/8・1/8）のに対し、**45° 以上は 4〜5/8 と明確に悪い。** タスク別中央値も
   +3.8%→+50.6% と伸びる。**Camera Viewpoints は 4 カテゴリの中で唯一、強度を上げると
   悪化することが確認できたカテゴリである。**
2. **崩れ始めは 30° ではなく、30° と 45° の間である。** 30° の時点では 300 に達した割合が
   1/8（Base より良い）、タスク別中央値も +5.1% にとどまる。**表のまま読んだ +33.6% が
   4 節の Camera の +34.6% とほぼ同じに見えるのは、どちらも打ち切りを含んだ値だからで、
   「4 節が測っていた負荷は方位角 30° 相当」とは言えない。**
3. **2.2 節の二山と重ねると、本選で出る Camera 摂動のうち 44.3%（30° 以上）が悪化する側、
   44.6%（15° 未満）がほぼ無害な側に落ちる。** カテゴリ平均は、この 2 つを平均した値に
   なるので、対策の効き目を測る指標には向かない。

**粒度の限界が 3 つある。** どれも 1 セル 1 エピソードから来る。

- 成功率は 1 件 = 12.5 pt 刻みで動く。45°→60° の −1.7 pt は逆転と読まない。
- **推論は乱数を使い、seed を固定していない**（`policy_server.py` は
  `_get_action_chunk` に `noise=None` を渡し、モデル側が毎回引く）。**同じ条件を
  繰り返した評価が 1 度も無いので、揺れ幅が分かっていない。**
  `turn_on_the_stove` は Base 82 歩・15° 85 歩・30° 83 歩・**45° 300 歩（未完了）**・
  60° 89 歩・75° 74 歩と、45° だけが跳ねて戻っている。**【8/23 追記】これは揺れだった**
  ——同じ行を同じ設定で 3 回回すと **300 → 74 → 70 歩**になる。同じく、上の表で
  「Base が 300 で打ち切られたので除いた」2 行のうち `STUDY_SCENE1` は
  **300 → 219 → 170 歩**で、除いた理由が「そのタスクが遅い」ではなく
  「その 1 回が転んだ」だった。**24 行のうち 14 行で 3 回の結果が割れる。**
  詳細と、この揺れの中でも結論が残ること（Base 2/24 対 45〜75° 31/72、p=0.0023）は
  [plan/10 の 7.1 節 (10)〜(12)](../plan/10_eval_perturbation_suite.md)。
- ステップ比の n は 6 以下で、上の表のとおり打ち切りを外すと 3 まで落ちる。

`work/gpu_eval/0823_141340_camera_azimuth_n16_ep1_max300_ema03_blend0_s1/summary.txt`。

## 5. 実測と文献の食い違い（確認したい仮定）

**3 節（他モデルの文献値）と 4 節（自チームの実測、ステップ数ベース）を比べると、
食い違いは当初思っていたほど大きくない。** 文献では Camera・Robot が他カテゴリより
一段深く崩れると報告されており、4 節のステップ数ベースの読みでも **Camera Viewpoints が
最も大きく崩れている（+34.6%）**点は文献と方向が一致する。一方 **Robot Initial States は
文献（mix-SFT でも伸びが最も小さい弱点カテゴリ）ほど突出して悪いわけではなく、
Objects Layout と近い水準（+17.5% 対 +15.6%）**である。

**Sensor Noise は依然として食い違いが残る。** CRT 論文は π0.5・SmolVLA がセンサ劣化で
90%→2% まで崩れると報告するが、4 節の実測は +24.4%（打ち切り 2/8）に留まる。原因の
候補として、**このスイートの Sensor Noise 8 行が `_noise_3`〜`_noise_14`——LIBERO-plus の
5 種の画質劣化のうち最も軽い motion_blur・gaussian_blur の低〜中強度しか使っておらず、
より崩れの大きい zoom_blur・fog・glass_blur を 1 件も試していないこと**が判明している
（[09 §3.2](../plan/09_demo_perturbation_pipeline.md#32-高強度sensor-noiseの追加実験実行済み2026-08-22)）。
**この確認のための追加実験（`SENSOR_NOISE_HIGH_PROBE.csv`、32 行）は実行済みである
（2026-08-22、[09 §3.2](../plan/09_demo_perturbation_pipeline.md#32-高強度sensor-noiseの追加実験実行済み2026-08-22)）。**
結果は総合成功率 90.6%（29/32）——severity を上げても崩れなかった。つまり文献値との
食い違いは「強度の違い」では説明できず、**LIBERO-plus の合成画質劣化は π0.5 系モデルに
対して CRT 論文が報告するほどの崩れを起こしていない**、という結論になった
（Sensor Noise 対策の投資優先度を下げる判断に反映済み）。

**Robot Initial States にも、同じ構造の食い違いがあったが、Sensor Noise と同じ結論で
解決した。** 文献では mix-SFT 後も伸びが最小（+8.6pt 止まり）の弱点カテゴリだが、
自チームの実測は +17.5%でObjects Layout（+15.6%）とほぼ同水準——これが
`make_track2_probe.py`の`_pick_variant`が各カテゴリで「難易度が中央値の1件」しか
選ばないこと（中央値＝難易度3）による見落としなのかを、難易度5（分類表上の最大）の
追加probe（16行）で確認した（2026-08-23、
[09 §3.3](../plan/09_demo_perturbation_pipeline.md#33-高強度robot-initial-statesの追加実験実行済み2026-08-23)）。

**確認の途中で、`difficulty_level`は実際の関節角摂動量の段ではないことが判明した。**
`env_wrapper.py`は`_initstate_N`の`N`を直接使って`robots/new_init.py`の摂動量
（1〜100→0.1、…、401〜500→0.5）を選ぶが、この`N`と分類表の`difficulty_level`を
1550件全体で突き合わせると、**difficulty_level=5の変種にも実際の摂動量が0.1〜0.5まで
全段階混ざっている**（相関はあるが1対1ではない）。今回選んだ8件で実際の摂動量を
逆算すると平均0.19→0.31（8件中6件で増加・2件は変化なし・減少は0件）——狙った
0.3→0.5ほどきれいではないが、**実際に摂動量は増えている。**

**結果は悪化ではなく縮小だった。** 実際の摂動量が平均1.6倍に増えたにもかかわらず、
ステップ比は+17.5%→+2.0%と縮んだ。Sensor Noiseと同じく、摂動量を上げても崩れない。
つまり Robot Initial States の弱さも文献ほど突出しておらず、+17.5%という値自体が
元のprobe（n=8）の揺れだった可能性が高い。

**残っていた Camera Viewpoints の強度依存も測り、悪化が確認された**
（4.1 節、2026-08-23）。方位角 45° 以上で「300 ステップに達した割合」が 4〜5/8 になり、
Base（2/8）・15°（0/8）・30°（1/8）と明確に分かれる。ただし 2.2 節の二山により、本選で
出る Camera 摂動のうち悪化する側は 44.3% である。

**【8/24 訂正】「強度を上げて悪化するのは Camera だけ」＝「効くのは Camera だけ」では
なかった。** エピソードを 3 倍に増やして 16 タスクで測り直すと、**いちばん歩数が伸びるのは
Robot Initial States（+47.8%）で、Camera（+16.6%）の 3 倍近い**
（[plan/10 の 8.2 節](../plan/10_eval_perturbation_suite.md)）。

**この節が Robot を「文献ほど突出していない」と読んでいたのは、測り方の誤りによる。**
Robot の効き方は「Base が安定して速いタスクを 300 に張り付かせる」形（`turn_on_the_stove`
は Base [81, 83, 76] 歩 → 摂動 [85, 206, 300] 歩）で、**「両側が完走した組だけ」で読むと
その組が除かれて効果が消える。** 組を Base 側だけで選ぶと、12 タスク中 12 タスクで歩数が
増え（二項検定 p = 0.0005）、6 タスクが壊れた。

**上の「摂動量を上げても悪化しない」自体は正しい。** 今回選ばれた 16 変種の実際の摂動量は
平均 0.20 で、高強度 probe が上げた先（平均 0.31）と重なる。**つまり Robot は摂動量 0.2 で
既に効いており、そこから上げても増えない（飽和している）。** 文献（mix-SFT 後も伸びが
最小の弱点カテゴリ）との食い違いは、これで解消する。

**投資の順は Robot Initial States → Camera Viewpoints である**（[plan/10 の 8.5 節](../plan/10_eval_perturbation_suite.md)）。

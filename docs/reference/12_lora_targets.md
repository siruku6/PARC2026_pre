# 12. LoRA をどこに当てるか — 4 つの候補と、採用したもの

**追加学習で動かしているのは、モデル 4.5 億個のうち 74 万個（0.17%）だけだった。**
残り 99.8% は凍ったままである。ここを広げると成績が動くのか、広げるとしたら
どこまでか。**候補を 4 つ並べて、1 つを選んだ記録である。**

先に用語を 2 つ。

- **LoRA** …… 元の重みは凍らせたまま、その隣に小さな差分だけを置いて学習する
  やり方。**当てた層だけが学習の対象になる。**
- **中間結果** …… 順方向の計算で出てくる途中の値。**逆伝播で使うので、
  学習する層から損失までの経路にあるものは、全部メモリに置き続ける。**
  ここがメモリを食う正体である。

## モデルの中身と、いま学習している範囲

| 部位 | パラメータ | 割合 | 従来の扱い |
|---|---|---|---|
| VLM（画像と言葉を読む側） | 350,165,184 | 77.8% | **完全に凍結** |
| └ うち視覚エンコーダ | 86,433,024 | 19.2% | **完全に凍結** |
| action expert（動きを出す側） | 98,245,840 | 21.8% | q/v 射影だけ LoRA |
| 射影層など | 1,635,152 | 0.4% | LoRA |

**出発点の重み（`lerobot/smolvla_libero_plus`）は、この 4.5 億個を全部学習して
作られている。** 同梱の `train_config.json` が `use_peft: false` /
`freeze_vision_encoder: false` / `train_expert_only: false` である。
**我々はその上に 0.17% だけを載せていたことになる。**

## 候補の一覧

| 候補 | 当たる層 | 学習される重み | 採否 |
|---|---|---|---|
| ① action expert だけ（LeRobot の既定、r=16） | 37 | 742,656（0.17%） | **（従来）** |
| ② ① ＋ **言語**（r=32） | 69 | **3,123,712（0.69%）** | **（今回採用）** |
| ③ ② ＋ **視覚**（r=32） | 93 | 4,303,360（0.96%） | （見送り・メモリ不足） |
| ④ ① ＋ **視覚**、言語は外す（r=32） | 61 | 2,664,960（0.59%） | （見送り・メモリが減らない） |
| ⑤ 全パラメータ学習（出発点と同じやり方） | — | 450,046,176（100%） | （見送り・後述） |

**当たる層の数は、重みファイルのキーと正規表現を突き合わせて数えたものである。**
`--peft-scope` の指定と対応する（`expert` / `text` / `vlm`）。

## なぜ ② を採ったか

### 理由 1 — 0.17% は、文献が良いとする幅より 1 桁小さい

研究の結果が 2 つあり、**逆を向いているように見えて、実は別のことを言っている。**

| 出典 | 設定 | 言っていること |
|---|---|---|
| [arXiv:2607.10172](https://arxiv.org/abs/2607.10172) | π0 を**別のロボットへ移す** | **VLM を凍結すると成功率 0.76 → 0.15。** 推奨は「r=16〜32 を VLM と action expert に均等」 |
| [arXiv:2605.06175](https://arxiv.org/abs/2605.06175) | **LIBERO-plus**（我々と同じ） | **全パラメータ学習は 74.9% で PEFT に負ける。** 良かったのは 2.51% を学習する構成 |

**前者は「移す」話で可塑性が要る。後者は「同じ課題で摂動に耐える」話で保存が要る。
我々は後者である。** だから ⑤（全パラメータ学習）は見送った。

ただし**後者が良いとする 2.51% に対し、我々の 0.17% は 15 分の 1 である。**
どちらの推奨からも外れて小さい側に落ちていた。**これが広げる根拠である。**

### 理由 2 — 落としているのは言語の摂動

評価のタスク名には摂動の種類が入っている。5 件の手早い確認（8/12）では、
**`language`（言い換え）だけが 0% で、`light` `table` `view` `add` は 100%** だった。
**言葉を読むのは VLM の側で、そこを完全に凍結していた。**

### 理由 3 — 視覚まで広げると 20 GB に入らない（実測）

③ を流したところ、**1 歩も進まずに落ちた**（8/12）。

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 14.00 MiB.
GPU 0 has a total capacity of 19.80 GiB of which 45.62 MiB is free.
Training: 0%| | 0/60000 [00:15<?, ?step/s]
```

## ④ が「言語を外したのにメモリが減らない」理由

**順番のせいである。** `smolvlm_with_expert.py` の `embed_image` で、視覚
エンコーダの出力は言語側のトークン列に差し込まれる。つまりこう流れる。

```mermaid
flowchart LR
    V["視覚エンコーダ<br/>12 層"] --> T["言語（VLM）<br/>16 層"]
    T --> E["action expert<br/>16 層"]
    E --> L["損失"]
```

**逆伝播はこの矢印を逆にたどる。** 視覚を学習の対象にすると、そこへ勾配を返す
ために**言語の 16 層を必ず通る。** だから言語を当て先から外しても、言語の
中間結果は持ち続けることになり、**メモリは減らない。**

逆に**視覚を外すと、逆伝播は言語の入り口で止まる。** 視覚エンコーダの中間結果を
丸ごと捨てられる。

| 候補 | 逆伝播が通る範囲 | 中間結果 |
|---|---|---|
| ① expert だけ | expert | いちばん少ない |
| **② ＋ 言語** | 言語 → expert | **言語ぶんだけ増える** |
| ④ ＋ 視覚（言語を外す） | **視覚 → 言語 → expert** | ③ と同じだけ要る |
| ③ ＋ 言語 ＋ 視覚 | 視覚 → 言語 → expert | 入らなかった |

**量の差も大きい。** バッチ 32 のときの見積もりを置く。

| | トークンの数 | 層 | 積 |
|---|---|---|---|
| 視覚（512×512 の画像を 2 台ぶん、1,024 ずつ） | 65,536 | 12 | 786,432 |
| 言語（差し込んだあと 178 と見積もり） | 5,696 | 16 | 91,136 |

**視覚は言語の 8.6 倍にあたる。** トークン数は見積もりだが、**実測が裏付けた。**

| | ② expert ＋ 言語 | ③ ＋ 視覚 |
|---|---|---|
| GPU メモリ | **9.1 GB**（ログの `mem_gb: 7.80`） | **19.8 GB を使い切って停止** |
| 1 歩あたり | **0.266 秒** | 1 歩も進まず |

**言語を足しても、①（0.254 秒）から 5% しか遅くならなかった。** 逆伝播が 16 層
増えても計算量がほとんど変わらないのは、言語側のトークンが少ないからである。
**重いのは視覚だ、という読みと合っている。**

> **視覚まで広げたいなら、バッチを 16 に落とせば入る見込みである。**
> ② がバッチ 32 で 9.1 GB なので、視覚ぶんの増分は 10 GB 強にあたる。
> 半分にすれば 20 GB に収まる計算になる。**ただし引く回数も半分になるので、
> 歩数を倍にしないと見るコマは増えない。**

## 採用した設定

```bash
python /workspace/train.py --run-name text_lora32_40k --peft-scope text \
    --lora-r 32 --lora-alpha 32 --steps 40000
```

| 決めたこと | 値 | なぜ |
|---|---|---|
| 当て先 | **② expert ＋ 言語** | 上の 3 つの理由 |
| rank | **32** | 文献の推奨が 16〜32。①（従来）は 16 だった |
| lora_alpha | **32** | **rank と同じにして倍率を 1.0 に保つ。** 従来も 16 / 16 だった |
| 歩数 | **40,000** | 1 コマを見る回数 0.29 → 0.57 回（[11](11_training_schedule.md) の 20,000 の 2 倍） |
| バッチ | **32**（据え置き） | 16 にすると引く回数が半分になり、**歩数を増やした意味が消える** |
| 数値の精度 | **fp32**（据え置き） | bf16 も検討したが、LeRobot の attention は計算を fp32 に上げ直すため**効きが読めない** |

**変えたのは当て先と歩数の 2 つだけである。**

## 回した結果（8/12）

**40,000 歩を終了コード 0 で走り切った。** 2 時間 54 分 12 秒。

| 見たもの | 結果 |
|---|---|
| 学習される重み | **3,123,712**（狙いどおり） |
| 学習率 | 1e-4 → **2.5e-6 まで落ちきった**（途中で止めていない） |
| **1 コマを見た回数** | **`epch:0.57`** —— 引く回数から計算した 0.57 回と**一致した** |
| 勾配の大きさ | 0.117 → **0.047**（7,000 歩で落ち着き、以降ほぼ平ら） |
| GPU メモリ | 7.80 GB のまま最後まで変わらず |
| 出力 | チェックポイント 81 個・2.8 GB |

**loss は動かなかった。** 0.094 で始まり、最後まで 0.092〜0.099 の間を往復している。

> **これは失敗の合図ではないが、成功の合図でもない。** 出発点の重みは
> **同じデータで既に学習済み**なので、loss は最初から下限近くにいる。
> 学習するのが 0.69% では、手本への近さがそれ以上詰まらないのは自然である。
>
> **だから今回の当て先が効いたかどうかは、loss では判定できない。**
> 評価にかけるまで分からない。4 回目の提出も loss は下がっていて、
> 本番スコアは 8.8 倍悪化した（[11](11_training_schedule.md)）。

### 畳み込んだあとの検算（8/12）

**当て先 69 に対し、動いたのは 68 だった。** 動かなかったのは
`vlm.model.text_model.layers.15.self_attn.q_proj` の 1 つだけである。

**言語側のいちばん最後の層の `q_proj` は、原理的に動かない。** 言語側は
「action expert へ渡す鍵と値」を作るために流れるので、各層の `key` と `value` は
保管されるが、**最後の層が出した状態そのものは捨てられる。**
`v_proj` は保管される値を作るので勾配が来るが、`q_proj` はその層の出力を作る
ためだけに要るので**勾配が 0 になる。** 65,536 個が余っているだけで、失敗ではない。

| 見たもの | 結果 |
|---|---|
| 変化したテンソル | **68 個**（対象と数えられる 63 ／ 対象外 5） |
| 対象外の 5 個 | `state_proj` など射影層。**名前に `q_proj` が入らないだけ**で正常 |
| いちばん大きい相対変化 | **0.388**（`lm_expert.layers.14.self_attn.q_proj`） |
| 参考・従来の回 | `lora20k` は **0.816**、`weak3x` は 0.165 |
| 当て先の外で動いたもの | **無し** |

**当て先を広げたのに変化が小さくなった** —— rank を 2 倍・歩数を 2 倍にしても
1 層あたりの動きは `lora20k` の半分以下である。**69 層に分散したぶん、
1 層が背負う量が減ったと読める。**

## 動き出したかを確かめる 2 行

```bash
docker logs <コンテナ名> 2>&1 | grep -E "num_learnable_params|OutOfMemory"
docker logs <コンテナ名> 2>&1 | grep "step:" | head -3
```

**`num_learnable_params=3123712` が出れば当て先が正しい。**
従来は `742656` だった。ここが 742656 のままなら指定が効いていない。

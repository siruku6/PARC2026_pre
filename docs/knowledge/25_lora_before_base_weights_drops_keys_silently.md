# 25. LoRA を当ててから重みを読むと、名前が変わって一致しない分が黙って消える

**2026-09-16、MolmoAct2 の LoRA 学習で `loss:nan grdn:nan` になった原因がこれだった**
（経緯は [reference/19](../reference/19_weights_catalog.md) 7.10 節）。

## 何が起きたか

学習の起動順は次のとおりだった。

1. `--policy.path` に渡した事前学習済みモデルの重みを読む
2. その後で PEFT の LoRA をモデルに当てる

**PEFT は LoRA を当てるときにパラメータ名を書き換える**
（`base_model.model.〜.lora_A` のような形が増える）。順序が上と逆——
**LoRA を先に当ててから重みを読む**——実装になっていたため、
safetensors に保存されている素の名前（書き換え前の名前）と、
いま模型が持っている名前（書き換え後の名前）が一致しなくなった。

**ここで止まってほしかったが、止まらなかった。**多くの重み読み込み実装は
「一致しないキーは読まずに黙って捨てる」動きをする（`strict=False` 相当）。
今回は 1,295 個の safetensors キーがまるごと不一致になり、**エラーも警告も出ないまま
本体の重みがランダム初期化のまま学習が始まった。**症状として出たのは 20 歩後の
`loss:nan` で、原因（読み込み失敗）とは離れた場所・離れた時点に出た。

## Claude 側

**「学習は起動した」「エラーは出ていない」を、重みが読めた証拠にしない。**
起動直後に、**読み込み前後でパラメータ名の集合を突き合わせ、一致した個数を
1 回ログに出す**（今回は「1,295 個中 1,295 個読めた」まで確認して初めて安心できた）。
黙って捨てる読み込みコードは、量が変わっても形は変えずに動くので、
**症状（nan・loss が下がらない）から遡っても実装のどこが悪いかは分からない。**
遡るのではなく、**読み込みの直後にその場で確かめる。**

## 人間側

**PEFT・LoRA・アダプタ全般に共通する順序の制約として覚える。**
「事前学習済み重みを読む→アダプタを当てる」が正しい順序で、
逆にすると一致しないパラメータが出る。**フレームワークが順序を強制してくれるとは限らない**
（今回使った LeRobot v0.6.0 はどちらの順でも書けてしまい、コード上は静かに動いた）。
新しいフレームワークで LoRA を組み込むときは、まずこの順序がどちらかを確認し、
確認できなければ読み込み直後にキーの一致数をログへ出す仕込みを先に入れる。

# 014. 学習データの raw states が時間反転に使えてかを、実データで確認する

> **状態: 依頼中** ／ 受け側: RTX6000（`eng003sasaki01`）のセッション ／ 更新: 2026-09-05

## 背景

PARC2026 本選。Track1 0.492／Track2 0.233／**Track3 0.000**（他参加者の最高は
0.09603 ＝ 8 本中 1 本ぶん）。締切は **9/17**。

Track3 は LIBERO の既存タスクの**逆順**（「A を B に置く」→「B から A に戻す」）で、
学習データに逆向きの型が 1 件も無いのが 0 点の主因と読めている。逆向きデータの
本命案は**時間反転**——順方向デモを後ろから前へ辿り直して逆向きデモにする
（[006_track3_reverse_direction.md](006_track3_reverse_direction.md)）。

時間反転は**デモの `observation.state`（ロボット状態）がフレーム単位で入っていること**
を前提にしている。これまでの確認は「学習コードが state 8 次元を宣言している」
（`solution/train/train_pi05.py:151-159` 周辺）と「`docs/reference/25` が
`observation.state` を float32・8 次元と記載している」までで、**実データが本当に
使えた形かまでは 1 度も見ていない**。これは本命案の正真正銘の前提なので、
次の学習に回す前に潰す。

## 何をしてほしいか

**学習データ 2 つのうち 1 つ以上**（下の「前提となる事実」参照）から 1 エピソードを
読み出し、**時間反転に使えるか go / no-go を表 1 つで報告**すること。

## なぜ要るか

- go（使える）→ 時間反転で 100 タスクぶんの逆向きデータを作れる。Track3 の本命が
  動き、次の長い学習の内容が決まる。
- no-go（使えない）→ 時間反転は「元デモを再収集して再生する」構成に作り直す必要が
  あり、日数が変わる。**9/17 の割り振りが変わる**。

## 前提となる事実

- 現在学習に使っているデータ: HF `lerobot/libero_plus`、
  revision `f3f49f426d75030177b18778374005bc12ccd588`、**LeRobot v3.0・fps 20**。
  （`solution/train/train_pi05.py:153-154`）
- 乗り換え候補 `libero_combined_20hz`（v3.0・19,533 エピソード・
  `libero_plus`＋`libero_90`＋`libero_10`＋spatial＋object）は
  **このマシンの `~/dataset/lerobot/` に読み出し専用で置かれている**
  （`docs/reference/25` 8 節）。転送は不要。
- `observation.state` は **8 次元** `[eef_pos(3), eef 軸角(3), gripper_qpos(2)]`。
  `action` は **7 次元** `[dx, dy, dz, droll, dpitch, dyaw, gripper]` で、
  **並進・回転は「前のフレームの姿勢からの差分」**、gripper は ±1 のバンバン。
  （`solution/policy_server.py` の action 定義・state 組み立て、`policy_server.py:583`
  付近のコメント）
- **重要な論点**: action が差分であるため、単純にフレーム順を逆にしただけでは
  「前の姿勢からのずれ」という意味が壊れる。だから時間反転の実行は
  **state 列から各フレームの絶対姿勢（eef_pos＋軸角）を取り出し、逆順で差分を
  作り直す**手順になる。**確認したいのは「state 列がその手順を支えられるか」**である。
- 時間反転後にデモを**再生して goal 条件を満たしたものだけ残す選別**は別途行う。
  今回はその選別は要らない（やること 5 は state 品質のチェックだけでよい）。

## やること

1. **対象エピソードの選択**: `libero_combined_20hz`（`~/dataset/lerobot/`）から
   **SCENE 名タスク（`KITCHEN_SCENE*` 等）の順方向デモ 2 本**を読む。
   1 本は「pick and place 系」、1 本は「引き出し・扉の開閉を含む系」を選ぶ。
   2 本目は「掴む以外の接触があるデモでも state 列は壊れないか」を見るため。
2. **`observation.state` 列の 4 チェック**（各 1 本分、表にする）:
   1. **8 次元で全フレーム入っている**か（欠損・ NaN が無い）。
   2. **eef_pos（先頭 3 次元）がフレームごとに変化**しているか（静的コピーでない）。
      最初の 50 フレームの min/max スパンを報告する。
   3. **gripper（末尾 2 次元）が 0 と 1（または ±1）の離散値で、少なくとも 2 回以上
      値を変化**させているか（開閉がデモに含まれる）。
   4. **state から再構築した絶対姿勢と action の差分が整合するか**——
      `eef_pos[t] − eef_pos[t-1]` が `action[t]` の先頭 3 次元と
      **1 mm 以内で一致するフレームの割合**を報告する（回転の 3 次元も
      同様に軸角の差分で比較して割合を出す）。一致率が 90% 未満なら
      no-go 候補になる（差分の定義が想定と違う可能性がある）。
3. **最終フレームの状態**を記録する（eef_pos・gripper の値だけ。
   「この値が逆向きデモの初期状態候補になる」という確認）。
4. 読み出しは LeRobot の API（`LeRobotDataset`、v3.0 対応）で行う。
   **動画をデコードする必要はない**（state 列は parquet にある）。
   画像列を触ると torchcodec が必要になるが、それまでは行かない。
5. 報告には**各チェックに出たコマンド（またはスクリプトの保存先）**を添える。

## できあがりの条件

- 上の 2 本ぶん分の **4 チェックの表**（1 行 1 チェック、数値付き）が出ること。
- **go / no-go の 1 行判断**（判定基準: チェック 1〜4 が全て通れば go。
  どれかでも通らなければ no-go で、通らなかったチェックの名前を添える）。

## やらなくてよいこと

- デモの再生・シミュレータでの選別（これは次の依頼で行う）
- 全エピソードのスキャン（2 本で十分。品質がエピソードで変わると疑う根拠は無い）
- `IPEC-COMMUNITY` の v2.1 系データセット（v3.0 の 2 つだけで十分）
- 画像・動画の内容の確認

## 報告の書き方

表（エピソード名・4 チェックの数値・最終フレームの状態）＋ go/no-go 1 行 ＋
使ったコマンド。説明は 5 行まで。

## 判断が必要になったら

この依頼は「時間反転を次の学習の本命にするかどうか」を変えるためのもの。
**より良い測り方を思いついたら変えてよい**（例: エピソード 2 本 → 5 本、
チェック項目の追加）。変えた場合は理由を報告に書いて。
no-go が出て「再収集が必要」という結論になったら、その構成（どこで何を再生して
何を残すか）を報告の末尾に 1 段落書いてほしい。

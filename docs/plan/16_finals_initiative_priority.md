## 2. なぜ「評価集合を直す」が 1 番なのか

**提出候補を選ぶのに使っている 36 行に、Track2 の摂動が 1 件も入っていない。**
`compe/val/EVAL_TASKS.csv` の `category` 列を数えた結果である。

| その 36 行の中身 | 本数 |
|---|---|
| Background Textures | 20 |
| Light Conditions | 16 |
| **Camera Viewpoints** | **0** |
| **Robot Initial States** | **0** |
| Objects Layout | 0 |
| Sensor Noise | 0 |

**この 2 カテゴリは Track1 の摂動である。** つまり **Track2 と Track3 の候補を、
Track1 の分布で選んでいる。** 3 番の拡張学習も 2 番の平均も、狙った効き目が
この 36 行には原理的に現れない。**「base を壊していないか」だけが見えて、
「摂動に強くなったか」は見えない。**

**作る集合の設計。**

| 決めごと | 値 | なぜ |
|---|---|---|
| カテゴリ | **Camera Viewpoints・Robot Initial States・Base** の 3 つ | 効き目の順が Robot +47.8% → Camera +16.6% で、Sensor +9.8% と Layout +6.1% は床（±6.5%）のすぐ上か内側（[reference/21](../reference/21_weakness_map.md) 1 節） |
| Camera の強さ | **方位角 45〜75°** を直接指定 | 15° は 0/8、30° は 1/8 しか崩れず、45〜75° で 13/24 が 300 歩に達する。**公式一覧の 44.6% は 15° 未満なので、一覧から選ぶと効かない行が集まる** |
| 1 行あたり | **3 エピソード** | 同じ行を 3 回回すと 24 行のうち 14 行で「300 歩に達したか」が割れる |
| 読む量 | **消費ステップ数** | 成功率は 36 件で 11.1 ポイント動く。ステップ数の合計は ±6.5% |
| 学習に使った変種 | **除く** | 入れると「見た条件を再現できたか」を測るだけになる。`--exclude` が既にある |

**作り終えた。`compe/val/TRACK2_VAL72.csv`（72 行）である。**
12 タスク × 6 条件で、GPU もコンテナも要らずに作れた（LIBERO-plus の実体は
`work/LIBERO-plus` にある）。

| 条件 | 変種名の作り | 本数 |
|---|---|---|
| Base | 接尾辞なし | 12 |
| Camera 方位角 +45° | `_view_45_0_100_0_0_initstate_0` | 12 |
| Camera 方位角 −60° | `_view_300_0_100_0_0_initstate_0`（300 = 360−60） | 12 |
| Robot 摂動量 0.1 | `_view_0_0_100_0_0_initstate_50` | 12 |
| Robot 摂動量 0.2 | `_view_0_0_100_0_0_initstate_150` | 12 |
| Robot 摂動量 0.4 | `_view_0_0_100_0_0_initstate_350` | 12 |

**12 タスクの選び方。** 8/24 の 240 ロールアウトで **Base が 3 回とも 300 歩未満だった
12 タスク**をそのまま使った（`0824_065521_probe16...` の `eval.log` を読み直して同じ 12 を
再現した）。これで [reference/21](../reference/21_weakness_map.md) 1 節の表と同じ土台に乗る。

**Robot の番号が摂動量になる根拠。** `libero/libero/envs/robots/new_init.py` が
1〜100 に 0.1、101〜200 に 0.2、301〜400 に 0.4 を掛けている（関節 7 軸の単位ベクトル×倍率）。
**だから 50・150・350 はそれぞれ 0.1・0.2・0.4 である。**

**一覧に無い組み合わせを自分で書いてよい。** 環境が存在を確かめるのは `_view_` より前の
`.bddl` だけで（[reference/20](../reference/20_track2_perturbation_categories.md) 2.3 節）、
**72 行すべてについて `.bddl` と `.pruned_init` が実在することを確かめた（欠け 0）。**

**この 1 本で F15（Robot の 0.3〜0.5）も同時に答えが出る。** 0.4 が入っているので、
0.1 → 0.2 → 0.4 の並びで飽和するかどうかが読める。

**回す口を作った。** 配布キットは `compe/t2/T2_TASKS.csv` の **8 行**を読むだけで、
行を選び直す口が無かった。`run_final_eval.sh` に **`TASKS_CSV`** を足し、
こちらの CSV をキットの CSV の上にマウントする形にした（採点器を差し替えているのと同じ
やり方）。**入力の一覧は実行ディレクトリへ `TASKS_CSV.csv` として写す。**

```
TASKS_CSV=compe/val/TRACK2_VAL72.csv TRACK_EPISODES=3 MUJOCO_GL=egl \
  PARC_N_ACTION_STEPS=16 PARC_EMA_ALPHA=0.3 LABEL=val72base \
  solution/tools/eval/run_final_eval.sh track2
```

**設定を `n 16・EMA 0.3` にする理由。** [reference/21](../reference/21_weakness_map.md)
1 節の表を出した 240 ロールアウトと同じ設定なので、**新しい 72 行の数値をあの表と
並べて読める。**（`track3` は CSV を持たない——`compe/t3` は `paths.py` と `assets` から
組む——ので `TASKS_CSV` を渡すと止まるようにした。）

**失うもの。** 1 候補あたりの評価時間が伸びる。

| どこで | 1 ロールアウト | 216 ロールアウト |
|---|---|---|
| **JAIST（このマシン）** | **54.5 秒**（8/24 の 240 件を 3 時間 38 分で回した実測） | **約 3.3 時間** |
| **RTX6000（EGL）** | **30.6 秒**（[howto/12](../howto/12_bring_eval_to_rtx6000.md) の実測） | **約 1.8 時間** |

**いまの 36 行 1 エピソード（約 20 分）の 5 倍以上になる。**
**RTX6000 で回す前提でしか成り立たない。**

## 3. なぜ「重みの平均」が 2 番なのか

**GPU 学習が要らないのに、実測がそのまま根拠になっている唯一の施策である。**

**8/27 の 24,000 歩で分かったこと。** loss は 0.203 で、6,000 歩からの改善は
-1.0〜-3.3%。一方で重みは行動側で 0.4〜3.4% 動き、凍結側は 0.000000 だった。
**24,000 歩でもデータの 17% しか見ていない**（ログの `epch:0.17`）。
つまり**データを使い切って止まったのではなく、平らな谷の底を横に動いている。**

**平らな谷を横に動いている重みは、平均すると谷の中心に寄る。** これが重み平均
（複数のチェックポイントを足して割る）が効く条件そのものである。

**道具は書いて、動くことも正しいことも確かめた**
（`solution/tools/weights/average_checkpoints.py`）。ホストに torch が無いので
numpy だけで safetensors を直接読み書きする。**8/27 深夜に 012000 と 018000 で実測した値。**

| 測ったこと | 値 |
|---|---|
| テンソルの数 | **813 個で 3 つとも完全に一致**（F32 が 558・BF16 が 255） |
| **動いたテンソル** | **208 個だけ。全部 `gemma_expert`（行動側）の中にある** |
| **動いたバイト** | **1,097,539,712（本体 9.35 GB の 11.7%）。残り 88.3% はバイト列をそのまま写す** |
| かかった時間 | **21 秒**（9.35 GB を書き出して） |
| 正しさの確かめ方 | 12 個を別に計算し直して突き合わせた。**誤差は BF16 で 2.0e-05・F32 で 5.2e-08** ——どちらもその形式の刻み幅そのもの |
| 凍結側 | **20 個を抜き出して 1 ビットも違わないことを確かめた** |

**`train_expert_only=true` で凍結側はビット単位で同じなので、平均は行動側だけを動かす。**
これは推測ではなく、上の「動いたテンソル 208 個が全部 `gemma_expert`」が示している。

**3 通り作って、有望な 2 つを評価する。**

| 案 | 中身 | 狙い |
|---|---|---|
| **末尾平均** | 018000 と 024000 | 直近の揺れだけを打ち消す。**いちばん素直** |
| **全平均** | 006000・012000・018000・024000 | 谷の中心へ最も寄る。**古い重みを混ぜる副作用がある** |
| **α 縮小** | rp3000 と 024000 を 1:1 | **学習で動いた分を半分にする。**動いた分が雑音なら、これがいちばん効く |

**失うもの。** ディスク。1 本 9.35 GB で、いま空きが 54 GB。**3 本作ると 26 GB 減る。**
提出用の zip も 9.4 GB 要るので、**作る前に 006000〜018000 のうち使わないものを消す判断が要る。**

## 4. 学習データを作る話は今どこにいるか

**ユーザの言う「学習用の動画を作る」「モノやロボットの配置を変える」は、
片方が既に答えの出ている問いである。**

| 軸 | 歩数の増え方 | 判定 |
|---|---|---|
| **ロボットの初期姿勢** | **+47.8%**（6/12 を壊した・p = 0.0005） | **最悪。ここに投資する** |
| **カメラ視点** | **+16.6%**（p = 0.039） | 2 番目。**45° 以上だけ** |
| センサ雑音 | +9.8% | 床（±6.5%）のすぐ上。**投資しない** |
| **物の配置** | **+6.1%**（p = 0.388） | **床の内側。差があると言えない。投資しない** |

**「モノの配置を変える」は、やらなくてよいと既に測れている。** 妨害物を 3 個から
10 個に増やしても歩数は -5.0%、つまり増えない。**「ロボットの配置」は逆に最優先である。**

**費用が桁違いに違う。**

| | 何をするか | 行動列 | 費用 |
|---|---|---|---|
| **Tier1（カメラ）** | 既にある行動列を別の視点で**描き直す**だけ | **そのまま使える** | CPU 数時間 |
| **Tier2（初期姿勢）** | 初期姿勢が変わると行動列が使えないので**台本から撮り直す** | **作り直し** | 336 回の撮影・数日 |

**Tier2 は効き目が 1 位だが、閉ループの台本があるタスクが 16 のうち 2 つ
（SCENE3・SCENE8）しか無い**（`scripted_demo.TASK_PLANS`）。**14 タスクぶんは撮れない。**
だから本選 1 の期間では Tier1 を先に済ませる。

**Tier1 には既に 2 通りある。** 3 番の RunPod 学習が使う `--camera-viewpoint-augment` は
**画像を 2 次元的に歪ませる近似**で、実装済み・CPU で動作確認済み（[plan/11](11_tier1_camera_augmentation.md) 3 節）。
**本物の撮り直し（3 次元で視点を動かして描画）は別物で、まだやっていない。**
**近似で足りるかどうかは 3 番の結果で分かるので、6 番はその後でよい。**

## 5. 幾何を学習したモデルを接ぐ話

**やりたいことは筋が通っている。** 崩れる 2 つの軸（初期姿勢・カメラ視点）は
**どちらも幾何の問題**であり、RGB だけを見る SigLIP の特徴は視点と絡み合っている。
**外から幾何を学習した表現（単眼深度・3 次元特徴）を持ち込めば、視点が変わっても
同じ表現になる**——これが狙いである。

**本選 1 に入らない理由は 3 つある。**

| | 中身 |
|---|---|
| **推論で使えるのは RGB 2 枚だけ** | 採点環境から届くのは `front` と `wrist` の画像 2 枚のみ（[reference/10](../reference/10_observation_interface.md)）。**深度は与えられないので、RGB から推定するモデルを内側に持つことになる** |
| **接ぎ目を学習しないと動かない** | 特徴を足すだけでは方策が読めない。融合の層を学習する必要があり、**行動側だけの学習では届かない**（凍結側が 0.000000 しか動かないことを実測済み） |
| **1 回のレンタルで収束するか分からない** | 3 番のフルパラメータ学習が 13 時間で 4,500 歩である。**新しい入力の意味を覚えるのはそれより重い** |

**やるなら本選 2 以降の土台として、順序はこうなる。**
①深度推定を挟んで推論の時間が 10 秒／要求に収まるかを測る → ②融合の層だけを学習して
base を壊さないことを確かめる → ③摂動集合で測る。**①は GPU が 30 分あれば測れるので、
本選 1 の合間に入れる価値はある**（板 F18 はこの①だけを指す）。

## 6. 撤回した判断

| 私の主張 | 実際 | なぜ間違えたか |
|---|---|---|
| 並進の倍率を 1.15 に上げれば歩数が減る | Track1 0.370 → 0.136、歩数は 1,039 → 1,398 に**増えた** | 分布が上限に届いていないことだけを見て、行き過ぎて戻る動きが増える分を数えなかった |
| 行動側だけの追加学習でまだ伸びる | 6,000 歩でも 24,000 歩でも loss は -1.0〜-3.3% | 学習量が足りないのだと読んだが、凍結された画像側が上限を決めていた |
| Track2 の摂動は配布キットの `PerturbationConfig` 由来 | `T2_TASKS.csv` は LIBERO-plus のタスク変種だった | 配布物の中身を数える前に推論した |
| Robot Initial States は 3 番目に悪い | **1 番悪い**（+17.5% → +47.8%） | 「両側が完走した組」で読み、**Base が速いタスクを摂動が壊した組**を除いてしまった |

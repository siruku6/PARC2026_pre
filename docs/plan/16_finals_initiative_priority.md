## 2. なぜ「点の作り方」が 1 番なのか（**8/28 に作った**）

**`solution/tools/eval/score_composite.py` として作った。**
成功 0.70・歩数 0.12・ジャーク 0.08・滑らかさ 0.06・経路長 0.04 の重みで、
補助の 4 指標は `ref / (ref + x)` で 0〜1 に写す（基準値のとき 0.5）。
**過去の実行にもそのまま当てられる**——8/26 の 3 本を回し直して確かめた。

**効き目は「同点をほどけること」だった。**成功率では 0.806 で並ぶ 3 条件が、
合計点では 0.716 / 0.715 / 0.713 に分かれる。**8 本や 12 行では成功率が粗すぎて
順位が付かない**——そこが埋まる。


### 2.1 `0.370` は `3/8` ではない

**本選の 7 本の採点ログすべてで、走ったエピソードは 8 本である。**
評価パイプラインは 1 エピソードの開始ごとに `POST /reset` を 1 回投げるので、その回数が本数である。

**点は [../reference/19_weights_catalog.md](../reference/19_weights_catalog.md) の
「本選の提出と点」にあり、ここには載せない。**

| 提出 | `/reset` | `/act` |
|---|---|---|
| Track1 4.2.0 | **8** | 1,039 |
| Track1 4.3.0 | **8** | 1,416 |
| Track1 4.5.0 | **8** | 1,398 |
| Track2 4.2.0 | **8** | 1,723 |
| Track2 4.3.0 | **8** | 1,368 |
| Track2 4.5.0 | **8** | 1,677 |
| Track3 4.2.0 | **8** | **2,400** |

**8 本の成功率なら、出る値は必ず 0.125 の倍数になる。**
`3/8` は `0.375`、`2/8` は `0.250`、`1/8` は `0.125` である。
**返ってきた 6 つはどれも 0.125 の倍数でない。** つまり採点側の総合スコアには
**成功率のほかに連続値の項が入っている。**

**一方、手元の総合スコアは 0.125 の倍数になる。** 8/27 の Track2 の 8 行の実行は
`overall_score` が **0.375**、`mean_success_rate` も 0.375 で、ちょうど `3/8` である。
配布された `pipeline/scorer.py:124` が `overall_score = float(overall_success)` と
書いているからで、**ジャーク・衝突率・SPARC・経路長は報告されるだけで点に入らない。**

**これは母集団の問題ではない。** F13 で行を入れ替えても、計算している関数が違うままである。

### 2.2 直す道は配布物の中にある

`pipeline/total_score.py:14-20` の内蔵既定がこれである。

```python
_BUILTIN_TOTAL_SCORE_DEFAULT = {
    "control_dt": 0.05,
    "use_total_score_as_overall": False,
    "weights": {},
    "collision": {"enabled": True, "threshold_m": 0.001},
}
```

**`weights` を書いて `use_total_score_as_overall` を立てれば、重み付きの合計点が
総合スコアになる道が開く。** 採点側は `total_score_config.json` と
`normalization_config.json` を秘匿ファイルとして持ち込む（`evaluate.py:33-41` の
`_EVAL_SECRET_PATHS`）。**中身は分からないが、器はこちらにもある。**

**重みが分からなくても意味がある。** 成功率だけの点と、歩数・ジャーク・衝突を含む点は、
**候補の順位が変わる。** 採点側が後者なら、前者で選ぶのは間違った順位で選ぶことである。

### 2.3 GPU を使わずにできる

**手元の結果 JSON は、タスクごとの指標を既に持っている。** 8/27 の実行の
`results/server_8000.json` に入っていた項目である。

| 持っている | 項目 |
|---|---|
| タスクごと | `success_rate`・`cartesian_path_length`・`joint_path_length`・`orientation_path_length`・`avg_cartesian_jerk`・`rms_cartesian_jerk`・`avg_joint_jerk`・`rms_joint_jerk`・`avg_episode_time_sec` |
| 全体 | 上の平均 ＋ `mean_avg_steps_to_success`・`min/max_success_rate`・`n_tasks`・`n_total_episodes` |
| **差し替えた採点器で足したもの** | **`collision_rate`・`sparc`** |

**だから過去の実行を計算し直せる。** 新しい `total_score_config.json` を書いて、
**既に手元にある JSON に当て直すだけで、過去の候補すべてに新しい点が付く。**
評価を回し直す必要が無い。

### 2.4 確認したい仮定

| 仮定 | 外れたら何が変わるか |
|---|---|
| 採点側の重みは、こちらが選ぶどの重みでも順位の向きが同じになる程度に素直である | 順位が重みに敏感なら、手元の点は「成功率だけ」より良くはなるが代わりにはならない。**そのときは 5 番（自動化）の価値も下がる** |

**「衝突は門である」は仮定ではなくなった。**`pipeline/rollout.py:233-234` にこう書いてある。

```python
collided = any(d > collision_threshold for d in object_max_disp.values())
success = bool(done) and not collided
```

**しきい値は 1 mm**（`total_score.py` の `{"enabled": True, "threshold_m": 0.001}`）で、
対象は **`obj_of_interest` に入っていない、ロボット以外のすべての物体**である
（`rollout.py:170-178`）。**操作対象でない物が 1 mm でも動いたら、ゴールに着いていても失敗になる。**
配布版のコメントも「成功判定に効くため、ローカル評価を本番と一致させる」と書いている。

**採点側の 8 本という本数が、突き合わせの限界を決めている。**
Track1 の 4.2.0 と 4.3.0（`infer` 20）の差は 0.065 で、**8 本のうち 1 本ひっくり返ると
成功率の項は 0.125 動く。** つまり **この 2 つは区別できない。** 突き合わせに使えるのは
**倍率 1.15（4.5.0）の下がり方だけ**で、これは歩数が 1,039 → 1,398 に増えたことでも裏が取れる。

## 3. なぜ「評価する行の母集団」が 2 番なのか

**提出候補を選ぶのに使っている 36 行に、Track2 の摂動が 1 件も入っていない。**
`compe/val/EVAL_TASKS.csv` の `category` 列を数えた結果である。

| その 36 行の中身 | 本数 |
|---|---|
| Background Textures | 20 |
| Light Conditions | 16 |
| **Camera Viewpoints** | **0** |
| **Robot Initial States** | **0** |
| Objects Layout | 0 |
| Sensor Noise | 0 |

**この 2 カテゴリは Track1 の摂動である。** つまり **Track2 と Track3 の候補を、
Track1 の分布で選んでいる。**

**作り終えた。`compe/val/TRACK2_VAL72.csv`（72 行）である。**
12 タスク × 6 条件で、GPU もコンテナも要らずに作れた。

| 条件 | variant 名の作り | 本数 |
|---|---|---|
| Base | 接尾辞なし | 12 |
| Camera 方位角 +45° | `_view_45_0_100_0_0_initstate_0` | 12 |
| Camera 方位角 −60° | `_view_300_0_100_0_0_initstate_0`（300 = 360−60） | 12 |
| Robot 摂動量 0.1 | `_view_0_0_100_0_0_initstate_50` | 12 |
| Robot 摂動量 0.2 | `_view_0_0_100_0_0_initstate_150` | 12 |
| Robot 摂動量 0.4 | `_view_0_0_100_0_0_initstate_350` | 12 |

**12 タスクの選び方。** 8/24 の 240 ロールアウトで **Base が 3 回とも 300 歩未満だった
12 タスク**をそのまま使った（生ログを読み直して同じ 12 を再現した）。
これで [reference/21](../reference/21_weakness_map.md) 1 節の表と同じ土台に乗る。

**カテゴリの選び方。** 生ログから 4 カテゴリの歩数比を計算し直した（reference/21 と一致）。

| 軸 | 歩数比 | 壊した | 判定 |
|---|---|---|---|
| **ロボットの初期姿勢** | **+47.8%** | 6/12 | **入れる** |
| カメラ視点 | +16.6% | 2/12 | **入れる（45° 以上だけ）** |
| センサ雑音 | +9.8% | 2/12 | 入れない |
| **物の配置** | **+6.1%**（p = 0.388） | 1/12 | **床（±6.5%）の内側。入れない** |

**Robot の番号が摂動量になる根拠。** `libero/libero/envs/robots/new_init.py` が
1〜100 に 0.1、101〜200 に 0.2、201〜300 に 0.3、301〜400 に 0.4、401〜500 に 0.5 を
掛けている（関節 7 軸の単位ベクトル×倍率）。**だから 50・150・350 は 0.1・0.2・0.4 である。**

**一覧に無い組み合わせを自分で書いてよい。** 環境が存在を確かめるのは `_view_` より前の
`.bddl` だけで（[reference/20](../reference/20_track2_perturbation_categories.md) 2.3 節）、
**72 行すべてについて `.bddl` と `.pruned_init` の実在を確かめた（欠け 0）。**

**回す口を作った。** 配布キットは `compe/t2/T2_TASKS.csv` の **8 行**を読むだけで、
行を選び直す口が無かった。`run_final_eval.sh` に **`TASKS_CSV`** を足し、
こちらの CSV をキットの CSV の上にマウントする形にした。

```
TASKS_CSV=compe/val/TRACK2_VAL72.csv TRACK_EPISODES=3 MUJOCO_GL=egl \
  PARC_N_ACTION_STEPS=16 PARC_EMA_ALPHA=0.3 LABEL=val72base \
  solution/tools/eval/run_final_eval.sh track2
```

**費用。**

| どこで | 1 ロールアウト | 216 ロールアウト |
|---|---|---|
| **JAIST（このマシン）** | **54.5 秒**（8/24 の 240 件を 3 時間 38 分で回した実測） | 約 3.3 時間 |
| **RTX6000（EGL）** | **30.6 秒**（8/26 の実測。[howto/03](../howto/03_gpu_eval.md) の「会社の RTX6000 では EGL が効く」） | **約 1.8 時間** |

### 3.1 回した結果（8/28・216 本・64 分）

**合計点 0.6523・成功率 0.7222・衝突率 0.2269。**

| 条件 | 合計点 | 成功 | 衝突率 | 所要時間の Base 比 |
|---|---|---|---|---|
| **Base** | **0.716** | 0.806 | **0.167** | — |
| Robot 摂動量 0.1 | 0.715 | 0.806 | 0.167 | **−4.1%** |
| Robot 摂動量 0.4 | 0.713 | 0.806 | 0.167 | **+3.6%** |
| Robot 摂動量 0.2 | 0.636 | 0.694 | 0.278 | **+6.9%** |
| **Camera 方位角 −60°** | **0.569** | 0.611 | **0.306** | **+14.2%** |
| **Camera 方位角 +45°** | **0.565** | 0.611 | **0.278** | **+25.4%** |

**いちばん大きいのは、摂動の話ではなかった。**

| 条件 | 失敗 | うち衝突 | 割合 |
|---|---|---|---|
| Base | 0.194 | 0.167 | **86%** |
| Camera +45 | 0.389 | 0.278 | 71% |
| Camera −60 | 0.389 | 0.306 | 79% |
| Robot 0.2 | 0.306 | 0.278 | **91%** |
| **全体** | **0.278** | **0.227** | **82%** |

**摂動を 1 つも掛けていない Base ですら 16.7% が衝突で落ちている。**
**これは学習でしか直らない類の失敗ではない**（4.3 節）。

### 3.2 変位を測ったら、衝突の読みが変わった（8/28 夕方）

**「失敗の 82% が衝突」は数え方が甘かった。** 衝突した 49 本を
**ゴールに着いたかどうか（`done`）で分けると、2 種類ある。**

| | 本数 | 意味 |
|---|---|---|
| **着いたのに衝突で落ちた** | **36** | **衝突対策で取り戻せる点はここだけ** |
| 300 歩で着いていない | 13 | 衝突が無くても失敗。300 歩暴れた末の変位 |

**216 本の失敗 60 本のうち、衝突だけが原因なのは 36 本で 60% である**（82% ではない）。
**それでも 36 本は成功率で 16.7 ポイントに当たる。**

**取り戻せる 36 本は「かすった」寄りである**（実距離 L2）。

| | 値 |
|---|---|
| 中央値 | **4.44 mm** |
| 5 mm 未満 | **20 / 36** |
| 10 mm 未満 | 26 / 36 |
| **50 mm 以上** | **0 本** |
| 最大 | 35.0 mm |

**裾の数十 cm は打ち切りの 13 本に集まっている**——そちらは衝突が無くても失敗である。

**しかも 1 物体に集まっている。**

| | 中身 |
|---|---|
| **`cookies_1`** | **取り戻せる 36 本のうち 20 本** |
| クッキー箱の 2 タスク | 衝突 49 本のうち 22 本 |
| **同じ 2 タスクで通せている回** | **18 本のうち 8 本は `cookies_1` を 1 mm 未満に収めている**（中央値 1.14 mm） |

**同じ物理で通せる回があるので、これは避けようのない衝突ではなく制御の精度の問題である。**

**判定に使われている距離は L1（3 軸の絶対値の和）である**
（`rollout.py:212` の `np.sum(np.abs(cur - p0))`）。**実距離より最大 √3 倍大きく出るので、
しきい値 1 mm は実距離では 1 mm より厳しい。**

**カメラは効く。ロボットの初期姿勢は効かなかった。** 後者は
[reference/21](../reference/21_weakness_map.md) の **+47.8%** と食い違う。

| 食い違いの読み | 中身 |
|---|---|
| **こちらの設計の穴** | **1 段階につき姿勢を 1 つしか見ていない**（番号 50・150・350 に固定）。8/24 は 12 タスクに 12 通りの姿勢が当たっていた。**摂動は「単位ベクトル×倍率」なので、番号が違えば向きが違う**——優しい向きを 3 つ引いた可能性がある |
| キットの違い | 8/24 は予選の eval-kit、8/28 は本選キットである |

**摂動は効いている**（72 行すべてで Base と経路長が違い、完全一致は 0 件だった）。
**効いていないのではなく、この 3 つの姿勢では崩れなかった、が正しい。**
**学習データの設計をこの数字で決めてはいけない。**

**Track1 と Track3 の集合も同じ作りで要る**（F13 の続き）。Track1 は背景・照明で、
**手元の 36 行が 0.713 を出したのに本番が 0.141 だった**——母集団か点の作り方か、
その両方かが違う。**2 節を先に済ませれば、どちらの寄与かを切り分けられる。**

## 4. トラックごとの対策を 1 つずつ

**3 トラックは失敗の型が違うので、対策も別である。**「1 つの改善で 3 つ上がる」ものは
すでに使い切っている（指示文の正規化・倍率・推論の刻み）。

### 4.1 Track3 —— 目標条件は関係節を見ていない

**Track3 は 0.000 で、`/act` が 2,400 回 = 8 × 300 である。**
評価側はゴールに着いた時点でループを抜けるので（`rollout.py` の `if done: break`）、
**割り切れているということは 8 本とも 1 度もゴールに着いていない。**

**他の 2 トラックと比べると、これがどれだけ異常かが分かる。**

| トラック | `/act` ÷ 8 | 読み |
|---|---|---|
| **Track1 4.2.0** | **130 歩** | 打ち切り 300 のはるか手前で抜けている。**ゴールには着いている** |
| Track2 4.2.0 | 215 歩 | 半分くらいは着いている |
| **Track3 4.2.0** | **300.0 歩** | **1 本も着いていない** |

**だから Track3 は「着いたのに衝突で失格」ではない。着けていない。**

**配布された 4 つの example タスクの bddl を読んだ。** 指示文は長く、置き場所を
他の物との関係で言う。**ところが採点される目標条件は、名前の付いた領域 1 つに載せることだけである。**

| タスク | 指示文の言い方 | **目標条件（`:goal`）** |
|---|---|---|
| alphabet soup | 「トレイから出して、**ケチャップの手前の**テーブルに置く」 | `(On alphabet_soup_1 living_room_table_alphabet_soup_init_region)` |
| red mug | 「左の皿から下ろして、**他の 2 つのマグの後ろの**テーブルに戻す」 | `(On red_coffee_mug_1 living_room_table_red_coffee_mug_init_region)` |
| two mugs | 「白を**赤いマグの左に**、黄白を**赤いマグの右に**」 | `(On porcelain_mug_1 ...) (On white_yellow_mug_1 ...)` の 2 つ |
| yellow book | 「棚の上から下ろして、**左側の**テーブルに戻す」 | `(On yellow_book_2 study_table_yellow_book_left_init_region)` |

**「ケチャップの手前」「他の 2 つのマグの後ろ」は採点されていない。**
目標の領域は bddl の中で座標で定義されており、alphabet soup の場合は
`(:ranges ((-0.2 -0.25 0.0 -0.05)))` ——**テーブル上の 20 cm × 25 cm の矩形**である。

**だから対策は「指示文を目標条件だけに削る」である。**
「take the alphabet soup out of the tray and place it on the table in front of the ketchup」
→「put the alphabet soup on the table」。**学習は要らない。推論側だけで済む。**

| 良くなること | 失うこと | 外れたとき |
|---|---|---|
| 学習データに無い長い関係節を、学習データにある短い形へ寄せられる。**0.000 からなので下げようがない** | 削りすぎると、どの物を動かすかが消える恐れがある（two mugs は 2 つ動かすので削れない） | **削っても 300 歩で打ち切られ続ける。**そのときは原因が言葉ではなく、見たことのない物・棚・トレイという配置そのものになる——**それが分かること自体が次の的になる** |

**ただし「着けた」あとに 1 mm の門がある。** 4 つとも**別の物と接している物を外す**
課題である——トレイの中・皿の上・皿の上・棚の上。alphabet soup の場合、
操作対象は `alphabet_soup_1` だけなので、**`wooden_tray_1`・`ketchup_1`・`cream_cheese_1`・
`tomato_sauce_1`・`butter_1` はすべて衝突の監視対象**で、**トレイを 1 mm 動かした時点で
その回は失敗になる。**

**つまり Track3 の対策は 2 段になる。** ①指示文を削って、まずゴールに着かせる →
②着いた回が 1 mm の門を通るかを見る。**①が通らないうちは②を作る意味が無いので、
F20 は①だけを指す。**

**確かめたい仮定。** 本番の Track3 はこの 4 つと同じではない
（`compe/t3/README.md`「本番評価は非公開タスクを含む別のタスクセットで実施される」）。
**関係節が飾りであることが 4 つとも成り立っているので同じ作りだと読んだが、
本番の目標条件は見られない。**

## 7. 幾何を学習したモデルを接ぐ話

**8/28 に格下げを取り消した。**前の版はこれを最下位（本選 2 以降）に置いていたが、
**そこに書いた 3 つの理由のうち 2 つが成り立たない。**

### 7.1 何をする作業か —— 写すのは Evo-0 であって GeoAware-VLA ではない

**+35 ポイントの出どころは GeoAware-VLA（arXiv 2509.14117）だが、その形はこちらでは採れない。**
論文を読むと、**視覚エンコーダを VGGT で丸ごと置き換えており**、土台も π0 系ではなく
**BAKU** という小さな方策である。**π0.5 の値打ちは事前学習された VLM そのものなので、
エンコーダを外すと土台が消える。**

**採れるのは Evo-0（arXiv 2507.00416）の形である。こちらは π0 の上に作られている。**

| | GeoAware-VLA | **Evo-0（写す方）** |
|---|---|---|
| 土台 | BAKU（小さな方策） | **π0** |
| 視覚エンコーダ | **VGGT で置き換える** | **元のまま残し、VGGT を横に足す** |
| つなぎ方 | 中間 4 層を 1 次元畳み込みで写す | **交差注意 1 層。**2D のトークンが質問側、VGGT の**最終層**のトークンが答え側 |
| 学習するもの | 投影層だけ | **つなぎの層 ＋ LoRA ＋ 行動側**（π0 本体は凍結） |
| 報告値 | LIBERO の未知視点で **+35 ポイント** | RLBench 5 課題 41% → **56%**、実機 5 課題 28.5% → **57.4%** |
| 推論の重さ | 記載なし | **RTX 4090 で 11.3 Hz → 6.94 Hz**（1 回あたり 88.5 ms → 144 ms。**VGGT のぶんが約 56 ms**） |

**Evo-0 が学習するもの（つなぎの層・LoRA・行動側）は、こちらが既に回している範囲と同じである。**
`--train-expert-only` と LoRA の当て先は用意がある（[reference/12](../reference/12_lora_targets.md)）。

**カメラの角度が変わると「見た目のパターン」は崩れるが、「物が立体としてどこにあるか」は
変わらない。**それが効く理屈である。

### 7.2 前の版の 3 つの理由のうち、2 つが成り立たない

| 前の版の理由 | 実際 |
|---|---|
| 推論で使えるのは RGB 2 枚だけで、**深度は与えられない** | **成り立たない。**この手は**深度センサを使わない。**RGB 画像を幾何のモデルに通して特徴を得る手である（14.11 節「深度センサもカメラの校正も要らない」）。**深度が来ないことは、この手を止める理由にならない** |
| 接ぎ目を学習しないと動かない。**行動側だけの学習では届かない**（凍結側が 0.000000 しか動かない） | **すり替わっていた。**「凍結側が動かない」は**凍結した画像側の重みが更新されない**という当たり前の観測で、**新しく足した変換層が学べるかとは無関係である。**行動側だけの学習が打ち止めなのは「同じ入力で歩数を増やしても伸びない」からであって、**入力に新しい情報を足す話は別である** |
| 1 回のレンタルで収束するか分からない（F2 は 13 時間で 4,500 学習ステップ） | **成り立たない。**学習するのは変換層 1 枚だけで、フルパラメータ学習ではない。**手元の H100-20C（20 GB）や RTX6000 で回せる。**RunPod も Blackwell も要らない |

### 7.3 10 秒に収まることを測った（2026-08-28・`open_items.md` の F18 は済み）

**収まる。余裕は 105 倍あった。**

`facebook/VGGT-1B` を手元の H100-20C に読み込み、`front` と `wrist` に見立てた 2 枚を
1 回通す時間を測った（3 回の暖機のあと 20 回）。道具は
[measure_vggt_latency.py](../../solution/tools/analysis/measure_vggt_latency.py)。

| 画像の大きさ | 測った範囲 | 中央値 | 最大 | GPU のピーク |
|---|---|---|---|---|
| 252×252 | **aggregator のみ（Evo-0 が使う分）** | **63 ms** | 63 ms | 4.76 GB |
| 252×252 | forward 全体（上限） | 117 ms | 119 ms | 4.91 GB |

**Evo-0 が使うのは aggregator の最終層のトークンだけ**なので、深度・点群・カメラ姿勢の

**余裕の勘定。**

| | 値 | 出典 |
|---|---|---|

| **何倍まで遅くなってよいか** | **105 倍以上** | 7.6 秒 ÷ 72 ms |

| 他の上限 | 値 | 見込み |
|---|---|---|
| 起動 1200 秒 | 重みの読み込み **10.2 秒**（実測） | 問題にならない |
| 提出 zip 20 GB | 重み **4.69 GB**（float32。bf16 なら約 2.4 GB） | 収まる |
| 採点環境の VRAM | **L4 24 GB**。π0.5 が約 10 GB ＋ VGGT が 4.9 GB | 収まる |

### 7.4 どのモデルを選ぶか

**両論文とも VGGT（Visual Geometry Grounded Transformer・CVPR 2025）である。**
10 億パラメータで、1 枚から数百枚の画像を入れるとカメラの姿勢・奥行き・点群・点の追跡を
まとめて出すよう学習されている。**Evo-0 が使うのはその最終層のトークンだけである。**

| 候補 | 大きさ | 利用条件 | VLA での裏づけ | 実装の手間 |
|---|---|---|---|---|
| **`facebook/VGGT-1B-Commercial`（推奨）** | 10 億 | **商用可（軍事を除く）。**HF で連絡先に同意するだけの門がある | **Evo-0（π0）と GeoAware-VLA の両方がこれ** | `facebookresearch/vggt` を同梱する（transformers 5.5.4 には入っていない） |
| `facebook/VGGT-1B` | 同じ | **CC-BY-NC-4.0（非商用）** | 同上 | 同上 |
| `Ruicheng/moge-2-vitl`（MoGe-2） | 3 億級 | **MIT** | **無し** | 同上（transformers に無い） |
| Depth Anything V2 Small | 2,480 万 | **Apache-2.0** | **無し** | **不要。**transformers 5.5.4 に `DepthAnythingForDepthEstimation` がある |

**`VGGT-1B` と `VGGT-1B-Commercial` は同じ重み・同じ構造で、違うのは利用条件だけである。**
**同意の門はユーザの HF アカウントでしか通せない。**

**推奨は `VGGT-1B-Commercial`。**論文が確かめたのと同じ重みで、利用条件が明確である。
**下の 2 つは「VGGT が重すぎた場合の逃げ道」であって、代わりにはならない**
——どちらも VLA に足した報告値が無い。

### 7.5 実装した中身（`open_items.md` の F25・2026-08-28）

**`--geometry-fuse vggt` を付けると接がるようにした。**付けなければ今までと同じである。

```
python train_pi05.py --run-name <名前> --geometry-fuse vggt --batch-size 16 --steps <歩数>
```

| ファイル | 役割 |
|---|---|
| [experiments/geometry/vggt_fuser.py](../../solution/train/experiments/geometry/vggt_fuser.py) | 接ぎ木の本体。凍結した VGGT ＋ 交差注意 1 層 |
| [experiments/geometry/__init__.py](../../solution/train/experiments/geometry/__init__.py) | train_pi05.py 側の窓口（`experiments/quantization` と同じ 7 つの関数） |
| [experiments/geometry/lerobot_train_with_geometry.py](../../solution/train/experiments/geometry/lerobot_train_with_geometry.py) | 接ぎ木を import してから `lerobot-train` の `main()` を呼ぶラッパー |

**学習するのは 20,989,953 個（11 層）だけである**——`fusion_gate`・`to_policy_dim`・
`norm_query`・`norm_key`・`cross_attention`。**VGGT はチェックポイントに保存しない**
（保存すると 1 つあたり 4.69 GB 太る。公開の重みなので読み込み時に取り直せばよい）。

**学習の始まりで base を壊さない細工を入れた。** 混ぜる量の係数 `fusion_gate` を
**0 で初期化**してあるので、**学習ステップ 0 の出力は素の π0.5 と一致する**
（`x + 0 × 交差注意 = x`）。壊れるとすればそれは学習が進んだ結果であって、
接いだこと自体ではない。

### 7.5.1 接ぐ前と後を同じ日・同じ機械で測った（20 歩・batch 8）

**変えたのは `--geometry-fuse vggt` を付けたかどうかだけである。**

| | 接がない | **接ぐ** | 差 |
|---|---|---|---|
| 1 学習ステップ | 0.841 秒 | **1.196 秒** | **+42%** |
| 1 秒あたりのサンプル | 9 | 6 | −33% |
| GPU | 13.94 GB | **17.08 GB** | **+3.14 GB** |
| 20 歩時点の loss | 1.954 | **1.977** | +1.2% |
| 20 歩時点の勾配ノルム | 4.483 | 4.407 | −1.7% |

**loss がほぼ同じなのは、狙ったとおりである。** `fusion_gate` を 0 で初期化してあるので
学習の始まりでは接ぎ木が出力に効かない。**20 歩では差が出ないのが正しい**
——差が出るのはこの係数が動いてからである。**base を壊していないことの確認になっている。**

**batch 16 は載らない。** 18.98 GiB まで使って落ちた（H100-20C の使える容量は 19.80 GiB）。
**このマシンでは batch 8 が上限である。**

| | 判断 |
|---|---|
| batch を 8 に落とす | **いまの手** |
| 会社の RTX6000（24 GB）に移す | **使えない。**Turing 世代で bf16 にハードウェア対応していない |
| `--geometry-image-size` を 252 より下げる（238・224…） | 逃げ道。**ただし推論側と揃える必要がある** |

**20 歩の試し撃ちが通った**（`All keys loaded successfully!` → `End of training`）。

### 7.5.2 踏んだ穴 2 つ（同じ日に両方とも学習が止まった）

| 穴 | 何が起きたか | 直し方 |
|---|---|---|
| **土台の重みが 1 つも載らないまま学習が始まる** | `PI05Policy.from_pretrained` は `load_state_dict(..., strict=True)` を呼ぶ（modeling_pi05.py:1032）。**`__init__` の時点で接ぎ木の層が生えていると、土台の重みにその名前が無いので例外になる。**しかもその例外は握りつぶされて `Warning: Could not load state dict` と出るだけである（同 1057-1060 行） | **接ぐのは重みを読み終えたあとにした。**最適化器はそのあとに作られるので、接ぎ木の層はちゃんと最適化器に入る |
| **逆伝播で落ちる** | 最初は `embed_image` を包む形にしたが、`embed_prefix` はそれを `self._apply_checkpoint(...)` の中で呼ぶ。**再計算した値が元と一致せず `CheckpointError: A different number of tensors was saved during the original forward and recomputation`** | **接ぎ木を勾配チェックポイントの外側に出した** |

**前者のほうが危ない。** 例外が握りつぶされるので、**気づかなければ「乱数の π0.5 を
20,000 歩学習した」結果を、接ぎ木の効果だと読むところだった。**
**`All keys loaded successfully!` がログに出ているかを、毎回確かめること。**

### 7.5.3 12,000 歩回した結果 —— 動いたが、育たなかった（2026-08-28）

**接ぎ木は効いている。** 学習データの実物のコマを通し、足される量を元の画像トークンと比べた。

| | 6,000 歩 | 12,000 歩 |
|---|---|---|
| front の寄与 | 25.2% | **26.4%** |
| wrist の寄与 | 26.4% | **27.6%** |

**しかし学習できたのは 0 で初期化した層だけだった。**

| 層 | 初期値 | 6,000 歩 | 12,000 歩 |
|---|---|---|---|
| `cross_attention.out_proj.weight` | **0** | 0.001238 | 0.001286 |
| `cross_attention.out_proj.bias` | **0** | 0.001170 | 0.001205 |
| `norm_query.bias` | **0** | 0.000930 | 0.000973 |
| `norm_key.bias` | **0** | 0.000677 | 0.000823 |
| **`norm_query.weight`** | **1.0** | **0.000000** | **0.000000** |
| **`norm_key.weight`** | **1.0** | **0.000000** | **0.000000** |

（値は初期値からの差の絶対値の平均。）

### 7.5.4 原因は bf16 の刻み幅である

**「勾配が小さい」ではこの分かれ方を説明できない。**0 から始めた 4 つは全部動き、
1.0 から始めた 2 つは 6 桁目まで 1 つも動いていない。

| 値のあたり | bf16 の刻み幅 | 学習率 2.5e-5 の 1 歩が届くか |
|---|---|---|
| **1.0**（LayerNorm の weight） | **7.81e-03** | **312 歩ぶん同じ向きに押して 1 目盛り** |
| 0.011（`to_policy_dim`） | 6.10e-05 | 2.4 歩ぶん |
| **0.0**（`out_proj`） | 極めて細かい | **初手から動ける** |

**bf16 は仮数が 8 bit しかないので、1.0 の近くでは 0.0078 刻みでしか値を表せない。**
1 歩 2.5e-5 の更新は丸められて消える。`to_policy_dim` も同じで、6,000→12,000 の変化は
絶対値の平均 0.000038 と**この値のあたりの刻み 6.1e-5 より小さい**——大半の重みは
1 目盛りも動いていない。

**つまり 0 で初期化したことが、唯一この層が学習できた理由でもある。**
He や Xavier で初期化していたら、刻みの粗いところに置かれて**もっと動かなかった**
（`to_policy_dim` は PyTorch 既定の Kaiming 一様分布、`in_proj` は Xavier 一様分布で、
どちらも実際にそう初期化されている。**0 にしたのは `out_proj` だけである**）。

**次に回すときの手。**

| 手 | 中身 |
|---|---|
| **接ぎ木の層だけ fp32 で持つ** | π0.5 本体は bf16 のまま、足した 2,099 万個だけ精度を上げる。丸めの問題が消える |
| 接ぎ木の層だけ学習率を上げる | 1.0 の近くでも 1 目盛りを超えられるようにする。最適化器を層ごとに分ける実装が要る |

### 7.5.5 論文との違い —— LoRA を入れていない

| | Evo-0（写した相手） | GeoAware-VLA | **今回** |
|---|---|---|---|
| 土台 | π0 | BAKU | π0.5 |
| 視覚エンコーダ | 残す | **VGGT で置き換える** | **残す** |

### 7.6.1 何歩回すかを決めてほしい

**batch 8 で 1.196 秒/step である**（7.5.1 節の実測）。時間はこうなる。

| 学習ステップ | 見る量 | かかった時間 |
|---|---|---|
| 4,000 | 32,000 サンプル・0.014 エポック | **1.3 時間** |
| 12,000 | 96,000 サンプル・0.043 エポック | **4.0 時間** |
| 24,000 | 192,000 サンプル・0.086 エポック | **8.0 時間** |

**学習する層は 2,099 万個だけである。**フルパラメータ学習（33 億個）とは桁が違うので、
**0.086 エポックでも足りる見込みはある**——ただし**根拠は無い。**
Evo-0 の論文は学習量を書いていない。

**`--steps` は学習率の下げ方そのものを決める値なので、後から変えられない**
（`--resume` では変わらない。[howto/07](../howto/07_train_pi05_local.md)）。

**⓪の承認を待たずに②へ進める。** 非商用の `facebook/VGGT-1B` は門が無く、
**構造も大きさも同じ**（`embed_dim` 1024・`img_size` 518・`patch_size` 14）なので、
**開発と測定はこちらで進め、提出物に入れる段で商用可の重みに差し替える。**

**②が手元の GPU で回せることが、いまは効いている。** 長い学習は RunPod か Blackwell が
空くのを待つ状態なので、**その待ち時間に手元で進められる数少ない手である。**

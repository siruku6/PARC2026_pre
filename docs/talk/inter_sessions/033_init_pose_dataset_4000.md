## なぜ要るか

**A が無いと Track1 を払う。****B が無いと「まんべんなく」が嘘になる。**

### A の理由——素の見た目を 2 割以上足すと Track1 が薄まる

**配布データの「かさ」は外観の焼き直しでできている。**1,681 個の物理を平均 8.5 通りの
見た目で焼き直したものが 14,347 本である。**そこへ「素の見た目」の塊を約 24% 足すと、
見た目の分布がそのぶん素へ寄る。****Track1（0.492）は背景と照明だけのトラックなので、
ここは払いたくない代償である。**

### B の理由——いまのデータは通りやすいデモに寄っている

**9/12 の 950 本を数えた**（`work/regen/npz_init_pose/manifest_all.jsonl`）。

| 見るもの | 実測 |
|---|---|
| 撃った回 / 合格 / 歩留まり | 10,721 回 / 950 本 / **8.9%** |
| 合格が出た (課題, デモ) の種類 | **560 種**（合格 950 本ぶん） |
| 同じ (課題, デモ) が何回出たか | 1 回:334 / 2 回:124 / 3 回:64 / 4 回:24 / 5 回:9 / 6 回:3 / **8 回:1 / 9 回:1** |
| デモ番号ごとの本数 | 最多 35 本（demo 48）／ **最少 7 本**（demo 49・demo 16）＝ **5 倍差** |

**原因は `generate_perturbed.py` の作りである。**`_run_item` はデモを混ぜた順に撃ち、
**`written >= budget` に達したら止める。**合格したものだけが書かれるので、
**出力は「通ったデモ」に寄る。**通りやすいデモは何度も採られ、通りにくいデモは 1 度も出ない。

## 前提となる事実（受け側が知らないこと）

### 1. 変種名の組み立て（A の中身）

**LIBERO-plus の変種名は 4 軸を 1 つの名前に同居できる。**

```
<課題>_light_37_view_30_15_125_0_0_initstate_285_noise_12
  │      │        │                      │            └ 雑音（任意）
  │      │        └ カメラ（方位角・仰角・拡大率×100・レンズ回転・レンズ上下）
  │      └ 照明（または背景 _table_N / _tb_N）
  └ 課題
```

**`env_wrapper.py:207-237` は `_view_` で切って前半を `.bddl` として解決し、
`_initstate_` と `_noise_` を後半から読む。**だから

- **背景・照明は `<bddl>` 側**（`<課題>_light_37.bddl` が実在すれば通る）
- **カメラ・初期姿勢・雑音は名前側**（一覧に無い組み合わせを自分で書いてよい）

**追加費用はゼロである。**物理は `states[0]` で決まり、再生する行動列も同じなので、
**歩留まりも所要時間も変わらない。変わるのは描画するときの見た目だけである。**

**`if int(init_state) != 0: robots = [robots[0] + str(init_state)]`** という実装なので、
**初期姿勢の番号は `new_init.py` が作った 1〜500 のクラスに限られる。**

### 4. 3 つの門（採否の規則・`replay_yield.passes_gates`）

| 門 | 中身 | 定数 |
|---|---|---|
| `reached` | **300 歩以内**に bddl の goal が立つ | `MAX_STEPS = 300` |
| `clean` | **その時点で**対象外の物体が 1 mm を超えて動いていない | 採点と同じ |
| `covered` | **方策が引き継ぐ時点の手先のずれが 2 cm 以上** | `MIN_OFFSET_CM = 2.0` |

**3 番目が要る理由。**摂動しても腕が元の経路に戻ってしまえば、作っても覆う範囲は増えない。
**「作ったのに被覆が増えていない」という静かな失敗を止める門である。**

### 5. 2 通りの撃ち方

| `--method` | 中身 | 歩留まり |
|---|---|---|
| **`open_loop`（既定）** | **ずれを最後まで抱える。**記録された行動をそのまま流す | **9/12 の実測で 8.9%**（50 番号・2 cm 以上） |
| `prealign` | **先に腕をデモの 0 コマ目の手先へ寄せてから**流す | 160 組の実測で 35.0%（比例制御）／**40.6%（Ruckig）** |

**`open_loop` のほうが被覆としては上等である**（ずれを最後まで抱えるので）。
**`prealign` は歩留まりの穴埋めに使う。**
**`prealign` を使うなら `--prealign-planner glide`（Ruckig）にすること**——
歩留まりが 35.0% → 40.6% に上がり、**指令が上限 ±1.000 ちょうどに張り付く形
（配布データに 1 コマも無い形）が 2.60% → 0.00% になる**。**9/13 夜に入口加速度の向きを直した版で測り直した**——歩留まりは同じ 40.6%、寄せる区間の符号反転は 7.19% → 0.08%（034 の 1 節）
（[../tmp_reply/260913_ruckig_prealign_result.md](../tmp_reply/260913_ruckig_prealign_result.md)）。

### 6. 実測した費用（9/12 の 950 本から）

| 段 | 実測 | 4,000 本ぶん |
|---|---|---|
| 生成（13〜14 並列） | 950 本 / **3.3 時間** | **13.9 時間** |
| 変換（1 プロセス・**13.5 秒/本**） | 950 本 / **3.3 時間** | **15.0 時間** |
| **重ねた合計** | 950 本 / 6.5 時間 | **約 15〜16 時間** |

**変換が生成と同じだけかかる。**`run_init_pose_batches.sh` は次の塊の生成と重ねる作りに
してあるので、**直列 29 時間が約 15〜16 時間になる。****さらに変換を 2〜3 並列にすれば
生成の 13.9 時間で律速する。**

> **9/12 に出した見積（生成 250 本/19 分・変換 9.0 秒/本）は楽観だった。**

> **上の表を使うこと。**

### 8. 指示文の穴（**これを外すと全部無駄になる**）

**自作した手本は、評価でモデルが実際に見る文で入れないと 1 度も引かれない**
（[knowledge/23](../../knowledge/23_self_made_demos_need_the_instruction_the_model_sees.md)）。
`record` が残すのは bddl の言い方で、`policy_server.py` は採点で来た文を
配布データの 40 種へ寄せてからモデルへ渡す。**寄せた先の言い方で入っていない手本は誰も引かない。**

**この穴は沈黙して失敗する。**学習は通り、損失も下がり、エラーも出ない。
出るのは「作ったのに効かない」という結果だけである。

**塞ぎ方は 2 つとも必ず打つこと。**

1. **変換のときに `--normalize-instructions` を付ける**（`npz_to_lerobot.py build`）

### 2. 外観の配り方を、配布データの出方に合わせて決める

**素の見た目だけにしない。**配布データの出方に合わせて引く。

| 軸 | 引き方 |
|---|---|
| 背景・照明 | **素 : `_light_N` : `_table_N`/`_tb_N` を、配布データの出方に合わせる**（`reference/08_appearance_spread.md`） |
| カメラ | 配布データの振れ幅から引く（**32 本中 7 本が別位置 ≒ 22%**・`reference/06_training_data_composition.md`） |
| 雑音 | 実在する段から引く（`reference/20_track2_perturbation_categories.md` の 2.1） |

**引きは種で決めること**（`--seed`）。**どの本にどの外観を当てたかを npz と manifest に残す**
——後から「見た目の分布がどうなったか」を数え直せないと、Track1 への影響を測れない。

### 3. デモの偏りを除く

**いまの作り**（`generate_perturbed.py:_plan` と `_run_item`）は
「デモを混ぜた順に撃ち、`budget` 本書けたら止める」である。**通ったデモに寄る。**

**打ち方の案**（より良い手があれば変えてよい。理由を報告に書くこと）。

1. **(課題, デモ) ごとに上限を置く。**同じデモが `--per-demo-cap`（既定 2〜3）を超えて
   採られないようにする。上の実測では 8 回・9 回採られたデモがある
2. **2 周回す。**1 周目で全 (課題, デモ) を 1 回ずつ撃ち、
   2 周目は**まだ 1 本も出ていない (課題, デモ) を優先して**別の初期姿勢番号で撃つ
3. **課題ごとに目標を置く。**全体の `--target` で止めると、止めた時点で特定の課題に寄る。
   **`--per-task-cap` を 4,000 ÷ 38 ≒ 105 本に固定する**

**「厳密に均等」は要らない。**ユーザの要求は
**「通りやすいか通りにくいかでデータが偏るのは避ける」**である——ランダム性は良い。

### 4. 4,000 本作る

```bash
INITSTATES=work/regen/initstates_48.json \
OUT_NPZ=work/regen/npz_init_pose_v2 \
OUT_LEROBOT=work/regen/lerobot_init_pose_v2 \
OLD_MANIFEST=/dev/null \
PER_NUMBER=80 PER_CHUNK=5 WORKERS=13 \
  nohup bash solution/tools/regen/run_init_pose_batches.sh \
  > work/regen/logs/init_pose_v2.log 2>&1 &
```

**`OLD_MANIFEST=/dev/null` にする理由。**既存の 1,250 本は捨てるので、
**同じ組を撃たない仕掛けを外す**（外観が違えば別のデータである）。

**`PER_NUMBER` と `PER_CHUNK` の算数。**50 番号 × 80 本 = 4,000 本。
1 塊 = 5 番号 × 80 本 = 400 本 = **npz で 24〜39 GB**。**2 塊ぶんが同時に載る**ので
48〜78 GB になる。**空きが 143 GB なら `PER_CHUNK=5` で足りる。**

**`--method` の使い分け。**まず `open_loop` で回し、**足りなければ `prealign`
（`--prealign-planner glide`）で埋める。**歩留まり 8.9% だと 4,000 本に
45,000 回撃つことになるので、**`prealign` の併用はほぼ必須である。**

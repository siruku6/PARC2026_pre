# 27. `grdn` が 1.0 を超え続けても、学習は止まっていない —— 疑うのは、上限ちょうどに積み上がった指令である

**2026-09-10 に、逆向きの手本を混ぜた学習の勾配ノルムが、配布データだけの学習より
高いまま下がらない理由を調べて分かったことである。**

> **これが分かると何が決まるか。**学習ログの勾配の値を見て「実質の学習率が下がっている」
> 「クリップを外そう」と動かなくなる。**直す先は学習の設定ではなく、データを作る制御器になる。**

**`grdn`** は、lerobot の学習ログに 20 歩ごとに出る値で、**全パラメータの勾配をまとめた大きさ（ノルム）**である。
PyTorch の `clip_grad_norm_` が返す**切る前**の値で、この学習では上限 1.0 で切っている
（重みの隣の `train_config.json` の `optimizer.grad_clip_norm`）。

## 1. 何を読み違えたか

**9/10 まで、着手中の作業の板にこう書いていた。**
「逆向きの手本を混ぜた学習の `grdn` はクリップの上限 1.0 に当たり続けているので、
**実効の更新量が 1/3 になっている。**だから学習が進まない」。

**この読みは 2 か所で間違っていた。**クリップは勾配を縮めていない（2 節）。
仮に縮めていても、最適化器 AdamW は更新量を変えない（3 節）。

## 2. クリップは勾配を縮めずにノルムを揃える

**`clip_grad_norm_(params, 1.0)` は、ノルムが 1.0 を超えていたら、ちょうど 1.0 になるように全体を割る。**
**だから切られている歩では、最適化器が受け取る勾配のノルムは毎回 1.0 である。**

| 学習 | データ | `grdn` の中央（ログ 1,200 点） | **最適化器が受け取るノルムの中央** |
|---|---|---|---|
| `pi05_full_local` | 配布 14,347 本 | 0.819 | **0.819**（半分以上の歩で切られていない） |
| `pi05_v2_base24k` | 配布 ＋ 逆向き 49.5% | 1.221 | **1.000**（半分以上の歩で 1.0 に揃えられている） |

**逆向きを混ぜた学習のほうが、むしろ大きい勾配を受け取っている。**

## 3. AdamW は勾配の定数倍を打ち消す

AdamW の 1 歩の更新量は、勾配 `g` に対しておおよそ次の形をしている。

```
更新量 = 学習率 × m / (√v + eps)      m: g の移動平均      v: g² の移動平均
```

**勾配を一律に `c` 倍すると、`m` は `c` 倍、`√v` も `c` 倍になり、割り算で `c` が消える。**
この学習の設定は `betas = (0.9, 0.95)`・`eps = 1e-8` なので、`v` はおよそ 20 歩の窓で均され、
`eps` のずれは無視できる。

**帰結。`grdn` が 1.0 を超え続けていても、それだけでは学習は止まらない。**
**`grdn` は症状であって、原因ではない。**

**ただし、切られているあいだは本当の勾配の大きさがログから消える。**
原因を探す間だけクリップの上限を 3.0 に上げると値が読めるようになり、更新量は上の理由でほとんど変わらない。

## 4. 高止まりの正体の候補は上限ちょうどの指令である

**では、なぜ混ぜた学習の `grdn` は配布データだけの学習の 1.5 倍前後に留まるのか。**
学習データの行動（`action`・7 次元の指令）を全コマ数えると、特定の 1 点に積み上がっていた。

| 見たもの（`jaist_mix_v2_x8`・992,843 コマ） | 値 |
|---|---|
| **手首のひねり（6 次元目）が上限の ±0.375 ちょうどのコマ** | **全体の 14.53%**（逆向きのコマに限ると約 29%・配布のコマは 1% 未満） |
| **並進のどれかの軸が ±1.000 ちょうどのコマ** | **全体の 10.01%**（配布データの並進は ±0.9375 で頭打ちになっており、±1.000 は現れない） |

**出どころは、逆向きの手本の接近の区間を作った制御器である。**
目標姿勢との差を割って ±1 で切る比例制御なので、腕の初期位置から 300 mm 離れた接近の区間では、
**差が大きすぎて指令が上限のまま並ぶ。**逆向きのエピソードの先頭 10% では、並進はほぼすべてのコマで上限だった。

**回転に上限 0.375 をかけた作り直しは、外れ値を消したが、外れ値を上限ちょうどの 1 点へ積み替えただけだった。**
**「外れ値を消す」ことと「切る」ことは同じではない。切ると値は上限の 1 点に集まる。**

## 5. flow matching は 1 点に立った針を出せない

**π0.5 は、ノイズから行動へ連続的に流れる速度場を学ぶ型（flow matching）である。**
なめらかな速度場は、**分布の端の 1 点に立った針**を表せない。

```mermaid
flowchart LR
    A["学習データの行動の分布<br/>なだらかな山 ＋ 上限に立った針"] --> B["なめらかな速度場では<br/>針を出せない"]
    B --> C["針に当たるコマの残差が<br/>0 にならない"]
    C --> D["そのコマが勾配を出し続ける"]
    D --> E["grdn が下がりきらない"]
```

**モデルの側では、上限に張り付いた目標が中間の値へ潰れて出る。**
回転に上限をかける前のデータで学習した重みは、回転の指令を記録より小さくしか出していなかった
（[21 の 3.6.3](21_track3_stops_short_of_the_object.md)）。

**これはまだ候補である。**針を消したデータで学習し、`grdn` が配布データだけの学習の水準
（中央 0.8 前後）まで下がるかを見る 1 本は、2026-09-15 時点で回していない。
**`grdn` が下がらないときに何から疑うかの順番は [reference/33 の 3 節](../reference/33_gradient_norm_and_action_saturation.md) にある。**

## 6. 作る側での直し方

**針は学習の設定では消えない。**正規化の尺度を変えても、切る位置が動くだけで針は残る。
**消せるのは、データを作る制御器の段だけである。**

黒い丼の 5 課題の手本を作り直したとき（[24 の 6 節](24_reached_but_zero_is_collision_at_grasp.md)）、制御器に 3 つ入れた。

| 入れたもの | なぜ |
|---|---|
| **封筒**（並進 ±0.9375・回転 ±0.30 に収め、1 コマの変化量も制限する） | 配布データの指令の端に合わせる |
| **巡航 0.85**（いちばん大きい軸を上限まで振り切らない） | 振り切ると上限の 1 点に積み上がる |
| **降下を 2 段に割る** | 手首を回すためだけに腕を止めると、今度は指令 0 の 1 点に積み上がる |

**結果**（`solution/tools/motion/report_smoothness.py`・配布の手本 200 本と作った手本 10 本を比べた）。

| 見るもの | 配布 | 初版 | 直した版 |
|---|---|---|---|
| 並進が ±0.9375 以上のコマ | 7.79% | 33.79% | **0.00%** |
| 腕が止まっているコマ | 0.96% | 24.23% | 14.40% |
| 1 本のコマ数の中央 | 132 | 189 | **138** |

**止まっているコマだけが残った。**指を閉じる区間と、置いて待つ区間で腕が止まるためである。

**「止まる区間でも指令を厳密な 0 にせず、位置を保つように毎歩わずかに補正する」案は、測って外した。**
止まっているコマは 1.71% まで減ったが、**成功が 10/10 から 2/10・3/10 に落ちた。**
指が縁を挟む間、閉じる反力を毎歩打ち消しに行って腕が振動し、丼を押しのけた。
**手を止める区間は、本当に止めるしかない。**

## 7. 確かめ直すコマンド

```bash
cd ~/src/PARC2026_pre

# 2 節: grdn の中央（学習ログの \r を改行に直してから拾う）
for f in work/train/pi05_full_local.log work/train/pi05_v2_base24k.log; do
  tr '\r' '\n' < "$f" | grep -oE 'grdn:[0-9.]+' | cut -d: -f2 | sort -n \
    | awk -v f="$f" '{a[NR]=$1} END{print f, "n="NR, "median="a[int((NR+1)/2)]}'
done

# 3 節: クリップの上限と AdamW の設定
python3 -c "import json; print(json.load(open('work/artifacts/pi05_v2_base24k/train_config.json'))['optimizer'])"

# 4 節: 上限ちょうどのコマの割合
python3 - <<'EOF'
import glob
import numpy as np
import pyarrow.parquet as pq
total = rz = trans = 0
for f in sorted(glob.glob("work/artifacts/jaist_mix_v2_x8/data/**/*.parquet", recursive=True)):
    a = np.asarray(pq.read_table(f, columns=["action"]).column("action").to_pylist(), dtype=np.float32)
    total += len(a)
    rz += int(np.sum(np.isclose(np.abs(a[:, 5]), 0.375, atol=1e-6)))
    trans += int(np.sum(np.any(np.isclose(np.abs(a[:, 0:3]), 1.0, atol=1e-6), axis=1)))
print(total, f"rz ±0.375: {rz / total:.2%}", f"並進 ±1.0: {trans / total:.2%}")
EOF
```

## 8. Claude 側

**「クリップされている＝縮められている」と読み、揃える操作だと確かめなかった。**
AdamW の更新式が勾配の大きさを打ち消すことも見ていなかった。
**学習ログの数値から「学習が進んでいない」と言う前に、その数値が最適化器の更新量にどうつながるかを式で追う。**

**原因の候補と、確かめた原因を書き分ける。**4・5 節はデータの数えと理屈までで、
確かめる学習は回していない。

## 9. 人間側

**学習の数値がおかしいと感じたら、学習の設定をいじる前に、学習データの行動の分布を 1 回数える。**
上限ちょうどの値の割合は、GPU を使わず手元の parquet から 1 分で出る。
**自作のデータを混ぜた学習なら、なおさら先に数える。**

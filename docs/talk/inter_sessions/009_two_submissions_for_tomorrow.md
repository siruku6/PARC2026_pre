自然言語の指示を与え、LIBERO-plus のシミュレータの中で物を掴んで運ばせる。
こちらの方策は **π0.5**（4,143,404,816 パラメータ）。`solution/policy_server.py` が
画像 2 枚と状態を受け取り、行動列を返す。**提出は 1 日 1 トラック 1 回だけ。**

### いまの点（2026-08-29 の採点結果まで反映）

| トラック | **こちらの点** | **最高点** | いちばん新しい提出 |
|---|---|---|---|
| Track1 | **0.492** | **0.65** | 5.0.1（`001500` の重み） |
| Track2 | **0.233** | **0.53** | 5.0.1（同じ zip） |
| Track3 | 0.000 | 0.000（**全参加者 0**） | 5.0.1 |

### この依頼が効くところ —— **2 本とも「1 変数」の提出である**

**枠は 1 日 1 トラック 1 回しかない。だから 1 回の提出で 1 つだけ変える。**
明日出す 2 本は、それぞれ別の問いに答える。

| | 変えるもの | **答える問い** |
|---|---|---|
| **Track1** | `ema_alpha` 0.3 → **0.5**（重みは `001500` のまま） | **なめらかさの項だけで点が動くか** |
| **Track2** | 重み `001500` → **`001000`**（設定は 5.0.1 のまま） | **歩数を増やすほど点が上がるか** |

**なぜ Track1 でなめらかさを狙うのか。**5.0.1 の Track1 は
**8 エピソードすべてが打ち切り（300 歩）に達していない。**
手元の目盛りで「8 本すべて成功」の上限は 0.489〜0.499 で、**0.492 はほぼその線に乗っている。**
**つまり成功の側はもう埋まっていて、残り（最高点 0.65）はなめらかさ 5 項でしか取れない。**

**採点式は公開されている。**

```
smooth metrics = w1·time + w2·jerk + w3·SPARC + w4·trajectory + w5·rotation   (Σw = 1)
Total Score    = (1/N) · Σ successᵢ · (1 − collision penaltyᵢ) · smooth metricsᵢ
```

**重みは非公開。**`time` は壁時計ではなく歩数である（運営 Q&A No.23）。

**`ema_alpha` は jerk の項を単調に動かす。**手元の 12 行での実測——
`ema_alpha` 0 / 0.3 / 0.5 に対して jerk の項が **0.437 / 0.478 / 0.508**。
**摘みは看板どおりに効いている。**

**ただし手元では合計点が下がった**（0.1436 / 0.2055 / 0.2011）。
**それは成功率が落ちたからで、その 12 行は衝突が集まるように選んだ集合である**
（衝突率 0.611。72 行全体は 0.227）。
**Track1 は衝突も打ち切りも出ていないので、同じ落ち方はしないと読んでいる。**
**これは読みであって、測った事実ではない。**

**なぜ Track2 で 1,000 歩を出すのか。**`001500` が 0.233 で、**その 1,000 歩版が
それより下なら「歩数を増やすほど上がる」と言える。**
**手元の評価では 500 歩の差を分けられない**——同じ重みを 2 回測るだけで
成功率が 0.667 と 0.722 の間を動く。**提出でしか測れない。**
**この結果が、いま回している長い学習（依頼 008）をどこまで伸ばすかを決める。**

## 何をしてほしいか

**zip 2 本を作り、sha256 を取り、ユーザがそのまま貼れる提出手順を書いてほしい。**

| 版 | トラック | 重み | 変えるところ |
|---|---|---|---|
| **5.1.0** | **Track1** | `001500` | **`ema_alpha` の既定 0.3 → 0.5** |
| **6.1.0** | **Track2** | **`001000`** | **無し**（5.0.1 と同じ設定） |

**版番号の決まり。**`5.x` が 1,500 歩、`6.x` が 1,000 歩である（既存の対応を保つ）。

成果物は **(1) zip 2 本と sha256**、**(2) `--show` で出した設定の印字**、
**(3) 下の「報告の書き方」の表**である。

**明日の 2 つの枠が、そのまま 2 つの問いの答えになる。**
**zip が無いと枠が空で流れる**——枠は翌日に持ち越せない。

## 前提となる事実

### 5.0.1 の設定（これが基準。ここから 1 つだけ変える）

```
[parc] policy_server 5.0.1  model=pi05  device=cuda  num_inference_steps=10
       n_action_steps=16  ema_alpha=0.3  blend_steps=0  samples=1
       gain=(1.0,1.0)  seed=0  rtc=off  normalize=on  quant_serve=off
```

**`_MIN_LEXICAL`（指示文の正規化のしきい値）は 0.50 である。**
**リポジトリの `solution/policy_server.py` は 0.65 のままなので、zip の中だけを 0.50 にする。**
**0.65 は 8/27 のバグ修正**（Track3 の 1 文が意味の逆に書き換わっていた）**で入れたもので、
消さずに残している。**しきい値の違いは別の 1 変数として後日測る。

**0.50 と 0.65 の差は「効かない」ではない。**LIBERO-plus の全 bddl から指示文 2,124 種を
集めて測ると、**503 種（24%）で出力が違う。**違いが出るのは言い換えのカテゴリだけで、

### 材料の在り処

| 何 | どこ | 備考 |

### 長さが同じなら、9.4 GB を組み直さなくてよい

**`build_submission.py` が作る zip では `policy_server.py` が無圧縮（method=0）で入っている。**
**だから同じ長さの置き換えなら、バイトを差し替えて CRC を直すだけで済む。**
**5.1.0 の 3 か所は全部桁数が同じである。**

```bash
python3 solution/tools/build/patch_zip_policy_server.py <zip> --show   # まず中を見る

python3 solution/tools/build/patch_zip_policy_server.py <zip> \
    --replace '_MIN_LEXICAL = 0.65' '_MIN_LEXICAL = 0.50' \
    --replace '"PARC_EMA_ALPHA", "0.3"' '"PARC_EMA_ALPHA", "0.5"' \
    --replace '__version__ = "4.6.0"' '__version__ = "5.1.0"' \
    --in-place
```

**道具は書き換えの前後の設定を印字し、`zipfile` で読み直して `testzip()` まで通す。
通らなければ書かない。**`--in-place` を付けない限り 1 バイトも書かない。
**`policy_server.py` が無圧縮でなければその場で止まる。**

**`--replace` の左辺が zip の中に 1 か所だけあることを道具が確かめる。**
2 か所あると止まるので、そのときは**リポジトリを一時的に書き換えて組み直し、
`git checkout` で戻す**ほうへ切り替えること。

### 6.1.0 は組み直しになる（`001000` の zip は残っていない）

**8/29 に HF から `submission_6.0.0.zip` を消した**（容量の都合）。
**重みは生で残っているので 15 分で組み直せる。**

```bash
hf download siruku6/pi05_trial1500 --include '001000/*' --local-dir work/artifacts/trial1500
python3 solution/tools/build/build_submission.py --weights work/artifacts/trial1500/001000
```

**`--weights` に渡したディレクトリが、そのまま zip の `model_weights/` になる。**
`install_weights.py` は使わない（**9.4 GB の複製 2 つを作るうえ、`model_weights.bak/` を
上書きする**）。

**組んだあと、`policy_server.py` の 2 か所を patch する。**

```bash
--replace '_MIN_LEXICAL = 0.65' '_MIN_LEXICAL = 0.50'
--replace '__version__ = "4.6.0"' '__version__ = "6.1.0"'
```

**版番号の左辺は `--show` で実際の値を見てから決めること**（リポジトリの現在の
`__version__` は 4.6.0 とは限らない）。

### zip を組める機械の条件

**`work/artifacts/vendor/lerobot` が要る。**`build_submission.py` は
`model_weights` と `vendor` の 2 つを `work/artifacts/` から取るので、
**`vendor/` が無いと `生成物がありません` で落ちる。**

**RTX6000（`~/src/PARC2026_pre`）には 8/29 に作った**（487 ファイル）。
**無い機械で組むときは、LeRobot v0.6.0 のソースを取って `vendor_lerobot.py` を走らせる**
（13 MB・3 分。手順は [../../howto/02_build_submission.md](../../howto/02_build_submission.md) のケース 0）。

**`[build] 検証` の行が出ることを必ず確かめる。出ないビルドは使わない。**

## やること

1. **`git pull`。**`patch_zip_policy_server.py` と `howto/02` のケース 0 が入っている。

2. **5.1.0 を作る。**`submission_5.0.0.zip` を降ろし、`--show` で中を見て、
   3 か所を patch する（上のコマンド）。**名前は `submission_5.1.0.zip`。**

3. **6.1.0 を作る。**`001000` を降ろし、`--weights` で組み、2 か所を patch する。
   **名前は `submission_6.1.0.zip`。**

4. **sha256 を取り直す。**

   ```bash
   sha256sum work/submission_5.1.0.zip | tee work/submission_5.1.0.sha256
   ```

   **`build_submission.py` が自分で書く `work/submission.sha256` は
   patch する前の値なので消すこと。**

5. **中身を最後にもう一度確かめる。**

   ```bash
   python3 solution/tools/build/patch_zip_policy_server.py work/submission_5.1.0.zip --show
   ```

   | zip | `__version__` | `_MIN_LEXICAL` | `PARC_EMA_ALPHA` |
   |---|---|---|---|
   | 5.1.0 | `5.1.0` | `0.50` | **`0.5`** |
   | 6.1.0 | `6.1.0` | `0.50` | `0.3` |

6. **ユーザに渡す形を書く。**zip が置いてある機械とパス、Mac への降ろし方、
   **どちらをどのトラックへ出すか**を、報告の中に**そのまま貼れる 3 行以内**で書く。
   **Mac へは HF 経由が速い**（`scp` は 1.7 MB/s、HF は約 20 倍）。

7. **リポジトリを汚していないことを確かめる。**

   ```bash
   git status --short
   grep -n '^_MIN_LEXICAL = ' solution/policy_server.py    # 0.65 のままであること
   grep -n 'PARC_EMA_ALPHA' solution/policy_server.py      # 0.3 のままであること
   ```

## 報告の書き方

**表と数値だけでよい。**

1. **zip の表**——版・重み・バイト数・sha256・`--show` の印字。
2. **patch が使えたか**（無圧縮だったか）。使えなければ何に切り替えたか。
3. **`vendor/` の件**——あったか、作ったか。
4. **ユーザが打つもの**——3 行以内。
5. **想定と違ったところ。**

## 判断が必要になったら

**この依頼の目的は「明日の 2 つの枠を、それぞれ 1 変数の比較として使えるようにする」ことである。**
**Track1 は 0.492 と、Track2 は 0.233 と比べられる形でなければ意味が無い。**

**その目的に照らして、より確実なやり方を思いついたら変えてよい。**
たとえば **patch が通らなければ、リポジトリを一時的に書き換えて組み直し、
`git checkout` で戻す**ほうが確実である。**変えた場合は理由を報告に書くこと。**

**次の 2 つは動かさないでほしい。**

| 動かさないもの | なぜ |
|---|---|
| **指定した 1 か所以外の設定** | 1 変数にするための依頼である。他を触ると、点が動いた理由が読めなくなる |
| **`001500` と `001000` の対応**（`5.x` が 1500・`6.x` が 1000） | 台帳が版番号と歩数の対応で引いている |

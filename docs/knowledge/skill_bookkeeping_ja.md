## 貫くべき 1 本の鎖

**報告する数字はすべて、それを出した成果物から 1 手で辿れないといけない。
しかも誰も何も覚えていない状態で。**

```
採点結果 → 提出物のハッシュ → 実行ディレクトリ → 設定・コードの版・重みの身元 → 生ログ
```

**この矢印のどれか 1 本がチャットの中にしか無ければ、鎖はもう切れている。**
2 週間前のスコアを 1 つ選んで、実際に辿ってみれば分かる。

## 1. ディレクトリは「何で消えるか」で分ける

**置き場所を決める問いは「これは何についてのファイルか」ではなく
「これは何をすると消えるか」である。**

| 寿命 | 中身 | git で追跡 | ディスクが減ったら |
|---|---|---|---|
| **書いたもの** | ソース・道具・手順 | **する（追跡するのはここだけ）** | 触らない |
| **説明** | 何をなぜ決めたか、測った値 | **する** | 触らない |
| **1 次資料** | ルール PDF・運営 Q&A・配布元の設定 | **する。そして編集しない** | 触らない |
| **生成物（作り直せる）** | 実行ディレクトリ・ログ・要約 | しない | ログは残す。動画は消す |
| **生成物（大きい）** | チェックポイント・提出用 zip・同梱ソース・venv | しない | **スコアを記録したら消す** |

**生成物は 1 つの根（`work/`）の下にまとめて、その根ごと無視する。**
`.gitignore` の 1 行なら見て確かめられるが、話題ごとに散った十数個の指定は確かめられない。
今回それは `docs/README.md` の 1 文（*追跡するのは `solution/` だけ。重み・同梱ソース・
venv・zip は `work/` に出て管理外*）として書かれていて、
**9.4 GB の誤コミットを全部防いだ。**

**説明の木には、目次を 1 枚置く。**「何を探しているか → どのファイルか」に答えるものを
根に置く。木は誰も一覧できない大きさまで伸びる —— 今回は手順 8 本・
調べた事実 18 本・知見 13 本になった。

## 2. 実行ディレクトリの名前は、その設定から作る

**時刻は「いつ」に答える。ラベルは「何を」に答える。両方取る。
そしてラベルは設定から機械的に組む。手で打たない。**

```bash
label="n${PARC_N_ACTION_STEPS:-5}_ep${N_EPISODES}_max${MAX_STEPS}"
[ -n "${LABEL:-}" ]            && label="${LABEL}_${label}"
[ -n "${PARC_EMA_ALPHA:-}" ]   && label="${label}_ema${PARC_EMA_ALPHA//./}"
[ -n "${PARC_BLEND_STEPS:-}" ] && label="${label}_blend${PARC_BLEND_STEPS}"
[ -n "$CHECK_ONLY" ]           && label="check_${label}"

OUTPUT_DIR="$ROOT/work/gpu_eval/$(date +%m%d_%H%M%S)_${label}"
```

これで `0814_113657_pi05_24k_n16_ep1_max300` や
`0814_172608_pi05_24k_blend4_n16_ep1_max300_blend4` ができた。効く性質が 2 つある。

- **時刻順に並ぶ**ので、`ls` がそのまま履歴になる
- **設定で検索できる** —— `ls work/gpu_eval | grep n16` で、
  **数週間後でも 1 つの設定の実行を全部集められる**

**名前は、実行が読むのと同じ変数から組む。**手で打ったラベルは、
名付けた実行からずれていく。**そしてずれたラベルは、無いより悪い** ——
信じてしまうからである。`run1/ run2/ final/ final2/ final_new/` が失敗形で、
これは 3 週目ではなく **3 日目に来る。**

## 3. 出力だけでなく入力も実行ディレクトリに写す

**実行が終わった時点で、そのディレクトリだけで「何がこれを出したか」に
答えられないといけない。**シェル変数の中・コンテナの環境の中・別のファイルの中に
あったものは、そうしないと消える。今回の実行ディレクトリ 1 つの中身:

| ファイル | なぜ入っているか |
|---|---|
| `eval.log`・`robosuite.log` | 生の出力。要約で置き換えない |
| `server.log` | **コンテナから外へ出したもの**（`docker logs > server.log`） |
| `server_8000.json` | サーバーが実際に使った、解決後の設定 |
| `VAL_TASKS.csv` | **入力の一覧を写したもの** —— 来週の同じファイルは違うかもしれない |
| `summary.txt`・`summary_compare.txt` | 導いた数字。生ログから作り直せる |
| `videos/` | 大きい。最初に消す対象 |

**入力の一覧は、参照ではなくコピーする。**タスク一覧・分割の定義・エピソード番号の一覧は、
作り直されたり手で直されたりする。**`make_eval_split.py` の「今の出力」を指している実行は、
そのスクリプトを再実行した瞬間に再現不能になる。**

## 4. 版番号と設定をログに焼く

**採点環境は、設定の付かない数字を返す。**版番号と設定がログに焼かれていないと、
1 週間後にどの提出がどのスコアだったか誰も言えない。

```python
__version__ = "4.2.0"   # major: 重みが変わった / minor: 推論の挙動 / patch: 挙動不変
...
print(f"[parc] policy_server {__version__} model={model} device={device} "
      f"n_action_steps={n} ema_alpha={a} blend_steps={b} samples={s}", flush=True)
```

実際に提出物の採点から返ってきた行:

```
[parc] policy_server 4.2.0  model=pi05  device=cuda  num_inference_steps=10
       n_action_steps=16  ema_alpha=0.3  blend_steps=0  samples=1  rtc=off  normalize=on
```

**その提出物を作り直すのに必要な値が全部 1 行に載っていて、
しかも採点環境が返してきたログの中にある。**

**版番号だけでなく設定を出す** —— 版番号は、それを上げる規律の分しか信用できない。
**知りたいのは設定そのものである。**

**その行が、実際に自分が読む場所に届くことを確かめる。**
最初の試みは、誰も開かないファイルへ標準出力が流れていて見えなかった。
*端から端まで確かめていない観測は、無いのと同じ。*

## 5. ログと結果を回収するコードを、その場しのぎで書かない

その場で書いた保存用のコードが**違うログを写して**しまい、どの物体にぶつけたかの唯一の記録が消え、
実行をやり直す羽目になった。

- **回収するコードは 1 か所に 1 つだけ置く。**最新の実行を見つけ、古くないと確かめ、
  内訳を計算し、外へ出す —— これを 1 か所で。成果物ごとに書かない
- **生ログは必ず残す。**このプロジェクトで後から復元できた事実は全部、
  **実行を始めた時点では誰も想定していなかった読み方で生ログを読み直して得られた** ——
  採点環境のエピソード数、上限、1 本ごとのステップ数、指標の係数。
  **3 日目に書いた要約は、12 日目に初めて出た問いに答えられない**
- **ダイジェストは成果物の隣に置く。**両方まとめて運んでも対応が壊れないように:
  `submission_rp3000_i20.zip` と `submission_rp3000_i20.sha256`

## 6. ログを残して重みを消す

**残す／消すは、大きさと「取り返しがつくか」で決まる。そしてこの 2 つは逆を向く。**

| もの | 大きさ | 作り直せるか | 方針 |
|---|---|---|---|
| 学習ログ | 45 KB | **いいえ** | **永久に残す。学習した機械の外に** |
| `train_config.json` | 4 KB | チェックポイントに同梱 | 残す |
| チェックポイント | 8.5 GB | はい（実行の費用をかけて） | スコアを記録するまで残し、古くなったものを消す |
| 提出用の zip | 9.4 GB | 4 分で作り直せる | スコアが返ったら消す。`.sha256` は残す |
| 動画 | 数百 MB | はい | 最初に消す |

**loss の推移はログにしかない。**`train_config.json` に入っているのは設定で、履歴ではない。
**「1 回目の学習は頭打ちだった」**——このプロジェクト最大の改善の根拠——は、
45 KB のログを、借りた機械を返す前に `scp` していたから証明できた。
**ログは、機械がまだ在るうちに引き取る。**必要になってからでは遅い。

**何かを消す前に、ハッシュを記録する。**ハッシュが書いてある成果物は、
作り直して同一だと証明できる。**ハッシュが無ければ、作り直したものは
「同じに見える別物」でしかない。**

## 7. 採点 1 回につき 1 行の台帳

**採点はプロジェクトでいちばん希少な資源である。1 回につき 1 行を、
返ってきたその場で、列ごとに出典を付けて書く。**

| 列 | 出典 |
|---|---|
| 版 | 返ってきたログの中の版番号の行 |
| 前の行から何を変えたか | 1 つだけ、名前で |
| 設定 | 設定の行をそのまま写す |
| 提出物のハッシュ | zip の隣の `.sha256` |
| スコア | 採点結果の画面を**書き写すのではなく、落としたもの** |
| 返ってきた生ログ | リポジトリの中のファイル |

**採点器のログは、スコアが返ったその場で落とす。**今回は 15 回のうち
**4 回ぶんしか予選を生き残らなかった** —— 残りは web の画面の中にしか無く、
二度と開かれなかった。**そしてそのログは、採点環境自身の設定を報せる測定器だった。**

**1 提出につき 1 ファイル、名前は実行と同じ形式**
（`260814_230032_pi0.5_4.2.0.md`）**＋ 全体の要約表を 1 枚。**
個別ファイルには返ってきたログとその読み方を、要約表には次の一手を決めるときに見るものを置く。

## 8. 機械をまたいでも保つ身元を与える

今回の成果物は 4 つの機械をまたいだ —— 手元の GPU 機 → 借りた GPU → Mac → 提出先。
**ファイル名はこれを越えられない。ハッシュは越える。**

- 組んだ時点で `<名前>.sha256` を隣に書く
- **zip の中身と、展開したディレクトリで一致するダイジェスト**を用意する。
  「コンテナの中の写し」「Mac の写し」「zip の中の写し」を**比べられるようにする** ——
  写しはずれるし、直されるのはそのうち 1 つだけである
- **遅い転送の前に、実際に何が違うのか見る。**今回、9.4 GB の候補 2 つの差は
  **72 KB のファイル 1 つ**だった
- **成果物がソースの控えになるのは、残しているときだけ。**0 バイトになったソースは、
  検査を通した zip から取り出して復元できた。**あれは運であり、
  「良いと分かっている zip を 1 つ残しておく」理由になる。**

## 9. 未決事項の一覧は 1 枚。決着は消さずに残す

作業が何日にもまたがり、相手から「抜けている」と言われるようになる原因は、
**状態が会話の中にあること**である。規則を付けてファイルへ移す。

- **未決事項の一覧は 1 枚（`open_items.md`）。「次に何をするか」だけを持つ。**
  先頭に表（項目・担当・見積り・なぜ今）、それ以外は置かない
- **根拠は別ファイルへ、項目番号で。**測った値と決着した項目の詳細は、
  放っておくと一覧を埋め尽くす
- **手順は `howto/` へ。一覧からは節番号で指す。**一覧に書いてよいのは 1 行で終わるコマンドだけ。
  **複数行の手順を一覧に貼ると手順書と二重になり、片方が古くなる**
- **項目は書き換える。行を足さない。**増える一方の一覧は記録であって、次の一手の表ではない
- **終わった項目は消さずに「決着済み —— 見なくてよい」節へ移す。**
  蒸し返しを防ぐだけでなく、**自分が撤回した結論が見える形で残る。**
  相手が「こちらをどの程度信用してよいか」を測るのに、それが要る
- **報告していない作業は、既定で「手を付けていない」と扱い、そう言う。**
  既定は悲観側に置く
- **質問する前に、その質問の費用を言う。**情報集めは無料ではない ——
  提出上限についての問い合わせは、**訊くとルールが厳しくなる恐れがあった**ので
  取り下げたのが正しかった

## 10. ディスクと CPU も事務仕事である

**このプロジェクトでいちばん時間を失った事故は 2 件とも資源の事故で、
2 件とも静かだった。**

**ディスクが満杯だと、書いている途中のファイルが壊れる。**
`pathlib.Path.write_text()` は**書く前に中身を切る**ので、そこで `ENOSPC` になると
**元の中身は消え、新しい中身も入らない。**今回これでソースが 0 バイトになった。

```python
tmp = path.with_suffix(path.suffix + ".new")   # 別の名前で書いて
tmp.write_text(content, encoding="utf-8")
shutil.move(tmp, path)                          # 同じディスク内なら差し替えは一瞬で済む
```

**書く前に、書く量と空きを見比べる。**成果物 1 つが GB 単位のときは必ず。
**それを何個も作るビルドを始める前には、空き容量の数字を見る。**

**小さい機械で重い仕事を並べない。**2 コアの機械で 9.4 GB の zip を 2 つ組みながら
評価を回したら、**評価が餓死した。**ログは行の途中で切れ、コンテナは消えており、
気づいたのは**ユーザーが静かさを不審に思ったから**だった。
**直列にする。できないなら「並行で回した実行の数字は信用できない」と明言する。**

## いつ何をするか

| いつ | 何を |
|---|---|
| **実行の前** | 空き容量と出力見込みを比べる／基準に対して変えた要素は 1 つか／名前が設定を映しているか |
| **始まった時** | 版番号と設定の行が、回収されるログに出ているか |
| **終わった時** | 入力を実行ディレクトリへ写す／要約は回収スクリプトに作らせる／生ログを残す |
| **スコアが返った時** | 台帳に 1 行／採点器のログをファイルに落とす／提出物のハッシュを記録 |
| **空きが減った時** | 動画 → 古い zip → 古いチェックポイント の順に消す。**ログとハッシュは消さない** |
| **機械を返す前** | ログを先に、重みを後に |
| **作業を始める時** | 未決事項の一覧を読む。**新しい提案の前に、手つかずのものを報告する** |

# 06. 歩数が、本番スコアのいちばん強い説明変数だった

**このコンペで最も役に立った発見である。**レポートの「工夫点及び試行錯誤」の柱にする。

## 何が分かったか

**8 エピソードの合計歩数（`POST /act` の回数）と総合スコアが、強い負の相関を示した。**

| 範囲 | 本数 | **相関 r** |
|---|---|---|
| 全提出 | 15 | **−0.868** |
| SmolVLA だけ | 11 | −0.812 |
| π0.5 だけ | 4 | **−0.925** |

出典は [05_score_history.md](05_score_history.md) の表（採点ログ 16 本）。

## 「決める」とは言わない —— 反例がある

| 版 | 歩数 | スコア |
|---|---|---|
| 3.3.0（n=1） | **1,992** | **0.080** |
| 3.4.0（n=2・samples=3） | **1,994** | **0.168** |

**歩数がほぼ同じで、スコアは 2 倍以上違う。**総合スコアには成功判定・衝突・
滑らかさも重み付きで入る（予選 PDF p11）ので当然である。

**正しい言い方は「最も強い説明変数」。**「歩数がスコアを決定する」と書くと
過剰主張になる。**レポートには失格条項が掛かるので、言い過ぎない。**

## なぜ歩数が効くのか

**打ち切りは 300 歩で、方策には余裕が無い。**手元 36 件の測定で、
**成功した回は手本の 0.96 倍の歩数で終わっていた。**
手本が 230〜300 歩のタスクの成功率は 0.29 しかない。

**つまり少し遅くなるだけで、長いタスクが 300 歩を越えて未完了になる。**
未完了はゴール未到達なので、成功判定そのものを失う。

## 歩数と秒数は別の量である —— ここを半日取り違えた

| 量 | 何に効くか | 上限 | 実測 | 余裕 |
|---|---|---|---|---|
| **歩数** | **成功そのもの。**`max_steps=300` で打ち切られる | 1 本 300 歩 | 平均 124 歩（4.2.0） | **ほぼ無い** |
| 秒数 | トラック全体の 1 時間の上限だけ | 3,600 秒 | 110.4 秒（4.2.0） | **32 倍** |

**運営 Q&A No.23 が、スコアの `time` 要素は「エピソード内のシミュレーション
ステップ数に基づく値」であって壁時計時間ではないと明言している。**
先にこれを読んでいれば、取り違えずに済んだ。

## 歩数を悪くする要素

| 施策 | 歩数 | 結果 |
|---|---|---|
| **chunk 継ぎ目の平滑化（`blend_steps=4`）** | **+29%**（1,142 → 1,471） | **本番 0.264 → 0.169** |
| **RTC（`horizon=4`）** | **+39.5%**（手元 12 件で 1,995 → 2,783） | 手元の成功 8 → 4。**提出せずに済んだ** |
| n を小さくしすぎる（n=1） | 1,922 → 1,992 | 0.166 → 0.080 |
| 学習を失敗させる（LoRA 20,000 歩） | **2,173（全記録で最多）** | **0.016（全記録で最低）** |

**blend と RTC は仕組みが同じである。**どちらも「継ぎ目で前の計画へ引き戻す」ので、
**前へ進まなくなる。**別実装で同じ向きに出たので、この軸は閉じた。

> **手元 36 件の成功率では、この悪化を見抜けなかった。**blend4 は手元で
> 25/36 → 28/36 と**良くなって**いた。**歩数で見れば見抜けた。**
> → [07_local_eval_cannot_rank.md](07_local_eval_cannot_rank.md)

## 歩数を良くする要素

| 施策 | 歩数 | 結果 |
|---|---|---|
| **全パラメータ学習（画像を見る側まで解く）** | **−13%**（1,142 → 991） | **本番 0.264 → 0.485** |
| **chunk 長を最適値へ（n=10 → 16）** | **−20%**（1,428 → 1,142） | **0.177 → 0.264** |
| **指示文の正規化** | **−16%**（1,922 → 1,617） | **0.166 → 0.181。重みは 1 ビットも変えていない** |
| モデルを強いものへ（SmolVLA → π0.5） | −19%（1,766 → 1,428） | 0.184 → 0.177（スコアは横ばい） |

**「秒数だけ払って歩数を買う」施策は、事実上ただである。**
`num_inference_steps` と `samples` は推論の秒数しか増やさず、
**環境の歩数を 1 歩も増やさない。**秒数には 32 倍の余裕がある。

## 測り方

```bash
# 採点ログから歩数を数える
grep -c "POST /act" outputs/<採点ログ>.md

# 手元の 2 つの回を歩数で 1 件ずつ突き合わせる
python3 solution/tools/compare_steps.py \
    --base  work/gpu_eval/<基準の回> \
    --other work/gpu_eval/<比べる回>
```

**`compare_steps.py` は「両方が成功した回だけの歩数」も出す。**
打ち切り（300 歩）が混ざると合計が天井に張り付いて読めなくなるためである。

## Claude 側 / 人間側

**Claude 側**: **採点結果を読むときは、スコアだけでなく歩数を必ず数える。**
`grep -c "POST /act"` は 1 秒で済む。今回は 3 回目の提出まで数えていなかった。
**手元評価で施策を比べるときも、成功率の前に歩数を見る。**

**人間側**: **「速い／遅い」を口にするとき、どの量の話かを明示する。**
歩数（成功に効く・余裕ゼロ）と秒数（上限に 32 倍の余裕）を混ぜると、
**正反対の施策を勧めてしまう。**実際に一度、秒数を節約する方向の提案をしかけた。

**両方**: **採点の指標定義は、推測せず Q&A を検索する。**
今回は運営 Q&A No.23 に `time` の定義が書いてあった。

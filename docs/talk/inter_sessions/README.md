# セッション間の依頼のやり取り

**このセッション（施策の優先順位を決める側）が、具体的な作業を別のセッションへ渡すための場所である。**
2026-08-28 に作った。狙いは 1 つ——**1 つのセッションが抱える文脈を減らし、
判断する側が結果だけを読めるようにする。**

## 1 依頼 1 ファイル。往復も同じファイルに書く

`NNN_<英語のスラッグ>.md` という名前にする。番号は通し番号で、使い回さない。

**依頼と報告を同じファイルに置く。** 別ファイルにすると対応付けが必ず崩れる。
ファイルの上から順に「依頼」「報告」と並ぶ。

## 状態はファイルの 1 行目に書く

```
> **状態: 依頼中** ／ 受け側: 未定 ／ 更新: 2026-08-28
```

状態は **依頼中 → 着手 → 報告済み → 閉じた** の 4 つだけ。

**閉じたら消す**（2026-08-31 に「消さずに残す」から変えた）。**ここは一時ファイルの置き場である。**
残す価値のあるものは 1 つずつ行き先が決まっているので、**消す前にそちらへ移す。**

| 報告に入っていたもの | 移す先 |
|---|---|
| 採否の理由・測った値 | `reference/19_weights_catalog.md` |
| 2 回以上打つ手順 | `howto/` に節を作る（1 行で済むものは板の「打つもの」列） |
| 分かったこと・踏んだ穴 | `knowledge/` |
| 追わないと決めたこと | `talk/open_items.md` の「決めた — 蒸し返さない」 |

**移し終わったら、他のファイルからこのディレクトリを指しているリンクを消す。**
`grep -rn inter_sessions docs/` で全部出る。

## 依頼を書くときの決まり

**受け側は聞き返せない。** 別のセッションなので、こちらの会話も、いま何を測っているかも
見えない。だから `decision-request` スキルと同じ前提で書く——**そのファイルだけで作業が終わること。**

**節はこの順に並べる。**

| 節 | 中身 |
|---|---|
| **背景** | **いちばん先に置く。**このコンペが何で、いまどのトラックで何点で、**この依頼がどこに効くのか。**受け側を作業者にしないための節である——**背景が無いと、その場の判断ができず、指示の字面どおりにしか動けない** |
| **何をしてほしいか** | 1〜2 行。**成果物の形**（ファイルか、数値か、判断か）をここで名指しする |
| **なぜ要るか** | この結果が**どの判断を変えるか**。これが書けない依頼は出さない |
| **前提となる事実** | 受け側が知らない数値・ファイルの場所・すでに分かっていること。**リンクではなく本文に書き写す** |
| **やること** | 番号付き。コマンドは省略せずそのまま打てる形で |
| **できあがりの条件** | 何が揃ったら終わりか。**受け側が自分で判定できる形にする** |
| **やらなくてよいこと** | 範囲を広げさせないために書く |
| **報告の書き方** | 数値の並べ方の指定。**長い説明は要らない、表と数値がほしい** |

**背景の節に必ず入れる 4 つ。**

1. **どのトラックの話か**（3 つあり、対策が違う）
2. **いまの点と、リーダーボードの最高点**
3. **どのデータで測るのか**——その集合が何行で、どう作られたものか
4. **すでに分かっていること・すでに外したこと**（同じ道を二度歩かせないため）

**そして最後に「判断が必要になったら」を 1 段落。** この依頼が**どの判断を変えるためのものか**を
書き、**その目的に照らしてより良い測り方を思いついたら変えてよい**と明示する。
**変えた場合は理由を報告に書いてもらう。**

## 受け側が守ること

- **範囲は広げないが、測り方は目的に照らして判断してよい。** 気づいたことのうち
  実行しなかったものは「報告」の末尾に 1 行で書く。
- **`docker run` はこのマシンでは通らない**（組織の制約・解除不可）。既に起動しているコンテナへの
  `docker exec` は通る。GPU の評価は会社の RTX6000 でユーザが回す。
- **`NOW.md` は書き換えない。** 書き換えるのはユーザである。
- 報告には**実測値と、それを出したコマンドかファイルの場所**を必ず添える。

## 1. `train_pi05.py` のマウントについて

**イメージの作り直しは要らない。別の手順も要らない。** お送りしたコマンドの中の
この 1 行が、そのままマウントである。

```
-v "$PWD/solution/train/train_pi05.py:/opt/pi05/train_pi05.py:ro"
```

**`-v ホスト側:コンテナ側:ro` は、コンテナを起動する瞬間にホストのファイルを
コンテナの中のパスへ重ねる指定である。** イメージの中には `docker build` の時点の
古い `train_pi05.py` が焼かれているが、**この行があると起動時にホスト側の版で
上書きされて見える**（`:ro` は読み取り専用の意味で、コンテナ側から書き換えられない）。
イメージそのものは 1 バイトも変わらない。

**なぜ必要か。** 8/26 に私がホスト側の `train_pi05.py` へ 2 つ手を入れた
（`RandomPerspective` を拡張の種類に足した・誤った注記を直した）。**イメージの中の
版にはその変更が入っていない**ので、マウントしないと拡張が 7 種のまま回る。

**効いているかの確かめ方。** 学習の最初の出力に拡張の設定が出る。
`camera_perspective` という語が含まれていればホスト側の版が使われている。

```
docker logs parc-train-aug 2>&1 | grep -o "camera_perspective" | head -1
```

## 2. なぜ 1 本ではなく 2 本なのか

**1 本だけ回すと、何と比べても「1 つだけの違い」にならない。** ここがいちばん大事な点である。

**今日の学習は、4.2.0 の重みから続ける形になる。** その 4.2.0 と比べると、違いが 3 つ
同時に入る ── (a) 学習を足したこと、(b) 動かす範囲が違うこと（後述の
「行動を出す側だけ」）、(c) 画像拡張を入れたこと。**上がっても下がっても、
どれが原因か言えない。**

**だから同じ条件で拡張だけを外した 2 本目（対照）を回す。** そうすると、
**今日 1 日で「1 つだけ違う」比較が 2 つ手に入る。**

| 比べる 2 本 | 違う点の数 | 何が言えるか |
|---|---|---|
| **腕 A（拡張あり）対 腕 B（拡張なし）** | **1 つ（画像拡張だけ）** | **画像拡張の効果。これが今日の目的である** |
| **腕 B（拡張なし）対 4.2.0** | **1 つ（学習を足したかどうか）** | 行動を出す側だけの継続学習に伸びしろがあるか |
| 腕 A 対 4.2.0 | **2 つ** | **読んではいけない。**学習の追加と拡張が混ざっている |

**腕 A と腕 B は、乱数の種・ステップ数・学習率・バッチ・データ・初期重みまで
すべて同じにする。違うのは `--camera-viewpoint-augment` を付けるかどうかだけである。**

**3 時間ずつに割る理由。** 6 時間を 1 本に使うと対照が取れず、上の表の 1 行目が
作れない。**半分にしても、予選で本番スコアを 0.264 → 0.485 まで動かした 2 段目の学習は
3,000 ステップだった**ので、3 時間でその水準には届く見込みがある（4 節の表）。

| 途中の評価 | 無し（`env_eval_freq=0`） | 学習中にシミュレータを回さない |
| 記録の間隔 | 20 ステップごと | 既定 |
| W&B | 無効 | 既定 |

### 方策そのものの形（初期重みから引き継ぐので変えない）

| 項目 | 値 |
|---|---|
| 塊の長さ（`chunk_size`） | 50 |
| 学習側の `n_action_steps` | 10（**1 段目・2 段目も 10 だった。学習には効かない** ── 下記） |
| `empty_cameras` | 1 |
| 正規化 | 行動と状態は平均・標準偏差、画像はそのまま |
| 画像と行動の形 | 画像 [3,256,256] × 2 ＋ 空 1・状態 8・行動 7 |

**学習側の `n_action_steps` が効かない根拠。** データの取り方も損失の計算も
`chunk_size`（50）で決まっていて、`n_action_steps` を参照していない。

| 場所 | 何が使われているか |
|---|---|
| データローダが未来の行動を何歩ぶん引くか | `action_delta_indices` が **`range(chunk_size)`** を返す（`configuration_pi05.py:170-171`）。**50 歩ぶん引く** |
| 損失を計算する範囲 | `suffix_out[:, -chunk_size:]`（`modeling_pi05.py:781, 906`）。**50 歩ぶん全部** |
| `n_action_steps` が出てくる場所 | **`select_action` の行動キューだけ**（`modeling_pi05.py:1128-1232`）。作った 50 歩のうち先頭から何歩使うかを決める |

**つまり学習側の値が 10 でも 20 でも、でき上がる重みは 1 ビットも変わらない。**
提出時は環境変数で 16 に上書きしているが、上書きが効くのは推論だけなので矛盾しない。
**チャンク長を変えて試すために学習をやり直す必要は無い** ── 50 歩ぶんは常に学習されており、
そこから何歩使うかは提出時に選ぶだけである。

### 画像拡張（腕 A だけに付ける唯一の違い）

**`--camera-viewpoint-augment` を付けると、次の 8 種から毎フレーム最大 4 種が
掛け合わされる。** 付けなければ拡張は 1 つも掛からない（`enable=false`）。

| 種類 | 中身 | 何の摂動に対応させたか |
|---|---|---|
| 明るさ | 0.8〜1.2 倍 | Light Conditions |
| コントラスト | 0.8〜1.2 倍 | 同上 |
| 彩度 | 0.5〜1.5 倍 | 見た目 |
| 色相 | ±0.05 | 見た目 |
| 鮮鋭度 | 0.5〜1.5 倍 | Sensor Noise（ぼけ）の近似 |
| アフィン変換 | 回転 ±15°・並進 12%・拡縮 0.82〜1.22 | Camera Viewpoints の拡縮と並進 |
| ランダムクロップ＋ズーム | 面積 75〜100% を切って 256×256 に戻す | 同上 |
| **台形のゆがみ（8/26 に追加）** | 四隅を最大 25% ずらす | **Camera Viewpoints の回転。テーブル面に限れば厳密に対応する** |

**台形のゆがみを足した理由。** これまで「3 次元の視点回転は 2 次元変換では再現できない」と
書いていたが誤りだった。それは平行投影の話で、**実際のカメラは中心投影なので、
テーブル面という 1 枚の平面に限れば台形のゆがみはカメラの回転と厳密に一致する。**
壊れるのは高さのある物体の見え方の分だけである。

**注意が 1 つある。** 拡張はカメラごとに独立に掛かるので、**手首のカメラにも台形のゆがみが
掛かる。** 手首のカメラは評価で視点をずらされないので、これは本来要らない変形である。
**掴む直前の位置合わせを乱す恐れがある**が、場面カメラだけに掛けるには改修が要るので、
今日は両方に掛けたまま測る（6 節）。

**本番と同じバッチ 8 で 30 ステップだけ回す。保存はしない。** ここで
`--init-from` が通るか、台形のゆがみが構成できるかも同時に分かる。


**【8/26 実測・この手順は済んでいる】**

| 測った値 | 結果 |

**`vlm/` が無いと評価は 5 秒で落ちる。** 学習の出力には `vlm/` が入らないので、

```

      work/train/stage3_aug/checkpoints/<最後のステップ>/pretrained_model/
```

**判定の基準。** 手元は 8 件しかないので、**1 件分に満たない差は読まない。**
比べる相手は 8/25 に測った 4.2.0 の結果（**成功 6/8・衝突で失敗 2 件・300 打ち切り 0 件**）である。

| 見る量 | 何を意味するか |
|---|---|
| **成功の件数** | 壊れていないことの確認。**6/8 を大きく下回ったら、その腕は捨てる** |
| **衝突で失敗した件数** | 4.2.0 は 2 件だった。**増えていたら拡張が掴みを荒らした証拠**（3 節の手首カメラの注意） |
| 300 打ち切りの件数 | 4.2.0 は 0 件。増えていたら遅くなっている |
| 成功した回の歩数 | 本番スコアのいちばん強い説明変数 |

**8/28 の RunPod での判断はこうする。**

| 腕 A（拡張あり）と腕 B（拡張なし）の比較 | 8/28 の全パラメータ学習にどうするか |
|---|---|
| A が B より良い、または同じ | **拡張を入れる** |
| A が B より明らかに悪い（成功が減る・衝突が増える） | **拡張を外す。**または強さを半分にして測り直す |
| どちらも 4.2.0 より悪い | **継続学習そのものを見直す。**学習率かバッチが合っていない疑い |

## 6. 今日の限界（正直に）

**今日の結果は「拡張が壊さないか」までしか言えない。** 理由は 2 つある。

**(1) 画像を読む側が凍結されている。** 20 GB では全パラメータ学習が載らないので、
今日は行動を出す側だけを学習する。**画像拡張が本来効く仕組み（画像を読む側そのものが
摂動に慣れる）は、今日は働かない。** 今日効くのは「凍結された変換器の出力が揺れることに、
行動を出す側が慣れる」という別の筋である。**8/28 の全パラメータ学習では効き方が変わる。**

**(2) バッチが 8 で、4.2.0 の 64 と違う。** 2 本で同じなので今日の比較は成立するが、
**8/28（バッチ 64 の見込み）へそのまま移せる保証はない。**

**それでも今日やる価値がある。** 8/28 の全パラメータ学習は 1 回きりで費用もかかる。
**そこへ入れる要素のうち、唯一「入れると悪くなりうる」のが画像拡張である。**

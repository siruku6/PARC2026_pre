## 1. なぜ物差しを足したか —— 4 条件を満たしたデータに残っていた 2 つ

**028 の 6 節の 4 条件は「上限ちょうどに積み上がっていないか」だけを見る。**
[33](33_gradient_norm_and_action_saturation.md) が示したとおり、1 点に積み上がった
教師信号は学習で解けないので、この 4 つは必要である。**ただし十分ではない。**

**028 の作り直し（`work/probe_028/L`・9/11）は 4 条件をすべて満たしている。**
そこへ**配布データと同じ物差しをもう 3 つ当てると、差が残っていた**（2026-09-11 実測。
配布は `libero_plus` 無作為 200 本、自作は本タスクの 3 本）。

| 見るもの | 配布データ | **028 版** | 何を意味するか |
|---|---|---|---|
| ① 並進 ±1.000 ちょうど | 0.00% | **0.00%** | 028 が直したところ |
| ② 並進 ±0.9375 以上 | 7.43% | **0.00%** | 直りすぎ（配布より遅い側に外れている） |
| ③ 回転 ±0.375 ちょうど | 0.62% | **0.00%** | 同上 |
| **停止の塊**（`\|u_trans\| < 0.02` が続く区間の数） | **0.8 個/本** | **6.7 個/本** | **指令が 0 に落ちて立ち上がり直す回数** |
| **立ち上がり**（`\|u\|` が 0.2 に達するまで） | **1 コマ** | **8 コマ** | **エピソードの頭がほぼ空の列である** |
| 並進 `\|u\|` の中央値 | 0.587 | 0.472 | 配布より遅い |

**「1 点への積み上がり」は 0 の側にも起きる。**028 は `±0.375` の 1 点を潰したが、
**代わりに 0 付近へ積み替えていた**（停止コマが 1.05% → 4.21%）。
勾配が急に切り替わる点という意味では、上限の 1 点と 0 の 1 点に違いはない。

**立ち上がりのほうが重い。**Track3 の症状は
「学習データと同じ初期状態から回しても、記録の経路の 1〜4% しか辿れない」
（[knowledge/21 の 3.5](../knowledge/21_track3_stops_short_of_the_object.md)）である。
**手本の頭 8 コマが「ほぼ何もしない」列なら、方策はまず「動かない」を学ぶ。**
動かなければ観測も変わらないので、次のコマもまた「動かない」になる。

## 2. 停止と立ち上がりの正体 —— 5 次多項式の両端条件

**原因は制御の当て方ではなく、`w(s) = 10s³ − 15s⁴ + 6s⁵` という形そのものである。**
この重みは**両端で速度も加速度も 0** になる。つまり:

- **区間ごとに必ず止まる。**`rollout_phased` は 1 サイクルを 7 区間
  （手前へ・掴む姿勢へ・閉じる・持ち上げ・復路・下ろす・引く）に割るので、
  **止まる回数が区間の数だけ増える**（実測 6.7 個/本）。
- **頭で加速度も 0 なので、指令が育つのに何コマもかかる。**

**なめらかさは OSC がすでに持っている。**`control_delta=True` の OSC は位置サーボで、
1 コマの挙動は次の 2 式でよく近似できる。

```
u[t]       = clip((p_ref[t+1] − p_arm[t]) / OUT_MAX, ±1)
p_arm[t+1] = p_arm[t] + response × u[t]
```

閉ループ利得は `response / OUT_MAX = 0.0128 / 0.05 = 0.256`（時定数 3〜4 コマ）。
**配布データの立ち上がり `0.15 0.21 0.34 0.48 0.58 0.69 …` は、
1 コマ目から全速の指令を出したときのこのサーボの応答そのものである**
（`0.9 × (1 − 0.744^k)` が `0.23 0.40 0.53 0.62 …` を返す）。

**5 次多項式は、サーボが持っているなめらかさの上にもう一段かけていた。**
その二重掛けが、頭の 8 コマと 6.7 個の停止として出ている。

## 3. Ruckig で何が変わるか —— 実測

**Ruckig が 5 次多項式と違うのは 2 点だけである。**

1. **入口と出口の速度・加速度を指定できる。**止まる必要のない継ぎ目で止まらない。
2. **時間最適である。**「速度の山が平均の 1.875 倍」という 5 次多項式の損を払わない。

**単位の取り方が肝である**（[34 の 4.3](34_trajectory_regeneration_toolchain_survey.md) の
指摘どおり、行動の単位を先に固定する）。位置を「指令 1 単位ぶんの移動量」で割った
座標に取り、時間の単位を 1 コマに取る。**こうすると Ruckig の速度がそのまま
OSC の指令になる**ので、上限を換算せずに `max_velocity` へ渡せる。
自由度は 4 つ——並進 3 軸と、**回転の測地線 1 軸**。Ruckig が 4 つを時間同期する。

### 3.1 封筒は配布データから測って置いた

**上限だけでなく 1 階差分・2 階差分まで配布データから測る。**
指令が 1 コマでどれだけ変われるかを決めるのがこの 2 つで、
**立ち上がりの速さはここで決まる。**（`libero_plus` 無作為 400 本・61,373 コマ）

| | p50 | p95 | **p99（封筒に採った値）** | p100 |
|---|---|---|---|---|
| 並進 `\|u\|` | 0.592 | 0.9375 | — | 0.9375 |
| 回転 `\|u\|` | 0.055 | 0.194 | — | 0.375 |
| 並進 `\|Δu\|` | 0.051 | 0.171 | **0.252** | 0.836 |
| 回転 `\|Δu\|` | 0.009 | 0.031 | **0.051** | 0.156 |
| 並進 `\|Δ²u\|` | 0.032 | 0.118 | **0.185** | 0.788 |
| 回転 `\|Δ²u\|` | 0.006 | 0.028 | **0.046** | 0.257 |

### 3.2 シムを回さずに見た形（1 次サーボ近似・摘みを絞るため）

`compare_waypoint_profiles.py` は 2 節の 2 式で指令を作り、逆向きデモの
1 サイクル（7 区間）を 40 本ぶん合成して比べる。**合否はシムで測るが、
出口に残す速さのような摘みはここで絞れる。**

| 出口に残す速さ | 停止の塊 [個/本] | 立ち上がり [コマ] | コマ数 中央 |
|---|---|---|---|
| 5 次多項式（028） | 6.3 | 6 | 139 |
| Ruckig・**0.00** | 5.2 | **2** | 109 |
| Ruckig・**0.25** | **0.0** | **2** | **103** |
| Ruckig・0.50 | 0.1 | **2** | 103 |

**読み方が 2 つある。**

1. **立ち上がりは出口の速さと無関係に直る。**区間の頭で加速度を 0 に
   固定しないことだけで 6 コマ → 2 コマになる。
2. **停止の塊は出口の速さを残さないと直らない。**0.00 では 5.2 個のまま
   （区間ごとに止まるのは変わらない）。**0.25 で消える。**

**既定を 0.25 にした。**0.50 は封筒の端に触り始める（`±0.9375 以上`が
5.92% まで上がる）ので、内側に取れる 0.25 を採る。

### 3.3 シムの実測 —— 本タスク 3 本を、通過点の作り方だけ変えて回した

**1 変数だけの比較である。**`run_ruckig_replay.sh` で `MOTION_PLANNER` を
`minjerk` / `ruckig` に振り替えただけで、他の環境変数は
[30 の 9 節](30_reverse_grasp_pose.md)の `COMMON`（本タスク・`T3_INIT=0`）と同じ。

| 見るもの | 配布 | 028 版 | **共有 minjerk**（検算） | **Ruckig** |
|---|---|---|---|---|
| ① 並進 ±1.000 ちょうど | 0.00% | 0.00% | 0.00% | **0.00%** |
| ② 並進 ±0.9375 以上 | 7.43% | 0.00% | 0.00% | **0.00%** |
| ③ 回転 ±0.375 ちょうど | 0.62% | 0.00% | 0.00% | **0.00%** |
| ④ コマ数 中央 / 最長 | 136 / 401 | 274 / 320 | 274 / 320 | **263 / 307** |
| **停止の塊** | **0.8 個/本** | 6.7 個/本 | 6.7 個/本 | **3.7 個/本** |
| 停止コマ | 1.05% | 4.21% | 4.21% | **2.20%** |
| **立ち上がり** | **1 コマ** | 8 コマ | 8 コマ | **2 コマ** |
| 符号反転 並進 | 0.14% | 0.46% | 0.46% | 0.57% |

**課題としての出来。**

| 見るもの | 028 版 | **Ruckig** |
|---|---|---|
| 逆向き goal | **3 / 3** | **3 / 3**（変わらず） |
| 接近に要したコマ | 56 / 56 / 57 | **45 / 45 / 45**（−20%） |
| 掴む姿勢との誤差 | 4.57 / 4.54 / 4.64 mm | **3.57 / 3.47 / 3.62 mm**（改善） |
| 放したあとの落下 | 2.1 / 3.7 / 0.9 mm | 2.7 / **8.6** / 0.9 mm |
| 放すときの傾き | 7.2 / 4.3 / 3.3° | 7.3 / 4.4 / 3.3° |

**読み方が 3 つある。**

1. **028 の 4 条件は保ったまま、停止と立ち上がりが直った。**
   立ち上がりは 8 → **2 コマ**で、配布データ（1 コマ）にほぼ並ぶ。
2. **速くなって、しかも正確になった。**接近が 20% 短く、掴む姿勢との誤差は
   1 mm 小さい。**5 次多項式の「山が平均の 1.875 倍」という損を払わないぶん、
   同じ封筒でより多くの距離を稼げる**からである。
3. **1 本で落下が 3.7 → 8.6 mm に増えた**（ep4062）。goal は通っているが、
   **置く直前が速くなったぶん、放す高さが上がっている見込みがある。**
   本数を増やすときは D 段（`settle`）だけ `MOTION_EXIT_SPEED=0` にするか、
   落下の測り値で見張ること。

**停止が 0 にならないのは、通過点の作り方ではなく区間の並べ方が原因である**
（[6.2 節](#62-残る停止は-rollout_phased-の作りのほうにある)）。
ep4061 の塊を並べると、消えたものと残ったものがはっきり分かれる。

| | 028 版 | Ruckig |

**消えたのは「頭」と「掴む → 持ち上げ」である。**残っているのは指の開閉と
接触を探る下ろしで、**これは配布データにもある停止である。**

## 4. 共有モジュールの形 —— `motion` パッケージ

**置き場は `solution/tools/motion/` である。**026・028・`scripted_demo` の

|---|---|
| `envelope.py` | 配布データから測った指令の封筒（3.1 節の表） |
| `rotation.py` | 姿勢の回転の約束（**world 合成の軸角**）。robosuite があれば使う |
| `waypoints.py` | **028 の 5 次多項式・記録の割り直しを切り出したもの** |

### 4.1 026 と 028 のファイルには 1 行も書き込んでいない

**差し替えは実行時に行う。**`track3_ruckig_replay.py` が
`replay_video_probe` の 3 か所を包んでから `gripper_shift_sweep.py` を呼ぶ。

| 包むもの | 何をするか |
|---|---|
| `_approach_waypoints` | 通過点を Ruckig 版に替える（`MOTION_PLANNER=minjerk` で 028 と同じ列に戻る） |
| `osc_command` | **指令の作り方には触らず、撃つ前の腕の姿勢だけ生成器へ渡す** |
| `rollout_phased` | エピソードの頭で持ち越しを捨てる |

**`osc_command` を包む理由。**区間の切れ目には比例制御の詰めが数コマ挟まり、
指を閉じるあいだは止まっている。**そこで「計画上の速度」を持ち越すと嘘になる。**
実測の姿勢から速度を出せば、止まっている継ぎ目ではちゃんと 0 から始まり、
流れている継ぎ目では流れたまま続く。**Ruckig の本来の使い方（毎周期、いまの
状態から組み直す）に近い形である。**

### 4.2 切り出した 5 次多項式が 028 と同じであることの確かめ方

**共有化そのものが 028 の結果を静かに変えていないか**を 2 段で見ている。

| 段 | 見るもの | 結果 |
|---|---|---|
| 関数の単位 | 無作為 200 組の姿勢で `_approach_waypoints` と比べる | **位置は完全一致。**向きは robosuite が内部で float32 に落とすぶんだけ最大 **1.5e-6 rad**（＝8.5e-5 度。到着判定の許容は 5 度） |
| シムを通して | 同じ 3 本を `MOTION_PLANNER=minjerk` で作り直す | **コマ数は 274 / 320 / 261 で 028 と 1 コマも違わない。**1 節の物差し 13 項目すべて同値。指令は最大 3.5e-3 違う（上の 1.5e-6 が閉ループで開くぶん） |

## 5. 34 の記述で当たらなかった 1 点 —— `update()` は Community でも使える

**[34 の 4.1](34_trajectory_regeneration_toolchain_survey.md) の機能表は
「軌道を 1 歩ずつ進める `update()` は Pro のみ」と書いているが、
`pip install ruckig`（0.19.4・MIT）で `update()` は動く。**
実測（2026-09-11、`parc2026-final` の中）:

| 呼び方 | Community 0.19.4 | 外部通信 |
|---|---|---|
| `Ruckig(dofs, dt).update(inp, out)` のループ | **動く** | **無し** |
| `Ruckig(dofs).calculate(inp, traj)` | **動く** | 無し |
| `inp.intermediate_positions` を付ける | 動く | **`[ruckig] calculate trajectory via cloud API.` と出る** |

**34 の警告そのものは正しい**——**中間経由点だけがクラウド API に化ける。**
`otg.py` は state-to-state しか使わないので、そこには触れない。
**`--network none` のコンテナで通過点が出ることを確かめてある。**

**イメージには焼いていない。**`parc2026-final` は 69 GB あるので、
ホストへ `--target` で入れたものを読み取り専用で挿す。

```bash
pip install --target work/vendor_py310 --python-version 310 \
    --only-binary=:all: --platform manylinux_2_28_x86_64 ruckig
```

**`ruckig` が無くても落ちない。**`otg.py` は自前の S 字プロファイルに落ちる
（時間最適ではないぶん数コマ長いが、停止と立ち上がりは同じように直る）。

### 6.2 残る停止は `rollout_phased` の作りのほうにある

Ruckig を入れても停止が 0 にはならない。**残るのは通過点の作り方ではなく、
区間の並べ方が持っている停止である。**

| 残る停止 | 場所 | 直すなら |
|---|---|---|
| 指を閉じる `grip_hold`（10 コマ） | B 段 | **配布データにもある**（掴む所で 1 回・最長 8 コマ）。触らなくてよい |
| 指を開く `grip_hold`（10 コマ） | D 段のあと | **配布データは開きながら動いている。**削る余地がある |
| 5 mm ずつ下ろす `settle` | D 段 | 接触を探る動きなので遅いのは必然。**下ろし始めを早める余地はある** |

### 6.3 (A) の再生成（`work/regen/npz_batch1`）にも同じ物差しが当たる

**同じ物差しを [plan/23](../plan/23_data_regeneration_design.md) の (A) が作った
1,009 本にも当ててある**（先頭 120 本）。**028 の逆向きより健全だが、
配布データからは外れている。**

| 見るもの | 配布 | 028 逆向き | **(A) 再生成** |
|---|---|---|---|
| ③ 回転 ±0.375 ちょうど | 0.32% | 0.00% | **1.56%** |
| 停止の塊 | 0.8 個/本 | 6.7 個/本 | **1.6 個/本** |
| 立ち上がり | 1 コマ | 8 コマ | **3 コマ** |
| コマ数 中央 | 134 | 274 | **261** |

**(A) は `_smoothed`（前のコマとの指数移動平均）で躍度を下げているので、
停止と立ち上がりは 028 ほど悪くない。**ただし**回転が配布の 5 倍、上限に
乗っている**のと、**コマ数が配布の 2 倍**なのは残っている。
`scripted_demo.py` の `_velocity_command` は「いちばん大きい軸がちょうど
振り切れる大きさに揃える」作りなので、**遠い区間では必ず上限を出す。**
封筒を `envelope.py` に合わせるだけで③は下がる見込みがある（未実施）。

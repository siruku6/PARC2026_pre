# 低精度化で速くなる条件と、評価が何で律速されているか

**これを読むと、「量子化すれば速くなる」がこのリポジトリで試した5候補すべて空振りだった
理由が分かり、次にどこを速くすべきかが決まる。** 2026-08-23 に実測と一次情報で確定した。
**唯一速くしたのは量子化ではなく `torch.compile` である。**

| [学習と推論の違い](#学習と推論では上限になっているものが違う) | 何が上限か、効く手が違う |
| [評価の内訳](#手元の評価は方策ではなく-cpu-描画で律速されている) | 方策は壁時計の18〜29%だけ |
| [Colab が効く理由](#colab-では描画が-11-倍速いので方策の高速化が初めて意味を持つ) | 律速が入れ替わる |

## 低精度化が速さになる条件は 3 つあり、1 つ欠けると効果がゼロか逆になる

| 条件 | 満たさないとどうなるか |
|---|---|
| **1. 重みと、層に入ってくる値（活性）の両方を低精度にする** | 重みだけだと掛け算は元の精度に戻して行われるので、**計算量が1つも減らない** |
| **2. torch.compile を掛ける** | 元の精度へ戻す処理が別の処理として残り、**元の精度より遅くなる** |
| **3. 全体の秒数に占める割合が大きい場所に掛ける** | 割合が上限になる。1%の場所を2倍速くしても全体は0.5%しか速くならない |

このリポジトリで実際に起きたことを、この3条件で並べるとこうなる。

| 試したもの | 条件1 | 条件2 | 条件3 | 実測 |
|---|---|---|---|---|
| **学習 C0+compile（低精度化なし・compile だけ）** | **✗** | **○** | **○** | **-53.6%（0.650 秒/step）** |
| 学習 C3+compile（float8、action expert） | ○ | ○ | ○ | -53%（0.659 秒/step。**float8 の寄与はゼロ**） |
| 学習 C3（compile なし） | ○ | ✗ | ○ | +10.4%（遅化） |
| 推論 C4（bnb 4bit、vision encoder） | ✗ | ✗ | ✗ | +13.7%（遅化） |
| 推論 C5（torchao int8、vision encoder） | ✗ | ✗ | ✗ | -0.6%（実質ゼロ） |

**この表でいちばん速いのは、低精度化を1つもしていない行である。** 効いていたのは条件2
（torch.compile）だけだった。**推論側の2つは3条件を1つも満たしていない。** vision encoder は
推論1回の63回の計算（画像の符号化3回 ＋ action expert 20回×3）のうち3回にしか当たらない。

> **学習の -53% は量子化の効果ではなく torch.compile の効果である。** 2026-08-23 に対照
> （`C0+compile`、float8 を外して compile だけ）を 200 歩・batch 16 で測ったところ
> **0.650 秒/step・11.86 GB** で、`C3+compile` の 0.659 秒/step・11.86 GB と、速度は
> ばらつきの中（9 点が 0.648〜0.661）・メモリは完全一致だった。**「-27% のメモリ削減」も
> compile の効果で、float8 は速度もメモリも動かしていない**（float8 単体の C3 は 16.26 GB
> で、量子化なしの 16.27 GB と同じ）。torchao 公式が報告する float8 学習の高速化は
> H100・Llama3-8B で 10〜25%、規模の上限の主張でも 1.25 倍で、**-53%（2.1倍）は
> float8 では説明できない。** 公式自身が「行列が小さいと1倍を下回る」と書いており、
> 実測の +10.4%（遅化）と整合する。

## 学習と推論では、上限になっているものが違う

**「推論の低精度化のほうが易しい」という一般論は、条件付きである。**

| | 学習 | 推論 |
|---|---|---|
| 何が上限か | 行列が大きい（バッチ×トークン数）→ **計算量** | 場合による。1件ずつ小さく回すと**重みを読み込む速さ**やCPUの指示出しが上限 |
| 効く手 | 重みと活性の両方を低精度にする（これしかない） | **2種類ある。** (a) 重みだけ＝読み込みが上限のときだけ効く (b) 両方＝計算量が上限のときに効く |
| torch.compile | 推奨（無いと逆に遅い） | **事実上必須**（無いと (a) は元の精度より遅い） |

**「推論のほうが易しい」は (a) の話で、大きな言語モデルを1トークンずつ生成する場面を
指している。** π0.5 は 224×224 の画像を3枚まとめて通す（`policy_server.py:1285-1286` が
`front`・`wrist` の2枚を渡し、`config.json` の `empty_cameras=1` が3枚目を0埋めで足す）。
1トークンずつではなく画像1枚ぶんのトークンをまとめて掛けるので行列が太く、
読み込みではなく計算量が上限になる。だから「重みだけ小さくする」は空振りになる。

**π0.5 の推論で低精度化するなら (b) を選ぶ。** `Float8DynamicActivationFloat8WeightConfig`
（重みと活性の両方を fp8）を `language_model` + `gemma_expert` に compile 有りで掛ける。
要件は compute capability 8.9 以上（H100 は 9.0 で満たす。**Colab では L4 以上が必要で、
T4（7.5）と A100（8.0）は満たさない**）。**未試行である。**

## 手元の評価は、方策ではなく CPU 描画で律速されている

`n_action_steps` は推論と推論の**間隔だけ**を変える設定値なので、同じ重み・同じ日の3本から
`1環境stepの秒数 = S + T/n` を解けば、推論1回の秒数とそれ以外を分離できる。

| n_action_steps | 1環境stepの秒数 | 出典 |
|---|---|---|
| 10 | 475.8 ms | `work/gpu_eval/0814_091240_pi05_24k_n10_ep1_max300/eval.log` |
| 16 | 471.0 ms | `work/gpu_eval/0814_113657_pi05_24k_n16_ep1_max300/eval.log` |
| 32 | 455.4 ms | `work/gpu_eval/0814_145933_pi05_24k_n32_ep1_max300/eval.log` |

**T（推論1回）= 291 ms、S（それ以外）= 449 ms。** 本番設定
（`num_inference_steps=20  samples=3`）では T は 1.5〜2.4 秒で、16環境stepに1回なので
割り戻して1環境stepあたり 95〜151 ms。

| 内訳 | 1環境stepあたり | 割合 |
|---|---|---|
| 方策の推論 | 95〜151 ms | **18〜29%** |
| シミュレータ＋描画＋通信 | 366〜418 ms | **71〜82%** |
| 合計（2026-08-23の36件評価の実測） | 513 ms | 100% |

**7〜8割は CPU での描画である。** このマシンの vGPU は `NVIDIA Virtual Compute Server`
（計算専用で OpenGL 非対応）なので、`solution/tools/eval/run_docker_eval.sh` は
`MUJOCO_GL` の既定を `osmesa`（CPU 描画）にせざるを得ない。`nproc` は 2 で、
評価中の負荷は 1.95 ——2コアが埋まっている。

**したがって、このマシンでは方策をどれだけ速くしても評価は最大3割しか速くならない。**

| 施策 | 1環境step | 36件の評価1本 |
|---|---|---|
| 現状 | 513 ms | 約51分 |
| serve 時の compile（実測7.16倍。推論 95→13 ms） | 431 ms | 約43分（-16%） |
| 推論を無限に速くした場合（理論上限） | 366〜418 ms | 36〜42分（-18〜-29%） |

## Colab では描画が 11 倍速いので、方策の高速化が初めて意味を持つ

`docs/howto/11_colab_eval.md` の実測によると、Colab で EGL（GPU 描画）が正しく効くと
`env.step` は **431.8 ms から 38.6 ms** になる。**描画が律速から外れるので、
方策の推論が律速になる。**

| | このマシン（osmesa） | Colab（EGL） |
|---|---|---|
| 描画ほか | 366〜418 ms | 数十 ms |
| 方策の推論 | 95〜151 ms | 95〜151 ms（同じ） |
| **どちらが律速か** | **描画** | **方策** |
| 方策を7.16倍速くしたときの効果 | -16% | 律速そのものを削るので効果が大きい |

**この関係が、量子化と compile の位置づけを変える。** このマシン単体では
「推論を速くしても行き先が無い」が、Colab で回すなら「推論の速さがそのまま評価の本数に
なる」。**推論側の低精度化と serve 時の compile は、廃止ではなく Colab 待ちである。**

> 同じ資料は Track1（SmolVLA・`n_action_steps=5`）の実測で、Colab 110秒/本 対
> GPUマシン 98.6秒/本 と「差が消える」と結論している。**`n_action_steps=5` では
> 推論が 60回×0.85秒で支配的だったためで、上の表と同じ理由である。**
> Track2（π0.5・`n_action_steps=16`）では推論の頻度が3分の1なので、同じ数字にはならない。

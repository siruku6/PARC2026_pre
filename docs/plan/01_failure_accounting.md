# 01. 失敗の内訳を数える — ゴール到達・衝突・動き

**成功率だけでは打つ手が決まらない。** 採点の成功は
「LIBERO の成功条件を満たし、**かつ**操作対象以外の物体を 1mm 超動かしていない」
ことなので（[pipeline/rollout.py](../../pipeline/rollout.py) の
`success = bool(done) and not collided`）、0 点には 2 通りの意味がある。

| 見えている失敗 | 本当の中身 | 打つ手 |
|---|---|---|
| 成功 0 | ゴールに着いていない | 視覚・掴み・到達（＝学習とデータ） |
| 成功 0 | **着いたが物にぶつけた** | 近づき方・置き方（＝軌道と推論のつまみ） |

**この 2 つは正反対である。** 混ざったままでは、どちらに時間を使っても
半分は無駄になる。**測ってから決める。**

> **外部の観測値。** 他の参加者が 198 エピソードを手元で測った結果として
> ゴール到達 0.939 / 成功 0.667 / 衝突 0.303 / 初衝突の平均 108.6 歩を
> 共有している。**ゴールには着けるが 3 割弱を衝突で落としている**という形で、
> こちらの本番（8 本中 4 本が打ち切り）とは形が違う。**同じ物差しを持てば
> 比べられる。** それがこの資料の目的である。

## いま何ができるようになったか

**採点ハーネス側だけを直した。提出物（`solution/policy_server.py`）には触っていない。**
次に評価を回せば、そのまま新しい行が出る。

### `[結果]` 行

```
[結果] pick_up_the_black_bowl_light_49 ep0: 衝突 137 steps  ゴール 到達  経路 1.10m  変位 1.10m  握り x0  初衝突 108 歩  ぶつけた物体: ketchup_1=544.6mm
[結果] turn_on_the_stove_tb_6 ep0: 未完了 300 steps  ゴール 未達  経路 0.30m  変位 0.00m  握り x0  往復
```

| 項目 | 何が分かるか |
|---|---|
| `ゴール 到達 / 未達` | **成功と分けた到達判定**（`env.step` の `done`） |
| `経路 … / 変位 …` | 手先が通った距離と、始点から終点までの距離 |
| `握り xN` | グリッパの開閉が何回切り替わったか。**掴む瞬間があったか** |
| `静止 / 往復` | 経路長と変位の食い違いから付くラベル |
| `初衝突 N 歩` | 初めて 1mm を超えた歩。**前半なら近づき方、後半なら置き方** |
| `ぶつけた物体` | 何をどれだけ動かしたか（以前からある） |

**経路長と変位は全件に出る。** 映像は既定で「失敗した回だけ・最大 40 本」なので、
84 件すべての動きは**ログでしか分からない**。

## 出た数字をどう読むか

**先に決めておく。** 表を見てから理屈を付けると、都合のよい読み方に寄る。

| ゴール到達率 | 到達のうち衝突で失格 | 読み方 | 次にやること |
|---|---|---|---|
| 低い（< 0.3） | — | 課題そのものができていない | **18**（学習の設定）と **7**（データ）。衝突対策は後回し |
| 高い（> 0.7） | 多い（> 0.2） | できているのに失格している | 近づき方・置き方。**推論のつまみ（12）が効きうる** |
| 高い | 少ない | 惜しい失敗が主 | 打ち切り歩数と `n_action_steps` を見る |
| **どれでも** | **`静止` が大半** | **腕が動いていない** | 下の「動いていないときに見る順」 |

**`静止` の割合を最初に見る。** 8 割を超えたら集計が自分で警告を出す。
その状態では他のどの表も意味を持たない。

## 動いていないときに見る順

他の参加者から「学習側の評価では 80% 以上出るのに、pipeline で方策を動かすと
**全タスク 0%・卓上物体の最大移動量が常に 0.0mm**」という相談が出ている。
指示文・画像解像度・`control_delta`・`observation.state` の組み立ては
学習時と合わせたうえで、である。

**この症状は例外も警告も出さない。** こちらは 0.1409 を出しているので今のところ
無縁だが、**重みを差し替えた直後に同じ穴へ落ちうる**（提出はエラーの救済が無い）。
安い順に見る。

| # | 見るもの | 外れているとどうなるか | 確かめ方 |
|---|---|---|---|
| 1 | **行動の非正規化**（`dataset_stats` が重みに同梱されているか） | 出力が 0 付近に潰れ、**腕がほぼ動かない** | `model_weights/` に統計が入っているか。`/act` の返り値の絶対値 |
| 2 | **グリッパの符号**（±1 のバンバン制御） | 掴めない。`握り x0` のまま | `握り xN` が 0 でないか |
| 3 | **画像の上下反転**（評価環境の生画像は上下逆） | 見当違いの方向へ動く。**動くが届かない** | 録画した映像。`LiberoProcessorStep` の `flip(2,3)` と一致するか |
| 4 | **`observation.state` の並び**（関節 + グリッパ） | 同上 | 提出物側で受け取った形をログに出す |
| 5 | 行動の刻み（delta か絶対か） | 発散するか動かない | `経路 …m` が桁違いに大きい／0 |

**1 と 2 は `[結果]` 行だけで切り分けられる。** `経路 0.00m` かつ `握り x0` なら
1 か 2、`経路` は出ているのに届かないなら 3 か 4 である。

> **提出前の関門にもする。** `run_gpu_eval.sh --check` は 5 タスクだけ 5 分で回すので、
> **90 分の測定と提出の前に「腕が動いているか」を見る場所として使える。**

### なぜ書式を別ファイルへ出したか

パッチは「置換前の文字列を探して、それを含む文字列に置き換える」方式なので、
**置換後の中身を変えると、当たったままのキットに二重適用される。**
`work/eval-kit` は在れば作り直さないため、**`[結果]` 行が 1 エピソードに 2 本出て、
集計が件数を倍に数える**（成功率は変わらないので気づきにくい）。

2 つで防いだ。

- **書式をパッチの外へ出した。** 中身を直してもパッチの文字列は変わらない
- **古い版を剥がしてから当てる**（`_OBSOLETE`）。さらに最後に
  「`[結果]` 行を出す箇所が 1 つだけか」を数えて、違えば落とす

### 確かめたこと

| 確かめたこと | 結果 |
|---|---|
| 新品のキットへ当たるか・2 度当てても壊れないか | **当たる。2 度目は「適用済み」** |
| **古い版が当たったキットへ当てられるか** | **剥がして当て直す。`[結果]` の重複なし** |
| 当てたあと Python として通るか | `py_compile` OK（3 ファイル） |
| 書いた行を集計が読み戻せるか | **15 件の試験で固定**（項目・古いログ・接尾辞・カテゴリ） |
| 動きのラベルが以前と同じか | **5 例すべて一致**（実測値で固定した） |
| 84 行の CSV が変わらないか | **既存列は完全一致。** 母集団は動いていない |
| `is_applied()` が新しいパッチ集合を見るか | 新品・更新後ともに True、未適用は False |

**実物の LIBERO-plus に対しては未実行である。** numpy の要る箇所は
手元では動かせないので、そこは `--check`（5 分）で見る。

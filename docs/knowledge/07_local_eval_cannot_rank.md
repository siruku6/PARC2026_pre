# 07. 手元の評価は、本番の順位を付けられなかった

**同じ「手元 28/36」から、本番 0.169 と 0.485 が出た。**成功率は 2 つを
区別できず、ステップ数だけが区別できた。

## 決定的な 2 例

**どちらも 3.9.0（本番 0.264・手元 25/36）を基準にした 1 変数の変更である。**

| | 手元 36 件の成功 | 手元の判定 | **本番** |
|---|---|---|---|
| 3.10.0（chunk 継ぎ目の平滑化） | 25 → **28** | **良くなった** | **0.264 → 0.169（悪化）** |
| 4.2.0（全パラメータ学習の重み） | 25 → **28** | 良くなった | **0.264 → 0.485（大勝）** |

**手元の成功率は両方とも +3 件で、まったく同じ数字だった。**

**ステップ数で見ると分かれる。**

| | 手元のステップ数 | 本番のステップ数 |
|---|---|---|
| 3.10.0 | （36 件では読めなかった） | **1,471（+29%）** |
| 4.2.0 | — | **991（−13%）** |

## もう 1 例 —— n=16 のとき

| | 手元 36 件 | 本番 |
|---|---|---|
| 3.8.0（n=10） | 0.667 | 0.177 |
| 3.9.0（n=16） | **0.694（+0.028・符号検定 p = 1.000）** | **0.264（+0.087）** |

**手元では「差が無い」と出たものが、本番では 5 割増しになった。**

## なぜ順位が付かないのか

| 理由 | 中身 |
|---|---|
| **配点が秘匿** | 総合スコアは成功率だけでなく、時間・加速度の変化の激しさ（ジャーク）・動きの滑らかさを 1 つの値にまとめた指標（SPARC）・軌道・衝突の重み付き積（予選 PDF p11）。**重みの設定ファイルは採点環境にしかない** |
| **手元のキットは総合スコアを計算しない** | `pipeline/total_score.py` の既定は `weights: {}`、`pipeline/scorer.py` は `overall_score = float(overall_success)`＝成功率をそのまま返すだけ |
| **本数が少ない** | 36 件・1 タスク 1 本なので ±2 件は偶然と区別できない（符号検定が p = 0.4〜1.0 になりがち） |
| **タスクの偏り** | 手元の 36 件には長いタスクが少なく、**「遅くなると間に合わなくなる」悪化が現れにくい** |

## それでも手元評価をやめてはいけない

**やめるのではなく、見る指標を変える。**

| 見るもの | 使えるか |
|---|---|
| 成功率 | **順位付けには使えない。**壊れていないことの確認には使える |
| **ステップ数（とくに両方が成功した回だけの合計）** | **使える。**本番と繋がっている唯一の量 |
| **300 ステップの上限に達して打ち切られた件の割合** | **使える。**ステップ数が足りなくなっていないかの見張り |
| ジャーク・SPARC | 連続値なので少ない本数でも読めるが、**本番スコアとの対応は確認できていない** |

```bash
python3 solution/tools/analysis/compare_steps.py --base <基準の回> --other <比べる回>
```

### 【8/24】「使える」に数字が付いた —— 差が 7% 未満なら読まない

**上の表は「ステップ数は使える」と書いていたが、どこまで小さい差が読めるかを
測っていなかった。** 同じ 36 件・同じ設定・同じ重みで **5 回**回して測った
（`0824_125446_floor36_ep5`、180 ロールアウト）。

| 見るもの | 5 回のばらつき |
|---|---|
| 成功率 | **11.1 ポイント**（0.694 / 0.694 / 0.694 / 0.778 / 0.667） |
| 全 36 件の合計歩数 | +8.9% |
| **5 回とも完走した 26 件の合計歩数** | **+6.5%**（標準偏差 2.6%） |
| 1 行ごとの歩数 | 中央 29%・最大 145% |

**この 3 つが上の表を数字で裏づけた。**

1. **成功率が順位付けに使えないのは、同じ設定でも 4 件ぶん動くからである**
   （36 件で 1 件は 2.8 pt）。
2. **ステップ数は使えるが、差が 7% 未満なら読まない。** このページが挙げる
   本番で効いた施策（全パラメータ学習 −13%・chunk 長 −20%・指示文の正規化 −16%）は
   どれも床の 2 倍以上ある。**逆に blend4 の +0.3% は最初から読めない差だった。**
3. **1 行の差は読んではいけない。** 集計して初めて ±6.5% に収まる。

**組の選び方にも決めごとが要る。** 「両方が成功した回だけ」で選ぶと、
**基準では安定して速かったタスクを、比べる側が壊した回が除かれてしまう。**
2026-08-24 に Robot Initial States の摂動でこれが起き、悪化を 3 分の 1 に
読み違えた（[reference/21 の 3 節](../reference/21_weakness_map.md)）。
**基準側だけで組を選び、比べる側の 300 は 300 と数える**（出る値は下限になる）。

## 一度作ってしまった規則

> **「手元で差が無いから出さない」という判断はしてはいけない。**

これは n=16 のとき（手元 p=1.000・本番 +0.087）に作った規則で、正しかった。
**ただし裏返しの「手元で良くなったから出す」も成り立たない**ことが、
その後 blend4 で分かった。**手元は「出す／出さない」を決められない。**

## Claude 側 / 人間側

**Claude 側**: **手元で測れる量を本番スコアの代わりに使うと提案するとき（proxy metric）は、
本番の指標との対応が確認済みかを先に言う。**
「手元 36 件で +3 件」を良い知らせとして報告したが、**その +3 件が本番の +0.09 に
なるのか −0.09 になるのかは、当時まったく分かっていなかった。**
分かっていないことを、分かっている風に報告してはいけない。

**人間側**: **手元の proxy metric は「本番と対応が取れた」と実証するまで、判断の根拠にしない。**
対応を取るには、**本番の測定を 2 回以上使って手元の値と突き合わせる**必要がある。
その予算（提出枠）を、最初の数回ぶん確保しておく。

**両方**: **本番で測れる回数が限られているときこそ、1 回を「手元の proxy metric が本番と
対応しているかの確認」に使う価値がある。**今回は 11 回目まで対応を確かめないまま、
手元の proxy metric を信じて提出枠を使っていた。

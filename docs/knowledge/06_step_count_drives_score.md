# 06. ステップ数が、本番スコアのいちばん強い説明変数だった

**このコンペで最も役に立った発見である。**レポートの「工夫点及び試行錯誤」の柱にする。

## 何が分かったか

**8 エピソードの合計ステップ数（`POST /act` の回数）と総合スコアが、強い負の相関を示した。**

| 範囲 | 本数 | **相関 r** |
|---|---|---|
| 全提出 | 15 | **−0.868** |
| SmolVLA だけ | 11 | −0.812 |
| π0.5 だけ | 4 | **−0.925** |

出典は [05_score_history.md](05_score_history.md) の表（採点ログ 16 本）。

## 「決める」とは言わない —— 反例がある

| 版 | ステップ数 | スコア |
|---|---|---|
| 3.3.0（n=1） | **1,992** | **0.080** |
| 3.4.0（n=2・samples=3） | **1,994** | **0.168** |

**ステップ数がほぼ同じで、スコアは 2 倍以上違う。**総合スコアには成功判定・衝突・
滑らかさも重み付きで入る（予選 PDF p11）ので当然である。

**正しい言い方は「最も強い説明変数」。**「ステップ数がスコアを決定する」と書くと
過剰主張になる。**レポートには「記載と提出物が食い違えば失格」という条項が付いているので、
言い過ぎない。**

## なぜステップ数が効くのか

**打ち切りは 300 ステップで、方策には余裕が無い。**手元 36 件の測定で、
**成功した回は、学習データに入っている正解の軌道（デモ軌道）の 0.96 倍のステップ数で
終わっていた。**デモ軌道が 230〜300 ステップのタスクの成功率は 0.29 しかない。

**つまり少し遅くなるだけで、長いタスクが 300 ステップを越えて未完了になる。**
未完了はゴール未到達なので、成功判定そのものを失う。

## ステップ数と秒数は別の量である —— ここを半日取り違えた

| 量 | 何に効くか | 上限 | 実測 | 余裕 |
|---|---|---|---|---|
| **ステップ数** | **成功そのもの。**`max_steps=300` で打ち切られる | 1 本 300 ステップ | 平均 124 ステップ（4.2.0） | **ほぼ無い** |
| 秒数 | トラック全体の 1 時間の上限だけ | 3,600 秒 | 110.4 秒（4.2.0） | **32 倍** |

**運営 Q&A No.23 が、スコアの `time` 要素は「エピソード内のシミュレーション
ステップ数に基づく値」であって壁時計時間ではないと明言している。**
先にこれを読んでいれば、取り違えずに済んだ。

## 打ち消し合いに注意 —— 同じ施策が、評価セット次第で良くも悪くも見える

**blend4 は「全体を遅くする代わりに、300 ステップの上限に達して終わらない課題を救う」
施策だった。**
手元 36 件を、基準の回で打ち切りに達していたかで分けると打ち消し合いが見える。

| 手元 36 件を分けると | 件数 | 合計ステップ数 | 変化 |
|---|---|---|---|
| **基準で 300 ステップの上限に達していた件** | 6 | 1,800 → **1,230** | **−31.7%（救われた）** |
| **基準で 300 未満で終わっていた件** | 30 | 4,515 → **5,107** | **+13.1%（遅くなった）** |
| 全体 | 36 | 6,315 → 6,337 | **+0.3%（相殺）** |

**本番の 8 本は、基準（3.9.0）の時点で 1 本も上限に達していなかった**（最大 225 ステップ）。
**救う相手がいないので、13% の減速だけが効き、2 本が 300 を越えた** ——
1,142 → 1,471（+29%）。

**教訓: 評価セットに「上限に達して終わらない課題」がいくつ含まれるかで、
同じ施策の見え方が変わる。**
手元の 36 件には 6 件（17%）あり、本番の 4 タスクには 0 件だった。

### 見抜ける指標はあった —— **基準で完走していた件だけのステップ数**

| 指標 | blend4 の値 | 悪化を捉えたか |
|---|---|---|
| 成功件数 | 25 → 28 | **捉えられない**（良く見える） |
| 合計ステップ数 | +0.3% | **捉えられない** |
| 両方が成功した件だけのステップ数 | +1.6% | **捉えられない**（失敗に転じた件が除外されるため） |
| **基準で完走していた件だけのステップ数** | **+13.1%** | **捉えた** |

**`compare_steps.py` にこの指標を足した**（2026-08-15）。
打ち切りに達していた件は救われると大きく減るので、**全体の合計に混ぜてはいけない。**

### 【8/23 決着】置いておいた再検討の条件が満たされ、blend4 を測り直したが効かなかった

上で「探査40行のカテゴリ別打ち切り率を見て判断する。打ち切り率が高かったときの再検討材料
として置く」と書いた条件が、**Camera Viewpoints の方位角スイープで満たされた。** 方位角
45〜75° では 300 ステップに達した割合が **13/24 = 54%** で、救う相手が大量にいる
（Track1 の本番8本は 0 件だった）。そこで同じ48行を `blend0` と `blend4` で回して比べた。

| | blend0 | blend4 |
|---|---|---|
| 45〜75° の 300 到達 | 13/24 | 10/24 |
| 0〜30° の 300 到達 | 3/24 | 4/24 |
| 成功した回 | 31/48 | **31/48（同数）** |
| 対応のある反転（45〜75°） | — | **救われた 6 件 / 悪化した 3 件、McNemar p = 0.508** |
| 両方が完走した行のステップ数（0〜30°） | 2,664 歩 | 2,686 歩（**+0.8%**） |

**結論: `blend_steps` は 0 のままにする。この件は閉じる。** 救う相手がいる条件を作っても
効果が測れなかった。**加えて、Track1 で見えた「基準で完走していた件の +13.1% の減速」も、
今の重み（`pi05_rp3000`）では +0.8% しか出ていない**——代償が小さいかわりに効果も無い。

**測り方の限界も分かった。** 45〜75° の24行のうち**9行が向きを問わず反転している**
（救われた6・悪化した3）。**300歩の境界にいるタスクは、行動列がわずかに変わればどちらへも
転ぶので、1エピソードずつの設定比較はこの転びに埋もれる。** 推論は乱数を使い seed を
固定していない（`policy_server.py` は `_get_action_chunk` に `noise=None` を渡す）ため、
**同じ設定で回し直しても結果は変わる。** 設定値を比べるときは、まず「同じ設定で回し直して
何行が反転するか」を測ること。詳細は
[plan/10 の 7 節](../plan/10_eval_perturbation_suite.md#7-強度依存の実測と読み方の訂正2026-08-23-に確定)。

**`PARC_SEED` を既定オフで足した**（2026-08-23、`policy_server.py`・`run_docker_eval.sh`）。
渡すとエピソードごとに乱数を固定する。**ただし seed を揃えても `blend_steps` のように行動
そのものを書き換える設定は 16 歩目以降で軌道が変わるので、これだけでは上の転びは消えない。**
意味は、複数回で比べるときに対応が取れてばらつきが小さくなる点にある。

### 【8/23】この指標の床を初めて測った —— **約 11%**

**同じ 32 行を同じ設定（`blend0`）で 3 回回した**
（`0823_141340_camera_azimuth` の 1 回 ＋ `0823_201743_camera_high_control` の 2 回）。
**手元評価を同じ条件で繰り返したのは、49 回の評価で初めてである。**

| 集計のしかた | 3 回の値 | 幅 |
|---|---|---|
| 32 行すべての合計歩数 | 6,833 / 6,489 / 5,141 | **+32.9%** |
| Base 8 行の合計歩数 | 1,428 / 1,216 / 1,106 | +29.1% |
| **Base のうち 3 回すべて完走した 6 行の合計** | 828 / 877 / 793 | **+10.6%** |
| **摂動側のうち 3 回すべて完走した 6 行の合計** | 692 / 779 / 738 | **+12.6%** |

**上の表の「基準で完走していた件だけのステップ数」を選んだ判断は正しかった。**
全行の合計は同じ設定でも ±33% 動くのに、打ち切りに一度も達しなかった行だけに絞ると
±11% に落ちる。**打ち切りが混ざると読めなくなる、という理由が数字で裏づけられた。**

**そのうえで、床が約 11% あることは知っておく必要がある。** このページが挙げている
勝ち筋——全パラメータ学習 −13%・chunk 長 −20%・指示文の正規化 −16%——は、
**どれもこの床のすぐ上にある。** 差が 11% 未満のときは、1 エピソードずつの比較では
判定できない。

**行ごとに見ると、もっと大きい。** 3 回すべて完走した 12 行で、同じ行の最大と最小の幅は
**中央 42%・最大 96%**。**「300 に達したか」も 24 行のうち 14 行で 3 回の結果が割れた**——
たとえば `turn_on_the_stove` の方位角 45° は **300 → 74 → 70 歩**、`STUDY_SCENE1` の
無摂動は **300 → 219 → 170 歩**である。

**測るときの決めごと**（[plan/10 の 7.2 節](../plan/10_eval_perturbation_suite.md)）:

1. ステップ数で比べるときは**「一度も 300 に達していない行だけの合計」**を使う。
2. **差が 11% 未満なら読まない。**
3. 設定値や重みを比べるときは、**まず同じ設定で回し直して床を測る。**
4. 1 点あたり 8 行・1 エピソードでは何も言えない。**まとめて 24 行以上にしてから検定する**
   （同じデータが n=8 で p=0.294、n=24 で p=0.0023 になった実例がある）。

## ステップ数を良くする要素

| 施策 | ステップ数 | 結果 |
|---|---|---|
| **全パラメータ学習（カメラ画像を特徴量に変換する部分＝視覚エンコーダの固定も外す）** | **−13%**（1,142 → 991） | **本番 0.264 → 0.485** |
| **chunk 長を最適値へ（n=10 → 16）** | **−20%**（1,428 → 1,142） | **0.177 → 0.264** |
| **指示文の正規化** | **−16%**（1,922 → 1,617） | **0.166 → 0.181。重みは 1 ビットも変えていない** |
| モデルを強いものへ（SmolVLA → π0.5） | −19%（1,766 → 1,428） | 0.184 → 0.177（スコアは横ばい） |

**「秒数だけ払ってステップ数を買う」施策は、事実上ただである。**
`num_inference_steps` と `samples` は推論の秒数しか増やさず、
**環境のステップ数を 1 ステップも増やさない。**秒数には 32 倍の余裕がある。

## 測り方

```bash
# 採点ログからステップ数を数える
grep -c "POST /act" outputs/<採点ログ>.md

# 手元の 2 つの回をステップ数で 1 件ずつ突き合わせる
python3 solution/tools/analysis/compare_steps.py \
    --base  work/gpu_eval/<基準の回> \
    --other work/gpu_eval/<比べる回>
```

**`compare_steps.py` は「両方が成功した回だけのステップ数」も出す。**
打ち切り（300 ステップ）が混ざった件は必ず 300 と数えられ、合計が上限側へ寄って読めなくなるためである。

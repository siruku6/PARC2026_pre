# 001 衝突と判定されたとき、どの物体がどれだけ動いたかを数える

> **状態: 仕掛けは完成・実行待ち** ／ 受け側: 別セッション ／ 更新: 2026-08-28

## 背景（先に読んでほしい）

**このコンペで何をしているか。** PARC2026 の本選 1 である。ロボット（Franka Emika Panda）に
自然言語の指示を与え、LIBERO-plus のシミュレータの中で物を掴んで運ばせる。
こちらの方策は **π0.5**（PaliGemma + 行動側の小さな Transformer、41 億パラメータ）で、
`policy_server.py` が画像 2 枚（`front` と `wrist`）と状態を受け取って行動を返す。

**トラックは 3 つあり、この依頼は 3 つ全部に効く。**

| トラック | 中身 | こちらの点 | リーダーボードの最高 |
|---|---|---|---|
| Track1 | 学習済みタスク・背景と照明が変わる | **0.370** | **0.65** |
| Track2 | 学習済みタスク・視点や姿勢やノイズが変わる | **0.207** | **0.53** |
| Track3 | **見たことのないタスク** | 0.000 | **0.000（全参加者）** |

**こちらは先頭集団の下にいる。**多くの参加者が 0.4 を超えている。

**なぜ衝突が全トラックに効くのか。** 採点式は公開されていて、こうである。

```
Total Score = (1/N) * Σ successᵢ * (1 - collision penaltyᵢ) * smooth metricsᵢ
```

**collision penalty は [0,1] の 2 値なので、衝突した回の点はまるごと 0 になる。**
さらに手元の評価キットでは、衝突は成功判定そのものを落とす
（`pipeline/rollout.py:234` の `success = bool(done) and not collided`）。
**トラックによらず同じ門である。**

**測る対象のデータ。** `compe/val/TRACK2_VAL72.csv` という 72 行の集合を使う。
**Track2 の摂動を含むように 2026-08-28 に作ったもの**で、中身は
**12 タスク × 6 条件**（摂動なし・カメラ方位角 +45°・カメラ方位角 −60°・
ロボット初期姿勢の摂動量 0.1／0.2／0.4）。1 行 3 エピソードで 216 本になる。
12 タスクは、摂動なしで 3 回とも打ち切り（300 歩）に達しなかったものを選んである。

**名前は Track2 用だが、Base の 12 行は摂動なしの素の状態**なので、
**そこで起きる衝突は Track1 でも Track3 でも同じように起きると考えてよい。**

**いまの読み。** 216 本で成功 0.722・衝突 0.227 だった。
**失敗 0.278 のうち 0.227 が衝突なので、失敗の 82% が衝突である。**
そして**摂動を 1 つも掛けていない Base ですら 16.7% が衝突で落ちている。**
**衝突は摂動への弱さではなく、素の制御の問題だと見えてきた。**

**Track3 でも同じことが起きていて、そちらのほうが極端である。**
8/28 に 4 タスク × 2 エピソードを回した（`work/final_eval/0828_130103_track3_t3video`）。

| タスク | 成功率 | **衝突率** | **監視される物の数** |
|---|---|---|---|
| alphabet soup をトレイから出す | 0.00 | **1.00** | 4 |
| red mug を左の皿から下ろす | 0.00 | **1.00** | 3 |
| yellow book を棚から下ろす | 0.00 | **1.00** | 2 |
| **2 つのマグを皿から下ろす** | 0.00 | **0.00** | **1** |

**支えている物（トレイ・皿・棚）は `obj_of_interest` に入っていて見逃されるが、
隣に並んでいる物は見逃されない。**唯一衝突していないのが、監視される物が 1 個だけの
タスクである。**詳しくは [knowledge/17](../../knowledge/17_track3_is_a_1mm_clutter_problem.md)。**

**判断が必要になったら。** この依頼の目的は「後処理で届くのか、学習でしか直らないのか」を
決めることである。**その目的に照らして、より良い測り方を思いついたら変えてよい。**
変えた場合は、変えたことと理由を報告に書くこと。

## 何をしてほしいか

**評価のロールアウト 1 回ごとに「操作対象でない物体が、それぞれ何 mm 動いたか」を
記録する仕掛けを足し、1 本回して分布を出してほしい。**
成果物は **(1) 記録する仕掛けのコード** と **(2) 変位の分布を並べた表**である。

## なぜ要るか

**いま手元の失敗の 82% が衝突である。**次に何をするかが、この分布で分かれる。

| 分布がこうなら | 次にやること |
|---|---|
| **1〜3 mm に固まっている**（かすった） | 動きを滑らかにする・接触の手前で減速する、といった**推論側の後処理**に意味がある |
| **数 cm に散らばっている**（倒した・押しのけた） | **後処理では届かない。**学習でしか直らないと決まる |

**この判定なしに衝突対策へ着手すると、外れたときに何も残らない。**

## 前提となる事実

**判定の場所は `pipeline/rollout.py` である**（会社の RTX6000 と、このリポジトリの
`work/final_eval` から回すときに使う本選キット `/home/ubuntu/lab/b_PARC2026_final`）。

- **`rollout.py:233-234`**

  ```python
  collided = any(d > collision_threshold for d in object_max_disp.values())
  success = bool(done) and not collided
  ```

  **つまり「ゴールに着いた」だけでは成功にならない。**

- **しきい値は 1 mm。** `pipeline/total_score.py` の内蔵既定が
  `"collision": {"enabled": True, "threshold_m": 0.001}`。

- **監視される物体**は `rollout.py:170-178` で決まる。観測 `obs` のキーのうち
  `_pos` で終わり、`robot0` で始まらず、`_to_robot0_eef_pos` で終わらず、
  **`obj_of_interest`（そのタスクの操作対象）に入っていないもの。**
  初期位置は、ダミー行動を 10 ステップ流したあとの値を基準にしている。

- **`object_max_disp` は既に計算されている。** 各物体の「初期位置からの最大変位」である。
  **いまはしきい値と比べた真偽だけが使われ、値そのものは捨てられている。**
  ここを書き出すのが依頼の中心である。

**8/28 に測った衝突率**（`work/final_eval/0828_002049_track2_val72base`・72 タスク × 3 本 = 216 本）。

### 依頼から変えたところが 2 つある

**1. 距離を 2 通り書き出すことにした。** 元の `rollout.py:212` は
`np.sum(np.abs(cur - p0))` で、**3 軸の絶対値の和（L1）を取っている。**
ユークリッド距離ではないので、**実際に動いた距離を最大 √3 倍だけ大きく見せる。**
1〜3 mm か数 cm かを分ける依頼で、この差は結論を動かしうる。

**しきい値 1 mm と比べられている値は L1 なので、衝突したかどうかは L1 のままで数え、
何 mm 動いたかは L2 で読む。**JSONL には `max_disp_m`（L1・依頼どおりのキー）と
`max_disp_l2_m`（L2）の両方が入り、表も既定で両方出る。

**2. 書き出し先を `results/object_disp.jsonl` にした。**依頼は「実行ディレクトリの
`object_disp.jsonl`」だったが、**評価側の `docker run` は実行ディレクトリの直下を
コンテナへ見せていない。**見せているのは `$OUTPUT_DIR/results` と、`RECORD=1` のときの
`$OUTPUT_DIR/videos` の 2 つだけである。
外から見えるのは `work/final_eval/<日時>_track2_collision_probe/results/object_disp.jsonl` である。

### 動画を直した。cv2 の mp4v で書き、読み戻して確かめる（2026-08-28）

**1 行でいうと、`imageio` をやめて `cv2` の `mp4v` で書き、書いたものを読み戻して
確かめられなければ GIF・PNG 連番へ落ちるようにした。**

**原因は、評価用イメージに `imageio_ffmpeg` が入っていないことだった。**そのため
`imageio.mimwrite("....mp4", ...)` が MP4 の実装を見つけられず、**TIFF の実装に落ちて
いた**——TIFF は `fps` を知らないので `TiffWriter.write() got an unexpected keyword
argument 'fps'` で落ち、8 バイトの空 TIFF だけが残っていた。

**イメージの中で何が使えるかを実機で数えた**（`docker start parc2026_verify` で
既存のコンテナを起こし、`docker exec` で入った）。

| 実装 | ある／ない | 動画を書けるか |
|---|---|---|
| `imageio` 2.37.4 | ある | **MP4 は書けない**（`imageio_ffmpeg` が無い） |
| `imageio_ffmpeg` | **無い** | — |
| `cv2` 4.11.0（`opencv-python-headless`） | ある | **`mp4v` は書けた。**`avc1`（H.264）は encoder が無く `isOpened()` が False |
| `PIL` 12.3.0 | ある | GIF が書ける（外部のコーデックに依存しない） |

**直したあと、実機で 3 段すべてを動かした。**

| 試したこと | 結果 |
|---|---|
| パッチ版 `_write_video` を評価用イメージの中で呼ぶ | `demo_task__SUCCESS.mp4` が 108,610 バイト。**読み戻して 60 フレーム全部取れた** |
| フレームの大きさ | 128×256（front と wrist の並び）を 2 倍して 256×512。**素のままでは腕の行き先を目で追うには小さい** |
| cv2 をわざと壊す | GIF へ落ちた（19,413 バイト・30 フレーム） |
| GIF も壊す（直接呼ぶ） | PNG 連番が 30 枚できた |

**倍率は `T3_VIDEO_SCALE` で変えられる**（既定 2）。**近傍の複製なので情報は増えないが、
再生したときに見やすくなる。**

**元の不具合が黙って通った理由は、書いたあと確かめていなかったことである。**
新しい実装は mp4 なら `cv2.VideoCapture` で 1 フレーム読み、GIF なら `n_frames` を見て、
**確かめられたものだけを成功と見なす。**

### 分布の表

（1 本回したあとにここへ書く）

## 背景

PARC2026 本選。Track1 0.492／Track2 0.233／**Track3 0.000**（他参加者の最高は
0.09603 ＝ 8 本中 1 本ぶん）。締切は **9/17**。

Track3 は LIBERO の既存タスクの**逆順**で、学習データに逆向きの型が 1 件も無いのが
0 点の主因と読めている。逆向きデータの本命は**時間反転**（[006](006_track3_reverse_direction.md)）。

**この依頼は 006 の「forward 0/3」の切り分けに直接効く。** 006 の 2 節は、
デモの順再生が task 92 の `:goal` を 0/3 しか満たさないことの候補を 3 つ挙げていて、
その (b) が「**action 規約（gripper 極性・1 ステップの長さ）のずれ**」である。
[014](014_verify_raw_states_for_time_reversal.md) で同じ `action` 列を実測したところ、
**試作コードが docstring で宣言している規約と食い違った。** 014 は「state が時間反転に
使えるか」だけを見る依頼だったので、この食い違いはこちらでは決められない——
**シミュレータを持っている側でないと決着しない。**

すでに分かっていること・外したこと:

- `observation.state` 列は健全（8 次元・NaN 無し・静的コピーでない）。**これは確定。**
- 時間反転の手順（state の絶対姿勢を逆順にして差分を作り直す）は**それ自体で閉じている**
  ——往復テストで残差 中央 0.6〜0.9 mm。**state 側は問題ではない。**
- 014 の初回報告には誤りが 3 件あり、下の「前提となる事実」の数値は**訂正後のもの**である。
- 画像・動画の内容、`IPEC-COMMUNITY` の v2.1 系データセットは見ていない（不要）。

## 何をしてほしいか

`action` 列が「**正規化された相対差分**」なのか「**そのまま OSC に流せる生の指令値**」なのかを、
**シミュレータで 1 本再生して決める**こと。成果物は **どちらかに決めた 1 行**と、
その根拠になった**フレーム毎の state 比較（発散フレームの番号）**。

## なぜ要るか

**逆向きデモの作り方がこの 1 点で変わる。** 9/17 までの日割りに直接効く。

| もし `action` が… | 逆向きデモの作り方 | 006 の forward 0/3 は |
|---|---|---|
| **正規化された相対差分** | state の絶対姿勢を逆順にして差分を作り直し、定数で割る（014 の往復テスト済み） | 規約ずれで説明できる。`actions[::-1]` は**符号反転が要る**ので試作は直す必要がある |
| **生の OSC 指令値** | 定数で割るだけでは足りない。**制御器を通した逆算**（または kit 内で再生して作った軌跡を反転元にする）が必要 | 規約は無罪。原因は (a) 物理差か (c) 初期状態不一致 |

**どちらでも 006 の次の工程が変わる。**決まらないと、時間反転の実装を 2 通り抱えることになる。

## 前提となる事実

### 食い違っている 2 か所

**試作コード側の宣言**（`solution/tools/track3_reversal/reversal_probe.py`）:

- `build_reversed_actions`（50〜68 行）の docstring:
  「データ規約: **use_relative_actions=False（絶対 EEF 姿勢 6 次元 + gripper 1 次元）**。
  絶対姿勢の反転は意味が通る（同じ空間経路を戻る）。」
- 同 129 行 `--gripper-mode` のヘルプにも「データは use_relative_actions=False（絶対姿勢）」
- 実装は `rev = np.ascontiguousarray(actions[::-1].copy())` ——**並べ替えるだけで符号は変えない。**
  これは「絶対姿勢なら正しい」が、相対差分なら**014 の依頼書が警告していた壊れ方そのもの**
  （「単純にフレーム順を逆にしただけでは『前の姿勢からのずれ』という意味が壊れる」）。
- `gripper_mode=invert` は `rev[:, 6] = 1.0 - rev[:, 6]`。**`action[6]` の実値は ±1 のみ**なので、
  `1 − x` は {0, 2} を返す。**2 は指令範囲の外である。** `[0,1]` の gripper を想定した式に見える。

**014 の実測側**（`~/src/train_data/verify014_calib.py`・所要 1.4 秒）:

その `action` 列は `host_extract_actions.py` が
`libero_combined_20hz_extracted/.../data/chunk-000/file-000.parquet` から抜いているものと
**同一の列**である（同じファイル・同じ列名）。つまり両者は同じ数値を指して逆のことを言っている。

### 014 が「決められなかった」こと ＝ この依頼の核心

**`action` が「達成された差分」か「指令された差分」かは決着していない。**
先読み `k` を振って `pos[t+k] − pos[t] ≈ scale × action[t]` を当てると、
**相関は `k=3` で最大になる**:

| k | 1 | 2 | **3** | 4 | 6 | 8 |
|---|---|---|---|---|---|---|
| ep 5195 相関 | 0.9518 | 0.9685 | **0.9741** | 0.9693 | 0.9332 | 0.8740 |
| ep 5225 相関 | 0.9262 | 0.9348 | **0.9388** | 0.9384 | 0.9257 | 0.9020 |

`k=1` が最良でないことは「**制御器が 1 フレームでは到達していない**」＝ action は
**指令寄り**であることを示唆する。これは
「`action` は生の OSC 指令値で、当てた scale は達成／指令の**応答比**にすぎない」
という読みと整合する。

**回転側で検算が付く。** `solution/tools/scripted_demo/scripted_demo.py:164` は
yaw（手首）の指令について「**1.0 が上限（`output_max` は 0.5 rad）**」と明記している。
実測した回転 scale は **0.10149 rad/単位**なので、**応答比 0.10149 / 0.5 ≒ 0.20**。
並進の応答比も（`output_max` を 0.05 m とすれば）**0.01110 / 0.05 ≒ 0.22** で、
**並進と回転が独立に同じ ≒0.2 を出す。** 20 Hz の 1 ステップで指令の 2 割しか
到達しない、という 1 つの説明で両方が揃う。
**この読みが正しければ `action` はそのまま再生できる**（＝試作コードの前提のうち
「相対か絶対か」は外しているが「そのまま流せる」は当たっている）。

留保: 並進の `output_max` 0.05 m は**このホストでは確認できていない**
（robosuite が入っていない）。**回転の 0.5 rad も根拠はリポジトリ内の記述 1 か所で、
しかも yaw 軸についての記述である**（3 軸で同じ値かは未確認）。
再生する側は**コントローラ設定の `output_max` の実値を控えて報告に入れてほしい**——
並進・回転の応答比が揃って ≒0.2 になるかどうかが、この読みの決め手になる。

もう 1 つの傍証: **依頼書原文のチェック 4 は落ちている。** 正規化定数を当て直しても
「差分と action が 1 mm 以内で一致するフレーム」は **23.1%／15.3%** で、90% に遠い。
量子化（1/64 単位 ≒ 0.18 mm）では説明できない大きさなので、
**`action` は「その 1 フレームの state 差分の定数倍」ではない。**

### gripper は未確定

state の 2 次元は左右の指で符号対称（`d7 ≈ −d6`）。開き幅の増減の符号から `action[6]` を
復元すると一致率 **93.5%／83.8%**（幅が動かないフレームは判定不能）。
ただし**時間反転は「掴む」と「放す」を入れ替える**ので、順方向の `action[6]` を
逆順にするだけで意味が通るかは測っていない。試作コードが `keep`／`invert`／`skip` の
3 モードを持っているのは正しい態度である——**どれが正しいかは決まっていない。**

## やること

1. **順方向の 1 本を再生して、フレーム毎に state を突き合わせる**（006 の 3 節「次にやること」の
   1 番と同じ作業。こちらは**比較の相手になる基準値**を持っている）。
   ep 5195 か 5225 を使うなら、基準の state 列はこう出せる:

   ```
   /home/ubuntu/.pyenv/versions/3.12.14/bin/python ~/src/train_data/verify014_calib.py scale
   ```

   task 92 のエピソード（ep 4061〜4063）でやるなら、同じ計算を
   `verify014_calib.py` の `TARGET_EPISODES` を書き換えて回す（1.4 秒で終わる）。
2. **判定**: 再生後の eef_pos が、データの `observation.state[:, :3]` と
   **フレーム毎に何 mm ずれるか**を出す。
   - **全フレームで数 mm 以内 → `action` は生の指令値。そのまま再生できる。**
     この場合、逆向きデモは「定数で割る」では作れない。
   - **序盤から発散 → 初期状態か環境差**（規約の話ではない。006 の候補 (a)(c)）。
   - **中盤から徐々に発散 → 物理差か、1 ステップの長さのずれ。**
3. **`gripper_mode=invert` の式を確認する**。`action[6]` は ±1 なので `1.0 - x` は {0, 2} を返す。
   意図が「±1 の反転」なら `-x`、「[0,1] の反転」なら入力側の値域が違う。どちらが正か決める。
4. 決まった規約を **1 行で** `docs/reference/25_dataset_inventory.md` に足す
   （8.5 節が `observation.state` 8 次元・`action` 7 次元までは書いているが、
   **相対か絶対か・正規化の有無を書いていない**。ここが今回の食い違いの発生源である）。

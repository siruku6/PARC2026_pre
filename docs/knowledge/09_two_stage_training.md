# 09. 2 段学習 —— 行動側で頭打ちにしてから、画像を見る側を解いた

**提出物（4.2.0・本番 0.485）がどうやって出来たかの説明である。**
レポートの「工夫点及び試行錯誤」の柱の 1 つ。

## やったこと

| | 段 1 | **段 2（提出したもの）** |
|---|---|---|
| 出発点 | `lerobot/pi05_libero_base` rev `a217bfd3…` | 段 1 の 24,000 歩 |
| **凍らせた所** | **画像を見る側（vision encoder）と VLM** | **無し。全部動かす** |
| 更新したパラメータ | **693,422,112（693M）** | **4,143,404,816（4.14B）** |
| 歩数 | 24,000 | 3,000 |
| batch | 16 | 64 |
| 学習率 | 2.5e-5 → 2.5e-6 | 5e-6 → 2.5e-6 |
| 掛かった時間 | ローカル H100-20C で **9 時間 31 分** | RunPod A100 80GB で **8 時間 33 分** |
| 本番スコア | **0.264**（3.9.0） | **0.485**（4.2.0） |

**設定は 6 つとも同じにしたので、0.264 と 0.485 の差は重みだけである**
（n=16・blend 0・infer 10・samples 1・EMA 0.3・正規化 on）。

## なぜ 2 段にしたか（後から見た理由づけ）

**最初から全部を動かす計画だったわけではない。**段 1 は GPU が 20 GB しか
無かったため、**行動側だけなら載る**という制約から選んだ形である。
段 2 は外部の A100 80GB を借りられたので、初めて全部を動かせた。

**結果として、これは筋の良い順番だった。**

## 段 1 は頭打ちになっていた

| 段 1 の歩数 | loss |
|---|---|
| 18,001〜20,000 | 0.2375 |
| 20,001〜22,000 | 0.2352 |
| **22,001〜24,000** | **0.2360（上がっている）** |

**18,000 歩以降、行動側だけを動かしても loss が下がらなくなっていた。**

## 凍らせていた側を解いたら、また下がった

| 段 2 の歩数 | loss | grad norm |
|---|---|---|
| 1〜500 | 0.2294 | 0.692 |
| 1,001〜1,500 | 0.2162 | 0.653 |
| 2,001〜2,500 | 0.2122 | 0.653 |
| **2,501〜3,000** | **0.2100** | **0.640** |

**0.236 → 0.210（−11%）。3,000 歩で打ち切った時点でも、まだ下がり続けていた。**
grad norm は 0.86 → 0.64 に落ち、跳ねも `nan` も無い。完走（`End of training`・
終了コード 0・学習率は 2.5e-6 まで下がりきり）。

**読み: 段 1 が抱えていた残りの誤差は、凍らせていた側にあった。**

## 本番では歩数が減った

| | 8 本の合計歩数 | 秒数 | 本番 |
|---|---|---|---|
| 3.9.0（段 1 まで） | 1,142 | 128.3 | 0.264 |
| **4.2.0（段 2 まで）** | **991（−13%）** | 110.4 | **0.485** |

**全パラメータ学習は、方策を「速く」した。**遅くする施策（chunk 継ぎ目の平滑化・
RTC）が軒並み負けたのと対照的である（[06](06_step_count_drives_score.md)）。

## 引いたデータは全体の 4 分の 1 しかない

| | フレーム数 | epoch |
|---|---|---|
| 段 1 | 384,000 | 0.172 |
| 段 2 | 192,000 | 0.086 |
| **合計** | **576,000** | **0.257** |

（データ全体は 2,238,036 フレーム / 14,347 エピソード / 40 タスク）

**0.26 epoch でこれだけ動いたということは、まだ伸びしろがある。**
段 2 の loss が下がり続けていたことと合わせて、**本選では段 2 を延長するのが
最初の一手**になる。

## 中断したチェックポイントを使えるかの判断

**段 2 は 3,000 歩の予定で、途中の 1,000／1,500／2,000 歩も保存していた。**
「途中で止めると学習率が下がりきらず別物になる」問題は、**段 2 では起きない。**

| | 学習率の幅 | 途中で止めてよいか |
|---|---|---|
| 段 1 | 2.5e-5 → 2.5e-6（**10 分の 1**） | **駄目。**途中は別物になる |
| **段 2** | 5e-6 → 2.5e-6（**2 分の 1**） | **良い。**2,000 歩でも 3.2e-6 で、下がりきった値に近い |

**結果的には 3,000 歩が間に合ったので使わなかったが、この判断があったから
「間に合わなければ 2,000 歩を出す」という保険を持って進められた。**

## Claude 側 / 人間側

**Claude 側**: **loss が頭打ちになったとき、「データを増やす」「歩数を伸ばす」の
前に「凍らせている所が無いか」を見る。**今回は凍結を解くだけで −11% 動いた。

**人間側**: **GPU のメモリ制約で凍結したなら、それは「技術的な判断」ではなく
「資源の都合」である。**資源が変わったら、真っ先に見直す。
今回、外部の A100 を借りられた時点で全パラメータ学習に切り替えたのが、
結果的にいちばん大きな一手（0.264 → 0.485）になった。

**両方**: **学習ログは、チェックポイントとは別に持ち帰る。**
`train_config.json` には設定しか入っておらず、**loss の推移はログにしかない。**
今回は 45 KB のログを別途 `scp` した。これが無ければ「頭打ちだった」と
言えなかった。

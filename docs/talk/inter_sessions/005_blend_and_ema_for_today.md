# 005 `blend_steps` と `EMA` を測り、今日の提出物を作る

> **状態: 依頼中** ／ 受け側: 未定 ／ 更新: 2026-08-28

## 背景（先に読んでほしい）

**このコンペで何をしているか。** PARC2026 の本選 1 である。ロボット（Franka Emika Panda）に
自然言語の指示を与え、LIBERO-plus のシミュレータの中で物を掴んで運ばせる。
こちらの方策は **π0.5**（4,143,404,816 パラメータ）。
`solution/policy_server.py` が画像 2 枚（`front` と `wrist`）と状態を受け取り、行動列を返す。

**提出は 1 日 1 トラック 1 回だけである。** 今日（8/28）の枠はまだ使っていない。

| トラック | **こちらの点** | **最高点** |
|---|---|---|
| Track1 | **0.370** | **0.65** |
| Track2 | **0.207** | **0.53** |
| Track3 | 0.000 | 0.000（**全参加者 0**・投資しない） |

### 採点式は公開されている

```
smooth metrics = w1*time + w2*jerk + w3*SPARC + w4*trajectory + w5*rotation   (Σw = 1)
Total Score    = (1/N) * Σ successᵢ * (1 - collision penaltyᵢ) * smooth metricsᵢ
```

**成功は掛け算の門である。失敗した回・衝突した回は、その回の点がまるごと 0 になる。**
重み付きの和に入るのは 5 つだけで、**成功率は入っていない。**
重みと正規化の中身は非公開。

**衝突の判定は 1 mm である。**
`pipeline/rollout.py:233-234` が
`collided = any(d > 0.001 for d in object_max_disp.values())` と
`success = bool(done) and not collided` を計算している。
**対象は `obj_of_interest`（そのタスクの操作対象）に入っていない、ロボット以外のすべての物体。**

### 何を直そうとしているのか（依頼 001 の結果）

**8/28 に 216 本の衝突を 1 本ずつ測った。取り戻せる分がはっきりした。**

| | 本数 | 意味 |
|---|---|---|
| **ゴールに着いたのに衝突で落ちた** | **36** | **ここだけが取り戻せる。成功率で 16.7 ポイント** |
| 300 歩で着いていない | 13 | 衝突が無くても失敗 |
| （合計 216 本中の失敗） | 60 | — |

**その 36 本は「かすり」である**（実距離 L2）。

| | 値 |
|---|---|
| 中央値 | **4.44 mm** |
| 5 mm 未満 | **20 / 36** |
| **50 mm 以上** | **0 本**（最大 35.0 mm） |

**しかも 1 物体に集まっている。36 本のうち 20 本が `cookies_1` である。**
衝突 49 本のうち 22 本がクッキー箱の 2 タスクに集まり、
**同じ 2 タスクの 18 本のうち 8 本は `cookies_1` を 1 mm 未満に収めている**（中央値 1.14 mm）。
**同じ物理で通せる回があるので、避けようのない衝突ではなく制御の精度の問題である。**

**数 mm のかすりなら、行動列をならす後処理で届く見込みがある。** それがこの依頼である。

### `blend_steps` は測ってあるのに、一度も提出していない

**`PARC_BLEND_STEPS` は「行動列の継ぎ目を直前の行動へ寄せる本数」である**（既定 0 ＝ 寄せない）。
**過去の評価を公開式で付け直したら、同じ重み・同じ行で blend だけが違う組が 2 つあった。**

**組 A（36 行・2026-08-14・重み `pi05_24k`）**

| blend | **合計点** | 成功率 | **衝突率** | jerk の項 |
|---|---|---|---|---|
| 0 | 0.3571 | 0.694 | **0.167** | 0.516 |
| **4** | **0.3972** | 0.778 | **0.139** | **0.542** |

**組 B（48 行・カメラ方位角スイープ・2026-08-23・同じ重み）**

| blend | **合計点** | 成功率 | **衝突率** | jerk の項 |
|---|---|---|---|---|
| 0 | 0.3207 | 0.646 | **0.146** | 0.495 |
| **4** | 0.3210 | **0.646（同じ）** | **0.125** | **0.522** |

**再現しているのは 2 つ。衝突率が −17% と −14%、jerk の項が +5% と +5%。**
成功率は片方で +8.3 ポイント、もう片方で変わらず。
**36 行 1 エピソードの成功率のばらつきは 11.1 ポイントなので、組 A の +8.3 は雑音の内側である。
信じられるのは衝突と jerk である。**

**blend 8 は悪化していたが、12 行しか回っていないので比べられない**（合計点 0.3075）。

**なぜ落ちていたのか。** 予選の板にこう書いてある——「境界のモード跳びを狙った
`samples=3` が 0.04 本ぶんしか動かなかった。**同じ天井を狙う `blend_steps` も落とす**」。
**成功率だけを見て、狙いが同じだからと連座で落としていた。**
当時は手元の点が成功率そのものだったので、衝突と jerk の改善が点に出ていなかった。
**式が公開された今、この落とし方は根拠にならない。**

### `EMA` も比べる相手として要る

`PARC_EMA_ALPHA` は行動を指数移動平均でならす係数（既定 0.3）。
**8/27 に `EMA 0.5` の版（4.8.0）を Track2 へ提出したが、手元で一度も測っていない。**
blend と同じ「ならす」系なので、**どちらが効くかを並べて見る。**

**`blend 4` と `EMA 0.5` をクッキー箱 12 行で測って選び、勝った方を 72 行で確かめ、

**提出そのものはユーザがやる。** zip を HF の私有リポジトリへ上げて、
**そのままブラウザで落とせる形にするところまで。**

### 読む道具は 2 つある

### 採点環境は環境変数を渡さない

**評価では `PARC_BLEND_STEPS=4` と環境変数で渡せるが、提出物ではそれが効かない。**
`solution/policy_server.py` の**既定値を書き換える**必要がある。

```python
self._blend_steps = int(os.environ.get("PARC_BLEND_STEPS", "0"))   # ← この "0" を "4" にする
self._ema_alpha = float(os.environ.get("PARC_EMA_ALPHA", "0.3"))   # ← EMA ならこの "0.3"
```

**版の付け方。** いまリポジトリにあるのは **4.6.0**。
`__version__` の直上のコメントに履歴が並んでいるので、**そこへ 1 行足してから上げる。**

| 変える中身 | 上げ方 |
|---|---|
| blend 0 → 4 | **4.9.0** |
| EMA 0.3 → 0.5 | **4.10.0**（`EMA 0.5` は 8/27 の 4.8.0 と同じ中身なので、**その版を再利用してもよい**） |

**起動時の 1 行に必ず出ること。** `policy_server` は起動時に設定を 1 行印字する。
**採点ログに残る唯一の手がかりなので、`blend_steps=4` が出ていることを確かめる。**

```
[parc] policy_server 4.6.0  model=pi05  device=cuda  num_inference_steps=10
       n_action_steps=16  ema_alpha=0.3  blend_steps=4  samples=1  gain=(1.0,1.0)  seed=0 ...
```

### zip の作り方

**手順は [../../howto/02_build_submission.md](../../howto/02_build_submission.md) にある。**
**1 本 9.4 GB になるので、作る前に `df -h` で空きを見ること**——
過去にディスクが埋まって、書いている途中のファイルが 0 バイトになった事故がある。

**`sha256` を zip の隣に必ず書き出す。** 上げ直したものが同じか、
後から確かめられなくなる。

**HF の私有リポジトリ `siruku6/parc2026-submission` へ上げる。**
Xet の重複排除が効くので、**中身がほとんど同じ zip の上げ直しは 30 秒で終わる**実測がある。

## やること

1. **`git pull` する。** `COOKIE12.csv` と、`run_final_eval.sh` の直し
   （`TASKS_CSV` を相対パスで書けるようにした）が降りてくる。

2. **`blend 4` を 12 行で測る（20 分）。**

   ```bash
   cd ~/src/PARC2026_pre && git pull && \
     TASKS_CSV=compe/val/COOKIE12.csv TRACK_EPISODES=3 MUJOCO_GL=egl \
     PARC_N_ACTION_STEPS=16 PARC_EMA_ALPHA=0.3 PARC_BLEND_STEPS=4 \
     LABEL=cookie_blend4 solution/tools/eval/run_final_eval.sh track2
   ```

3. **`EMA 0.5` を同じ 12 行で測る（20 分）。**

   ```bash
   cd ~/src/PARC2026_pre && \
     TASKS_CSV=compe/val/COOKIE12.csv TRACK_EPISODES=3 MUJOCO_GL=egl \
     PARC_N_ACTION_STEPS=16 PARC_EMA_ALPHA=0.5 PARC_BLEND_STEPS=0 \
     LABEL=cookie_ema05 solution/tools/eval/run_final_eval.sh track2
   ```

4. **2 つを基準（成功率 0.389・衝突率 0.611・変位の中央値 4.44 mm）と並べ、
   勝った方を決める。** 判定は下の「進む・止めるの決め方」に従う。

5. **勝った方を 72 行で確かめる（1 時間）。**

   ```bash
   cd ~/src/PARC2026_pre && \
     TASKS_CSV=compe/val/TRACK2_VAL72.csv TRACK_EPISODES=3 MUJOCO_GL=egl \
     PARC_N_ACTION_STEPS=16 PARC_EMA_ALPHA=<勝った値> PARC_BLEND_STEPS=<勝った値> \
     LABEL=val72_<名前> solution/tools/eval/run_final_eval.sh track2
   ```

   **比べる相手は合計点 0.3674・衝突率 0.2269 である。**

6. **`policy_server.py` の既定値を書き換えて版を上げる。** コメントに
   **何をどう測って決めたかを 3 行以内で残す**（そこが後から読まれる唯一の場所である）。

7. **zip を作り、`sha256` を隣に置き、HF の私有リポジトリへ上げる。**

8. **ユーザへ渡す形にまとめる。** どの zip をどのトラックへ出すのか、
   **sha256 と一緒に 1 行で。**

## 進む・止めるの決め方

**5 に進むかどうか（12 行の結果で判定）。**

| 見るもの | 進む | 止める |
|---|---|---|
| **変位の中央値**（36 個の連続値・いちばん敏感） | **4.44 mm より下がった** | 上がった |
| 衝突率 | 0.611 より下がっている（ばらつき 0.081 なので参考） | 大きく上がった |
| 成功率 | 0.389 より下がっていない | 明確に下がった |

**変位の中央値が下がって成功率が落ちていなければ進む。**

**提出するかどうか（72 行の結果で判定）。**

| 見るもの | 出す | 出さない |
|---|---|---|
| **合計点** | **0.3674 + 0.04 以上**、または**衝突率が 0.2269 より明確に下がって合計点が下がっていない** | 合計点が 0.3674 − 0.04 より下 |

**両方が空振りだったら、今日は 3 枠とも出さないでよい。**
**当てずっぽうで枠を使うより、明日 RunPod の重みと一緒に出した方が読める。**
**その判断はユーザに渡すこと**（勝手に「出さない」で終わらせず、
**数値を並べて「出さないのが良いと考える」と書く**）。

## 判断が必要になったら

**この依頼の目的は「数 mm のかすりを、ならす後処理で減らせるか」を今日のうちに決め、
減るなら今日の枠で採点側に当てることである。**

**その目的に照らしてより良い測り方を思いついたら変えてよい。**
たとえば 12 行の結果が両方とも紛らわしいときは、
**同じ 12 行をエピソード数を増やして回し直す**方が、別の候補を試すより早く決まる
（12 行 × 5 エピソード = 60 本で約 30 分）。
**変えた場合は、変えたことと理由を報告に書くこと。**

**次の 2 つは変えないでほしい。**

| 変えないもの | なぜ |
|---|---|
| **1 変数だけ動かすこと** | `blend` と `EMA` を同時に変えると、どちらが効いたか読めなくなる。**採点の枠は 1 日 1 回しかない** |
| **`PARC_N_ACTION_STEPS=16`** | 基準の 8/28 の実行がこの値である。変えると 0.3674 と比べられない |

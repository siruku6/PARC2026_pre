# 04. 本番と同じ形で評価する（提出前の判断に使える検証を作る）

**この手順を最後まで実行すると、「手元の数字を信じて提出してよいか」が
はっきりする。**

## なぜ要るのか

**手元の 84 件の検証は、採点環境の結果と順序が逆になった。**

| 重み | 手元 84 件の成功率 | 採点環境の総合スコア |
|---|---|---|
| 素（`lerobot/smolvla_libero_plus@7bb70aa5`） | 0.476 | **0.1409** |
| λ=0.25 のブレンド | （未測定） | 0.095 |
| LoRA 20,000 ステップ | **0.500**（素より上に見えた） | **0.016** |

**手元では追加学習した重みの方が良く見えたが、採点環境では 8.8 倍悪かった。**
この状態では提出枠を有効に使えない。

原因は母集団の違いである。

| | エピソード数 | 何を並べているか |
|---|---|---|
| 手元の 84 件 | 84 | LIBERO-plus の摂動 7 カテゴリ × スイート 4 つ |
| **採点環境** | **8** | **「同一タスク・同一ドメインにおける、テクスチャなどの摂動」** |

- **採点環境が 8 エピソードであること**は、採点ログの `POST /reset` の回数を
  数えて分かる（4 提出すべて 8）。**打ち切りはちょうど 300 ステップ**で、
  `/reset` の間の `POST /act` の回数の最大が全提出で 300 だった。
- **タスクの範囲**は運営 Q&A No.21 の回答による。「7 カテゴリすべてが
  含まれているわけではありません。…予選スライドの Track 1 のタスク詳細で
  説明されている『同一タスク・同一ドメインにおける、テクスチャなどの摂動』に
  該当すると考えられるものが含まれています」。
- 同じ回答の (4) で、採点ログに出る `タスク用途: 3_Omni` は
  **「デバッグ時の名残」で意味を持たない**と説明されている。追う必要はない。

## 件数を減らすだけでは足りない

**先に押さえること。件数を 84 から 8 に減らしても、手元と本番が逆になる現象は
消えない。** 原因は件数ではなく、**学習に使ったタスクを検証にも使っていること**
である。

- **学習側**は全エピソードを使う。[../../solution/train/train.py](../../solution/train/train.py)
  の `--episodes-per-task` は既定 0 で「全 14,347 本を使う」と書かれており、
  エピソードの選び直しは `frame.groupby("task")` で回る。
  **タスクを丸ごと外す引数が無い。**
- **検証側**の `make_validation_suite.py` は LIBERO-plus の
  `task_classification.json` から選ぶ。これは**同じタスクの摂動版**である。

**つまり手元の数字は「覚えた度合い」を測っている。** 追加学習した重みが
手元で素より上に見えたのは、それで説明が付く。**どちらの数字も正しく、
測っているものが違う。**

さらに `train.py` の `--emphasize-tasks` の説明に
「**84 件の検証用データで切り分けたら**、落としているのは摂動ではなく
特定のタスクだった」と書かれている。**検証結果が学習データの配分も決めている。**

> **これはルール上の問題ではない。** 運営 Q&A No.33 の回答は
> 「ご自身の環境での自己評価の結果（タスク別成功率等）を『何を学習するか』の
> 選定に使うことは問題ありません」と明言している。
> **測定として混ざっているという話である。**

### 摂動版の id を外すだけでは足りない

**摂動版は元のタスクの実演データを共有する。** 検証に使う件の
`libero_plus_id` を学習から抜いても、**同じ指示文の別の摂動版が学習に残る**ので、
実演の中身は見たままになる。**指示文（タスク）単位で丸ごと分ける必要がある。**

### 出発点の重みは全タスクを見ている

**ここは直せない。** 素の重みに同梱された `train_config.json` によれば、
素の重みは `lerobot/libero_plus` 系のデータで 20,000 ステップ・バッチ 32 学習済みである。
**LIBERO-plus のどのタスクも、素の重みにとっては未知ではない。**

したがってタスクを外して得られるのは
**「こちらが足した学習が、覚えていないタスクでも効くか」**であって、
素の重みとの絶対的な比較が綺麗になるわけではない。**それでも、こちらの
記憶による下駄が外れるので、素との比較は本番の向きに近づく。**

## 配布 4 タスクを代理に使うときの注意

**配布されている 4 タスクは、まさにその 2 カテゴリだけで構成されている。**

| # | スイート | 摂動カテゴリ | 難易度 | 接尾辞 |
|---|---|---|---|---|
| 1 | `libero_spatial` | Background Textures | L3 | `_table_2` |
| 2 | `libero_object` | Background Textures | L5 | `_table_27` |
| 3 | `libero_object` | Light Conditions | L2 | `_light_15` |
| 4 | `libero_goal` | Light Conditions | L4 | `_light_11` |

出典は [../../compe/t1/T1_TASKS.csv](../../compe/t1/T1_TASKS.csv) である。
**4 タスク × 2 エピソード = 8 で、採点環境のエピソード数と一致する。**

> **ただしこの 4 タスクも学習に使われている**（`libero_plus_id` は
> 80 / 241 / 2408 / 2467）。**代理集合として使うなら、この 4 タスクを
> 学習から外す必要がある。** 外す口は `train.py` にまだ無い（下の
> 「まだ足りていない口」）。
>
> **`make_validation_suite.py` の `--exclude` は向きが逆である。**
> 既定が `compe/t1/T1_TASKS.csv` になっているが、これは
> 「**検証集合から** 例示を外す」ためのもので、学習からは外さない
> （`_load_excluded` の説明に「検証用スイートから外すため」とある）。

## 手順 1：本番と同じ形で 8 本を実行する

**新しいスクリプトは要らない。配布された評価パイプラインがそのまま使える。**

```bash
python -m pipeline --server-url http://localhost:8000 \
    --track track1 --n-episodes 2 --max-steps 300 --seed 42 \
    --output-dir outputs/0812_base_t1
```

| 引数 | なぜこの値か |
|---|---|
| `--track track1` | `libero_t1` スイートに解決される（[../../pipeline/config.py](../../pipeline/config.py) の `TRACK_BENCHMARKS`）。このスイートは [../../compe/t1/register.py](../../compe/t1/register.py) が `T1_TASKS.csv` から登録する**公開 4 タスク**である |
| `--n-episodes 2` | **タスクあたりの本数**である。4 × 2 = 8 になる。**既定は 20 なので必ず指定する**（そのままだと 80 本になる） |
| `--max-steps 300` | 採点環境の打ち切りと同じ。既定も 300 だが、明示しておく |
| `--seed 42` | 配布時の既定値。**提出間で条件を変えないため固定する** |

所要は 8 本で **15 分ほど**である（1 本あたり 1.7 分。84 件で 2 時間 21 分だった実測から）。

方策サーバーの起動と GPU の使い方は [03_gpu_eval.md](03_gpu_eval.md) と同じである。
**評価側と方策側でイメージが 2 つ要る**点も変わらない。

## 手順 2：この検証が使えるかを検定する

**ここが本題である。** 手元の数字を信じる前に、**答えが分かっている重みで
実行して、順位が採点環境と一致するかを見る。**

答えは 3 つある。

| 重み | 置き場所 | 採点環境の総合スコア |
|---|---|---|
| 素 | `work/artifacts/model_weights_base` | **0.1409** |
| λ=0.25 のブレンド | `work/artifacts/model_weights_lam025` | **0.095** |
| LoRA 20,000 ステップ | `work/train/smolvla_lora_all_suites/merged_model` | **0.016** |

**少なくとも 2 つで実行する。** 素と LoRA 20,000 ステップは差が大きいので、
まずこの 2 つでよい。

```bash
# 素の重みで 8 本
MUJOCO_GL=osmesa WEIGHTS=work/artifacts/model_weights_base LABEL=base_t1 \
    bash solution/tools/eval/run_docker_eval.sh --detach
# 終わってから、追加学習した重みで 8 本（**同時に流さない**）
MUJOCO_GL=osmesa WEIGHTS=work/train/smolvla_lora_all_suites/merged_model \
    LABEL=lora20k_t1 bash solution/tools/eval/run_docker_eval.sh --detach
```

> **`run_docker_eval.sh` は 84 件のスイートを作る作りになっている。**
> 8 本にするには、上の `python -m pipeline` の引数
> （`--track track1 --n-episodes 2`）が渡るようにするか、
> 手順 1 のコマンドを直接実行する。**渡した引数が実際に効いたかは、
> 出力の `server_*.json` の `metadata.eval_config` で確かめられる。**

## 手順 3：採点環境と突き合わせる

```bash
python3 solution/tools/analysis/compare_with_production.py \
    --pair "outputs/0812_base_t1=outputs/prod_eval_results/260810_評価結果_ema=0.3あり.md" \
    --pair "outputs/0812_lora20k_t1=outputs/prod_eval_results/260811_評価結果_ema=0.3あり_初回学習後.md"
```

**出るもの。**

| 見出し | 中身 |
|---|---|
| 組ごとの要約 | 採点環境と手元の、エピソード数・打ち切り・張り付いた本数・スコア |
| **エピソードごとのステップ数** | **本数が一致したときだけ**、1 本ずつ並べて差を出す。差が 10 ステップを超えた回に `*` が付く |
| **代理として使えるか** | **これが判定である。** 下の「同順の扱い」を読むこと |
| 気になった点 | 本数や打ち切りが違うなど。同じ指摘は 1 度しか出ない |

**終了コードは、判定が通ったときだけ 0 になる。** 比べられないときは 1 を返す。

### 同順の扱い —— 本番スコアの小さな差は判定に使わない

**採点環境の分解能は低い。** 8 本のうち **1〜4 本目は 3 種類の重みすべてで
300 ステップに張り付いた**ので、差が付くのは残り 4 本だけである。

| 提出 | 本番スコア | 8 本のステップ数 | 打ち切り |
|---|---|---|---|
| 素 | **0.1409** | 300, 300, 300, 300, 138, 132, 174, 182 | 4/8 |
| λ=0.25 | **0.095** | 300, 300, 300, 300, 143, 177, **300**, 168 | 5/8 |
| LoRA 20k | **0.016** | 300, 300, 300, 300, 234, **300**, 139, **300** | 6/8 |

**素とλ=0.25 の違いは、7 本目が 174 ステップで終わったか 300 ステップまで走ったかである。**
差は 0.046 しかない。**この順序を再現できたことを根拠に代理集合を合格にすると、
偶然を実力と読み違える。**

そのため `compare_with_production.py` は
**本番スコアの差が `--score-tie`（既定 0.05）以内のものを同順にまとめ、
段をまたぐ組み合わせだけで判定する。** 既定値だと素とλ=0.25 が 1 段目、
LoRA 20k が 2 段目になる（0.095 − 0.016 = 0.079）。

**読めるのは段の違いまでである** —— 「素の系統か、崩壊したか」の区別である。

### 打ち切り本数も判定に使う

**1 つの合成スコアより、8 本のステップ数のほうが情報が多い。**
打ち切りに張り付いた本数は 4 / 5 / 6 と単調に増えており、
**合成スコアより素直な信号である。**

判定では 2 つの向きを別々に出す。

| 信号 | 良い向き |
|---|---|
| 手元のスコア | 本番スコアが高い側が高い |
| 手元の打ち切り本数 | 本番スコアが高い側が少ない |

**スコアの向きが揃えば合格とするが、打ち切り本数だけ逆のときは名指しする。**

### 何を見て判断するか

| 見えたもの | 意味 | 次の手 |
|---|---|---|
| **向きが食い違わなかった** | この 8 本は提出前の判断に使える | **採用する。** ただし**段の違いだけ**を信じる |
| 向きが食い違った | 学習に使ったタスクを検証にも使っている | **学習から外す**（上の「件数を減らすだけでは足りない」） |
| すべて同順と言われる | 比べた提出の本番スコアが近すぎる | 差が 0.05 を超える提出どうしで比べる |
| ステップ数が半分以上の回で 10 ステップを超えて違う | 同じタスクを実行していない可能性がある | `--seed`・`--max-steps`・タスクの登録を確かめる |
| 本数が違う | `--n-episodes` を渡し忘れた | 手順 1 の引数を見直す |

**ステップ数の形も手がかりになる。** 採点環境では 4 提出すべてで
**最初の 4 本が必ず 300 ステップに張り付き、後の 4 本は変動している。**
手元で同じ形が出れば、同じタスクを実行している裏付けになる。

## 手順 0：学習と検証でタスクを分ける

**上の手順より先にこれを済ませる。** 分けていない検証は「覚えた度合い」を
測るだけである。

### 0-1. 外すタスクの一覧を作る

```bash
python3 solution/tools/suite/make_holdout_split.py
```

**8 タスクを外す**（配布 4 タスク ＋ 同じ 2 カテゴリから 4 つ）。
出力は `compe/val/HOLDOUT_TASKS.csv` で、**学習側と検証側が同じこの 1 枚を読む。**

```
[holdout] 自己検査: libero_spatial の 10 件が一致した
[holdout] 素のタスク 全 40 種 / 外す 8 種 / 学習に残る 32 種
[holdout] 摂動版で数えると 全 10030 件 / 学習に残る 8049 件
[holdout] 外したタスクのうち、本番と同じ 2 カテゴリの変種は 464 件（検証に使える上限）
```

**`自己検査` の行を必ず確かめる。** 摂動版の名前から素のタスク名を取り出す処理が
配布ノートブックの `SPATIAL_TASK_NAMES`（10 件）と一致するかを見ている。
**一致しなければ例外で止まる** —— LIBERO-plus の版が変わって接尾辞の形が
変わったときに、黙って間違った一覧を作らないためである。

本数を変えるときは `--extra` を渡す（`--extra 0` なら配布 4 タスクだけ）。
**選び方に乱数は使っていない。** 同じ入力なら同じ一覧になる。

### 0-2. 学習からそのタスクを外す

```bash
python train.py --holdout-tasks compe/val/HOLDOUT_TASKS.csv
```

**外した指示文がデータセットに 1 つも無ければ、その場で止まる。**
データセット側の書き方の例を並べて示すので、食い違いに気付ける。

```
[train] 除外: 8 タスク / 2,8xx エピソードを学習から外した
[train]   残り 11,xxx エピソード / 32 タスク
[train]   `--dataset.episodes` の長さ 約 70 KB
```

> **全部使うときは `--dataset.episodes` を省けるが、外すときは番号を並べる。**
> 長さが出るので、極端に大きければ気付ける。
>
> `--episodes-per-task` や `--emphasize-tasks` と併用してもよい。
> **3 つの経路すべてで除外が効く。**

### 0-3. 検証集合を外したタスクだけにする

```bash
python3 solution/tools/eval/make_validation_suite.py \
    --libero-plus work/LIBERO-plus \
    --holdout compe/val/HOLDOUT_TASKS.csv \
    --categories 'Light Conditions' 'Background Textures'
```

```
[val] 検証に使うのは外した 8 タスクの摂動版だけ: 10030 件 -> 1981 件
```

**1 件も残らなければ止まる。** 空の検証集合で重みの採否を決めないためである。

## やらないこと：採点ログから本番のタスクを特定する

**採点ログにタスク名は出ていない**（出るのは `タスク用途: 3_Omni` だけで、
これは Q&A No.21 (4) により「デバッグ時の名残」で意味を持たない）。
`/reset` で届く指示文を `policy_server.py` に出力させれば特定できてしまうが、
**やらない。**

**運営 Q&A No.33 の回答が線を引いている。**

> 禁止対象の「評価観測を保存しての後続学習」は、**運営の採点（本番評価）で
> 得られた観測・結果を利用すること**を指します。ご自身の環境での実行は
> これに含まれません（…）**禁止されるのは、運営の採点環境から得られた情報を
> 利用することです。**

- **自分の環境の自己評価をもとに学習内容を決めるのは問題ない**（同回答が明言）。
- **採点環境から得た情報でタスクを特定し、それを学習や検証の選定に使うのは
  禁止側である。**
- `/reset` と `/act` の**回数からステップ数を読むのは観測の保存ではなく、
  学習にも使っていない**。この文書のやり方はここで止める。
  **タスクの同一性まで踏み込まない。**

判断に迷う使い方をしたくなったら、**先に運営へ質問を出す。**

## 使えなかったときに広げる

**2 カテゴリのまま本数を増やす。** 摂動カテゴリを絞った 24 件のスイートが
すでに用意されている。

```bash
CATEGORIES='Light Conditions,Background Textures' \
    bash solution/tools/eval/run_docker_eval.sh --detach
```

24 件で **39 分**である（実測）。**8 本で差が小さすぎて判別できないときの
判別用**にも使える。

**84 件のスイートは「壊れていないかの確認」に格下げする。**
成功率の順序は当てにならないが、**動かなくなった・固まったといった
大きな壊れ方は拾える。**

## 落とし穴

| 症状 | 原因 | 対処 |
|---|---|---|
| 80 本流れる | `--n-episodes` を渡していない（既定 20） | 2 を渡す。`server_*.json` の `metadata.eval_config` で確認する |
| 600 ステップまで走る | `pipeline/config.py` の既定 600 が効いている | `--max-steps 300` を渡す |
| `[結果]` 行が読めない | 古い評価ログ | ステップ数の解析は `summarize_gpu_eval.py` の `_parse_log` と共通である。そちらが読めるログなら読める |
| 順位を比べられないと言われる | 組が 1 つしかない、またはスコアが読めない | 組を 2 つ以上渡す。`server_*.json` があるか確かめる |

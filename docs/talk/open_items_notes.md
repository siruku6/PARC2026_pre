### 24. 環境由来の衝突を、方策の衝突率から外す — **入れた（8/11）**

**ケチャップが空から落ちてくる**（[05_実測結果.md](../strategy/05_実測結果.md)）。
`LIVING_ROOM_SCENE1` / `SCENE2` の衝突は方策のせいではない。
**このままでは衝突対策の効き目を測り間違える。**

**実物のログ（8/10 の 25 件）で確かめた。水増しは 2.25 倍だった。**

```
=== 衝突の切り分け ===
  衝突した回 9 件 / 全 25 件
  ├ 環境由来だけ               5  （同じ変位が繰り返し出ている物体しか動いていない）
  └ **方策由来を含む           4**  ← 衝突対策で拾えるのはこの分

  **方策の衝突率      0.160**  (4/25)  ← 対策の効き目はこれで測る
  環境を含む衝突率    0.360  (9/25)  ← **本番のスコアに乗るのはこちら**

  環境由来と見た物体（同じ変位が 3 回以上）:
    ketchup_1=544.6mm
```

**判定は「同じ変位が 3 回以上出たか」だけで行う。**
物体の名前では決めない —— 同じ物体でも、方策がぶつける回と環境が落とす回がある。

| 使えた材料 | どう使ったか |
|---|---|
| **変位が何本も同じ値** | **判定に使う。** 0.1mm も違わないのは方策の振る舞いではない |
| `初衝突 N 歩` | **報告だけ。** 方策が本当に早くぶつかることもあるので決められない |
| ぶつけた物体の名前 | 判定に使わない（上記のとおり） |

**1 つでも方策由来があればその回は方策由来として数える**（対策で拾える回を
取りこぼさないため）。**「衝突しうる相手の数で割る」の節も方策由来だけに直した** ——
どの方策でも同じだけ出る分を混ぜると差が薄まる。

> **本番側は直せない。** 落ち着かせる 10 ステップは採点側のコードである。
> **「方策の衝突率」はスコアの予測ではなく、対策の効き目を測るための数字である。**
> この区別が無いと、**衝突対策を入れても数字が動かず「効かなかった」と
> 読んでしまう**（環境由来の分が下限として残るため）。

**試験を 6 件足した**（[tests/test_rollout_report_line.py](../../tests/test_rollout_report_line.py)）。
2 回では環境由来にしないこと、0.1mm 違えば方策由来にすること、
混ざった回を方策由来として数えること、報告に両方の率が出ることを固定した。

### 23. EGL で描けるようにする — **閉じた（8/11）。このマシンでは原理的に無理**

**診断で決着した。このマシンの vGPU は計算専用の製品である。**

```
$ nvidia-smi -q | grep -iA3 -e virtualization -e vgpu
    GPU Virtualization Mode
        Virtualization Mode               : VGPU
    vGPU Software Licensed Product
        Product Name                      : NVIDIA Virtual Compute Server
        License Status                    : Licensed (Expiry: 2026-8-11 23:50:59 GMT)
```

**`NVIDIA Virtual Compute Server`（vCS）は OpenGL / Vulkan に対応しない。**
vGPU の製品は用途で分かれており、**描画が使えるのは vWS（Virtual Workstation）系だけ**である。

| 製品 | 計算 | 描画 |
|---|---|---|
| **vCS（このマシン）** | ○ | **×** |
| vWS | ○ | ○ |

**こちら側では直せない。** マシンを貸している側が profile を変えるしかない。

> **「空の球が 0.2 ms で描けた」という観測も、これで説明が付く。**
> GPU で描けていたのではなく、**実質何も描いていなかったか、
> ソフトウェアに落ちていた。** 0.2 ms という速さ自体が不自然だった。
> **前回この観測を「GPU 描画で動いている」の根拠に使ったのは誤りである。**

**残るのは `osmesa`（CPU 描画）で 1 ステップ 384 ms・84 件 2.7 時間。**
**評価を速くする手は、スイートを絞ること（項目 29 ②）だけになった。**

#### ライセンスの期限に注意 — **今日の 23:50 GMT（8/12 08:50 JST）**

**vGPU のライセンスは通常は自動で更新される**（多くは 1 日の貸出を半分の時点で
延長する）。**ただしライセンスサーバーに届かないと、CUDA が止まるか性能が落ちる。**

**締切の 2 日前に GPU が止まると詰む。** その時刻をまたぐ長い実行を、
確かめずに仕掛けないこと。

```bash
# 09:00 過ぎに 1 回見る。Expiry が翌日に伸びていれば自動更新されている
```

### 19. 学習用と評価用のイメージを分ける — **17 のあとで判断**

#### 固定の 2 つは、LoRA を付けている限り効かない

**LeRobot の SmolVLA は、LoRA を当てる場所を自分で決めている。**

```python
# work/lerobot-src/src/lerobot/policies/smolvla/modeling_smolvla.py:495-504
def _get_default_peft_targets(self) -> dict[str, any]:
    common_projections = (
        "state_proj|action_in_proj|action_out_proj|action_time_mlp_in|action_time_mlp_out"
    )
    target_modules = rf"(model\.vlm_with_expert\.lm_expert\..*\.(q|v)_proj|model\.({common_projections}))"
    return {"target_modules": target_modules, "modules_to_save": []}
```

**当たるのは action expert の q/v 射影と、5 つの射影層だけである。**
**視覚側にも言語側にもアダプタが 1 つも無い。**

PEFT は元の重みを全部固定してアダプタだけ学習するので、
**`freeze_vision_encoder` と `train_expert_only` を `false` にしても、
学習される重みは 1 つも変わらない**（`requires_grad` はどちらの経路でも `False` になる）。
`.eval()` か `.train()` かが変わるだけである（dropout の有無）。

**`verify_merge.py` の結果がこれを裏づけている。** 変化した 37 テンソルは
**32（expert の q/v が 16 層 × 2）＋ 5（射影層）** で、
**`target_modules` の当たる場所と 1 つも違わない。**

| 視覚側も学ばせるには | 費用 |
|---|---|
| **(A) LoRA を外して全パラメータ学習** | 出発点と同じ recipe。**時間・メモリ・忘却のリスクが最大** |
| **(B) `--peft.target_modules` に視覚側を足す** | 中間。**正規表現を自分で書く。効く場所の当てが要る** |
| **(C) LoRA のまま（今の形）でデータと学習率だけ直す** | **変更が 1 軸に絞れる。いちばん安全** |

**勧めるのは C を先、余力で B か A である。** 理由は 2 つ。

1. **固定が悪かったという証拠は無い。** 8.8 倍の悪化は
   **データ量（18 倍の繰り返し）と学習率（3 倍）だけで説明できる。**
2. **`train_expert_only=true` は LeRobot の既定値である**
   （`configuration_smolvla.py:69-70`）。配布ノートブックの手落ちではない。
   出発点のほうが既定から外れている。

> **「集計が jerk を出していない」と書いたのは誤りだった。**

> `_report_json` は最初から `mean_avg_cartesian_jerk` /

> **読まずに「無い」と書いた。**

**代わりに 2 つ入れた。**

|---|---|
| **`--compare <別の出力先>`** | **2 回を並べて差を出す。** 84 件の報告を 2 つ見比べると見落とす |
| **出せなかった行を名指しする** | **行が無いのを「差が無い」と読み違えるのを防ぐ。** 滑らかさの行が消えるのがいちばん危ない |

```
  方策の衝突率                     0.125     0.160   -0.035  良くなった
  平均ジャーク                     3.721     3.900   -0.179  良くなった

    **「差が無い」ではない。**
```

#### 本番のスコアは手元で計算できない — **確かめた（8/11）**

**配点の設定ファイルが配布物に無い。**

| ファイル | 中身 | 手元に |
|---|---|---|
| `total_score_config.json` | 各指標の重み | **無い** |
| `normalization_config.json` | 正規化の基準値 | **無い** |

`pipeline/total_score.py` の内蔵既定は `weights` も `references` も**空**で、
`pipeline/scorer.py` は `overall_score = overall_success`（成功率そのもの）を返す。

**だから手元で比べられるのは成功率と滑らかさの指標までで、順位は予測できない。**
係数 0.282 / 0.064 は**本番のスコアと成功率から逆算した値**である。

### 27. 素の重みと学習後を λ で混ぜる — **保険**

**θ = (1−λ)·θ素 + λ·θ学習後** を作る。学習は要らない（数分）。

**狙いは「独自学習を行った提出物で、素の重みに負けない」ことである。**
Q&A No.36 は学習を必須にしているが、**スコアで負ける重みを載せる義理は無い。**

LoRA なら簡単である。**マージするときの強さを λ 倍するだけ。**

| λ | 中身 |
|---|---|
| 1.0 | いまの 4 回目（0.016） |
| **0.3〜0.5** | **測る価値がある範囲** |
| 0.0 | 素の重み。**学習の事実が消えるので採らない** |

> **λ を「素にどれだけ近づけられるか」で選ばない。** それは要件の潜り抜けになる。
> **84 件の検証スイートで選ぶ**（これは WiSE-FT として論文になっている手法である）。

### 30. 学習を流す — **回 A から。ここが「どの回を流すか」の一覧である**

### 22. 見た目の振れ幅 — **測った。結論は「拡張ではなくデータ量」（8/11）**

**共有された EDA の結論は「明るさだけでなく gamma・contrast・texture の拡張が
必要そう」だった。半分は裏づけが取れ、半分は逆だった。**

| 確かめたこと | 結果 |
|---|---|
| いま有効な拡張の範囲 | **明るさ ×0.8〜1.2。gamma は無い**（LeRobot の既定 6 種から最大 3 種） |
| 評価側の振れ幅 | `table`/`tb` の平均を基準に `light` は **×0.71**、`tb` の上端は **×1.70** |
| → 拡張は覆えているか | **覆えていない** |
| **学習データ自体の振れ幅** | **0.086〜0.723。評価側を含んでいる**（14,347 本。選んだ 200 本も同じ幅） |

**「届く範囲が無い」のではなく「密度が薄い」のだった。**
200 本しか使っていないので、幅は足りていても中身が疎になる。

**→ 打つ手は拡張を増やすことではなく、データを増やすことである（18）。**
**全データを使えばこの問題は自然に消える。** 拡張はそのあとの上積みとして考える。

測り方は残してある（方策を動かさずに数分で終わる） —
[plan/02_appearance_and_data.md](../plan/02_appearance_and_data.md)。
